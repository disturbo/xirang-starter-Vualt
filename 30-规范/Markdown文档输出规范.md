# Markdown 文档输出规范 v2.1

> 定义 vault 内所有 AI agent 输出 Markdown 文件的：命名 · 放置 · 排版 · 粒度。
> 本规范管「叫什么名」「放在哪」「怎么排」「什么时候该新建文件」，不管「写什么」——业务内容由各专项规范管理。
> 最后更新：2026-05-19 · v2.1

---

## 0 规范哲学：生成式优先，校验兜底

本规范采用**生成式设计**：为每种场景提供决策树和模板，agent 创建文件时**查表填空**即可产出合规命名和路径。校验脚本（lint）只是兜底安全网，不是主要指导手段。

**为什么不用纯校验式**：
- LLM 擅长模式匹配和模板填充，不擅长记忆 50 条禁令
- 命名和放置决策发生在文件创建瞬间——事后校验无法回溯"当时应该放哪"
- 生成式规范让 agent 只需回答"我在做什么类型的事？"即可得到正确答案

**执行优先级**：决策树 > 模板 > 硬规则 > 校验报错

## 1 适用范围

本规范适用于 vault 内所有 AI agent 输出的 `.md` 文件，包括但不限于：

- PRD / 设计方案 / 逻辑确认稿
- 资料摘要 / 飞书采集文档
- 会议纪要
- 规范文档本身

### 1.1 文件粒度规范：禁止阶段性拆分

> 这是本规范**最优先执行**的铁律。排版问题可以修，文件碎片化一旦形成极难清理。

| # | 规则 | 说明 |
|---|------|------|
| 1.1.1 | **同一主题的连续阶段合并** | 同一项目/同一路线的多个阶段（Phase 1/2/3、Step 1/2/3、上篇/下篇），必须合并为**一个文件**，用章节标题分隔 |
| 1.1.2 | **禁止按阶段新增文件** | 禁止产出 `Phase1-xxx.md` + `Phase2-xxx.md` + `Phase3-xxx.md` 这种碎片文件。它们是一件事的不同步骤，不是一个系列的独立文章 |
| 1.1.3 | **真正需要拆分的情况** | 当单一文件超过 **15KB 或 600 行**时，才允许拆分。拆出来的文件必须：① 文件名含 `(上)`/`(下)` 或 `第N部分` 标注；② 每篇 frontmatter 加 `series: "系列名"` 字段；③ 首篇末尾和续篇开头互挂 wikilink |
| 1.1.4 | **执行记录单文件原则** | 任何升级/优化的执行记录，除非用户明确要求分开写，否则全部写在**一份**文件内。多个 Phase 用 `## Phase N` 标题区分 |
| 1.1.5 | **违规检查** | doc-gardening cronjob 每周末自动扫描「同一主题碎片文件组」，推送熵报告时标注。Hermes 发现碎片后主动提议合并 |

> **判断标准**：如果你发现自己在给文件取名时犹豫"要不要加 Phase X 后缀"——答案永远是「不要加，合并到一个文件里」。

### 1.2 与现有规范的关系

| 规范 | 管什么 | 本规范补什么 |
|------|--------|-------------|
| [[30-规范/PRD输出规范-通用版-v1.0]] | 内容骨架、章节顺序 | Markdown 排版格式 |
| [[30-规范/原型输出规范-v3.2]] | HTML/CSS 视觉 | 不涉及 |
| [[30-规范/飞书文档采集规范]] | 采集流程与后处理 | 采集产出物的排版 |
| [[30-规范/会议纪要处理规范]] | 会议内容结构 | 纪要文档的排版 |

> **原则**：本规范是排版底线，各专项规范可在此基础上追加更严格的要求，但不得放宽。

## 2 标题规范

| # | 规则 | 说明 |
|---|------|------|
| 2.1 | 层级上限 | 最深到 H4（`####`），H5/H6 禁用——大纲面板可读性差 |
| 2.2 | 文档标题 | 第一个 H1 = 文档标题，全篇仅此一个 H1；正文从 H2 开始 |
| 2.3 | 编号触发 | 标题总数 ≥ 30 时**强制编号**；< 30 时可选 |
| 2.4 | 编号格式 | `## 1 一级章节` → `### 1.1 二级` → `#### 1.1.1 三级`；文档标题（H1）不编号 |
| 2.5 | 编号方式 | 数字烘焙到标题文本中（非 CSS 伪元素），保证 Obsidian 大纲面板可见 |
| 2.6 | 标题前空行 | 标题前必须有 1 个空行（紧接前文会导致渲染异常） |
| 2.7 | 标题后空行 | 标题后紧跟正文，不加额外空行（Markdown 标准行为） |

### 2.1 编号示例

```markdown
# {项目}服务模块PRD        ← H1 文档标题，不编号

## 1 版本信息            ← H2 从 1 开始
## 2 需求概述

### 2.1 背景             ← H3 = 父级.序号
### 2.2 目标

#### 2.2.1 短期目标      ← H4 = 父级.序号
#### 2.2.2 长期目标

## 3 功能设计
```

## 3 表格规范

| # | 规则 | 说明 |
|---|------|------|
| 3.1 | 前置空行 | 表格前**必须**有 1 个空行，否则 Obsidian 不渲染 |
| 3.2 | 列数上限 | 建议 ≤ 5 列，最多 7 列；超过 7 列拆为多个表格或改用列表 |
| 3.3 | 表头分隔 | 用 `|---|` 格式；不用 `:---:` 居中（除非数据列确实需要居中） |
| 3.4 | 单元格管线 | 内容中的 `|` 必须转义为 `\|` |
| 3.5 | 宽列位置 | 内容明显长于其他列时，将其放在最后一列（CSS 默认略灰处理） |
| 3.6 | 空单元格 | 用 `—` 或 `-` 填充，不留纯空（影响对齐可读性） |
| 3.7 | CSS 配套 | vault 已启用 `better-tables.css`（`table-layout: fixed` 均分列宽）；若需浏览器自动列宽，在 frontmatter 加 `cssclasses: [table-auto]` |

### 3.1 列数与布局建议

| 列数 | CSS 默认比例 | 适用场景 |
|------|-------------|---------|
| 2 列 | 30% / 70% | 项 + 说明 |
| 3 列 | 均分 33% | 三维对比 |
| 4 列 | 15% / 30% / 30% / 25% | 字段定义表 |
| 5+ 列 | 首列 12%，其余均分 | 大型矩阵（慎用） |

## 4 列表规范

| # | 规则 | 说明 |
|---|------|------|
| 4.1 | 无序列表 | 统一用 `- `（短横线 + 空格），不用 `* ` 或 `+ ` |
| 4.2 | 有序列表 | 用 `1. ` 起始（Markdown 自动递增），手动编号亦可 |
| 4.3 | 嵌套层级 | 最深 3 层（缩进 2 / 4 / 6 空格），超过 3 层改用标题或表格 |
| 4.4 | 列表前空行 | 列表前**必须**有 1 个空行 |
| 4.5 | 列表内段落 | 同一列表项内需要多段落时，用缩进空行分隔，不要拆成新列表项 |

## 5 Frontmatter 规范

### 5.1 通用必填字段

所有文档必须包含：

```yaml
---
title: "文档标题"
---
```

### 5.2 按文档类型的附加必填字段

| 文档类型 | 附加必填 | 可选 |
|---------|---------|------|
| 飞书采集文档 | `source`, `fetched`, `type: "飞书文档"` | `tags`, `cssclasses` |
| PRD | `version`, `module` | `tags`, `status` |
| 设计方案 | `module`, `step` | `tags` |
| 会议纪要 | `date`, `attendees` | `tags`, `type` |
| 规范文档 | `version`, `created` | `tags`, `aliases` |
| 资料摘要 | `module` | `tags` |

### 5.3 YAML 注意事项

- 含特殊字符的值用双引号包裹：`title: "PRD: 服务模块"` 
- 日期用 ISO 格式：`created: 2026-05-16`
- 布尔值用小写：`draft: true`

## 6 链接与引用

| # | 规则 | 说明 |
|---|------|------|
| 6.1 | 内部链接 | 用 wikilink `[[文件名]]` 或 `[[路径/文件名]]`，不用 Markdown 链接 |
| 6.2 | 外部链接 | 用 Markdown 链接 `[文字](URL)` |
| 6.3 | 图片嵌入 | 用 `![[路径/image.png]]`（Obsidian wikilink），不用 `![alt](url)` |
| 6.4 | 引用标注 | 引用其他规范时标注全名：`→ 详见 [[飞书文档采集规范]] §5` |
| 6.5 | 锚点引用 | 引用同文档章节用 `→ 见本文 §3.2`，不用 HTML 锚点 |

## 7 强调与标记

| 标记 | 用途 | 示例 |
|------|------|------|
| **粗体** | UI 标签、按钮名、字段名 | 点击 **保存** 按钮 |
| *斜体* | 元信息、占位符 | *可选字段* |
| `代码` | 值、编码、路径、命令 | 状态 = `APPROVED` |
| ~~删除线~~ | 已废弃内容 | ~~v1.0 已废弃~~ |

| `==高亮==` | **禁用**——跨平台兼容性差 | — |

## 8 空行与间距

| 元素 | 前空行 | 后空行 | 说明 |
|------|--------|--------|------|
| 标题 | 需要 1 行 | 不需要 | 标题前必空，后紧跟内容 |
| 表格 | 需要 1 行 | 需要 1 行 | 前后各空一行，否则不渲染 |
| 代码块 | 需要 1 行 | 需要 1 行 | 前后各空一行 |
| 列表 | 需要 1 行 | 需要 1 行 | 前后各空一行 |
| 分隔线 `---` | 需要 1 行 | 需要 1 行 | 前后各空一行（否则 `---` 变成标题下划线） |
| Mermaid 图 | 需要 1 行 | 需要 1 行 | 同代码块规则 |
| Callout | 需要 1 行 | 需要 1 行 | 前后各空一行 |

> **记忆口诀**：所有"块级元素"前后都空一行；只有标题后面不空（紧跟内容）。

## 9 图表与可视化规范

> **核心原则**：文档中的架构图、流程图、关系图必须以**人类可视化理解**为目标。
> ASCII 框线画出来的"图"在 Obsidian 里是等宽字符堆砌，不可缩放、不可交互、难以编辑，视觉可读性极差——**禁止使用**。

### 9.1 禁止的图表形式

以下形式**一律不得出现**在 vault 的 `.md` 文件中：

| 禁止形式 | 表现 | 问题 |
|---------|------|------|
| ASCII 框线图 | 用 `┌─┐│└─┘▼▲►◄` 等字符画的架构/关系/层级图 | 不可缩放、跨平台渲染不一致、无法编辑、视觉噪音大 |
| ASCII 流程图 | 用 `→ ← ↓ ↑` 加文字拼的流程 | 对齐依赖等宽字体，行宽变化即崩坏 |
| ASCII 树形图 | 用 `├── └──` 画的目录树或层级关系 | **例外**：目录结构展示可用（见 §9.1.1） |
| 纯文本框图 | 用空格/Tab 手动对齐的多栏布局 | 不同编辑器渲染宽度不同，必然错位 |

#### 9.1.1 ASCII 树形的唯一例外

展示**文件目录结构**时，允许使用 `tree` 风格的 ASCII 树（因为这恰好是它的本职用途，且没有更好的替代）：

```text
10-项目/{项目名}/08-工单管理/
├── README.md
├── 资料摘要.md
├── 设计方案.md
├── PRD.md
└── 流程01-主业务流.drawio
```

**但是**，如果这棵树要表达的是**概念层级**（不是真实文件路径），必须改用 Mermaid 或表格。

### 9.2 替代方案：四种可视化工具

| 工具 | 适用场景 | 嵌入方式 | 详细规则 |
|------|---------|---------|---------|
| **Mermaid handDrawn** | 概念关系图、简单流程（节点 ≤ 6）、状态机、层级图 | ` ```mermaid ` 代码块，内联在 .md 中 | 见 §9.3 |
| **drawio** | 泳道流程（角色 ≥ 2）、跨系统数据流、正式 PRD 交付 | `![[文件名.drawio]]` 嵌入 | 详见 [[流程图绘制规范]] |
| **Agent 手写 SVG** | 全局架构图、方法论总图、需要精确视觉控制的信息图 | `![[文件名.svg]]` 嵌入 | 见 §9.5、详见 [[SVG架构图设计规范]] |
| **Excalidraw** | 评审草图、头脑风暴、自由画布 | `![[文件名.excalidraw]]` 嵌入 | 非正式场景，不做强约束 |

> **Agent 手写 SVG** 是指 Agent 直接输出 SVG XML 代码保存为 `.svg` 文件。vault 中已有 4 个成功实例（V5/V6/V7/V8 架构图），证明 Agent 完全可以生成像素级精确的可视化图表。

**选型决策树**：

```text
需要画图？
 ├─ 是文件目录树？→ ASCII tree（§9.1.1 例外）
 ├─ 节点 ≤ 6 且无泳道？→ Mermaid handDrawn
 ├─ 角色 ≥ 2 或需要泳道？→ drawio
 ├─ 全局架构/方法论总图/精确视觉控制？→ Agent 手写 SVG
 ├─ 非正式草图/讨论？→ Excalidraw
 └─ 不确定？→ 默认 Mermaid，复杂再升级 drawio/SVG
```

### 9.3 Mermaid 内联规范

所有 Mermaid 代码块必须遵守：

| # | 规则 | 说明 |
|---|------|------|
| 9.3.1 | 必须启用手绘风 | 首行写 `%%{init: {'look': 'handDrawn', 'theme': 'neutral'}}%%` |
| 9.3.2 | 节点上限 | 单图 ≤ 6 个主节点；超过 6 个改用 drawio |
| 9.3.3 | 方向选择 | 业务流程用 `LR`（从左到右）；层级/架构用 `TB`（从上到下）；堆叠模型用 `BT`（从下到上） |
| 9.3.4 | 节点文字 | 用 `<b>` 标题 + `<br/>` 换行 + `<i>` 补充说明，保持节点内信息层次 |
| 9.3.5 | 连线标注 | 关键连线加标注文字（`-->\|"标注"\|`），非关键连线不加 |
| 9.3.6 | subgraph | 用于分组，标题简短（≤ 8 字），不嵌套超过 2 层 |
| 9.3.7 | 前后空行 | 代码块前后各空 1 行（同 §8 代码块规则） |

Mermaid 示例：

```mermaid
%%{init: {'look': 'handDrawn', 'theme': 'neutral'}}%%
flowchart LR
    A["<b>Source</b><br/>原始资料"] --> B["<b>Summary</b><br/>结构化摘要"]
    B --> C["<b>Published</b><br/>发布稿"]
```

### 9.4 drawio / Excalidraw 嵌入规范

| # | 规则 | 说明 |
|---|------|------|
| 9.4.1 | 嵌入语法 | 用 Obsidian wikilink 嵌入：`![[文件名.drawio]]` 或 `![[文件名.excalidraw]]` |
| 9.4.2 | 文件位置 | drawio 文件放在对应模块目录下，不放在 vault 根目录 |
| 9.4.3 | 嵌入上下文 | 嵌入前加一行说明文字（图表标题/用途），不要裸嵌入 |
| 9.4.4 | 不重复内容 | 同一张图不要同时用 drawio 嵌入 + 文字重复描述，图说清楚的不再赘述 |

嵌入示例：

```markdown
**工单管理主业务流程**：

![[流程01-主业务流.drawio]]
```

### 9.5 Agent 手写 SVG 规范

Agent 直接生成 SVG XML 文件时必须遵守：

| # | 规则 | 说明 |
|---|------|------|
| 9.5.1 | 响应式画布 | 用 `viewBox` 属性定义画布，不硬编码 `width`/`height`；推荐 `viewBox="0 0 1280 900"` 起步 |
| 9.5.2 | 字体栈 | `-apple-system, 'PingFang SC', 'Microsoft YaHei', sans-serif`（跨平台中文渲染） |
| 9.5.3 | CSS 集中定义 | 所有样式写在 `<defs><style>` 中，不内联 `style=""` 属性 |
| 9.5.4 | 元素分组 | 用 `<g transform="translate(x,y)">` 定位元素组，便于整体移动 |
| 9.5.5 | 中文行高 | 中文文本行高 >= 字号 x 1.6（防止上下行重叠） |
| 9.5.6 | 品牌色对齐 | 涉及品牌的图使用 [[品牌规范]] 色值；Agent 角色色系见 [[SVG架构图设计规范]] |
| 9.5.7 | 箭头定义 | 箭头用 `<marker>` 定义在 `<defs>` 中，`path` 引用 `marker-end` |
| 9.5.8 | 文件位置 | `.svg` 文件与引用它的 `.md` 文件放在同一目录或同一模块目录下 |
| 9.5.9 | 嵌入语法 | 用 `![[文件名.svg]]`（wikilink），不用 `<img>` 或 markdown 图片 |

> **完整规范**见 [[SVG架构图设计规范]]。上表是输出 Markdown 时必须遵守的最小集。
> **图表生成 Skill**：详细操作步骤和模板见 `.skills/generate-diagram/SKILL.md`。

### 9.6 存量 ASCII 图的处理

vault 中已有的 ASCII 框线图，按以下优先级逐步替换：

| 优先级 | 条件 | 处理 |
|--------|------|------|
| P0 | 正式交付文档（PRD/设计方案/规范） | 立即替换为 drawio 或 Mermaid |
| P1 | 方法论/经验文档 | 下次编辑时顺手替换 |
| P2 | 归档文档 / 历史版本 | 不改动，保持原样 |

> **增量执行**：不要求一次性全量替换，但**新产出的文档一律不得使用 ASCII 框线图**。

## 10 命名规范（生成式）

> **核心原则**：文件名是人类和 agent 的第一道导航。看名字就要知道「这是什么类型」「属于哪个模块」「什么时间产出」。

### 10.1 命名决策树

创建新文件时，按以下路径查表：

```text
你要创建什么？
 ├─ 项目模块内的标准产出？→ §10.2 模块标准件命名
 ├─ 任务卡 / 事件记录？→ §10.3 管理类命名
 ├─ 会议纪要 / 调研记录？→ §10.4 时间锚定命名
 ├─ 规范 / 方法论文档？→ §10.5 规范类命名
 ├─ 决策记录？→ §10.6 决策类命名
 └─ 临时文件 / 草稿？→ §10.7 临时文件命名
```

### 10.2 模块标准件命名

模块目录内的文件使用**固定文件名**——不带模块前缀（目录已经是上下文）：

| 文件类型 | 固定文件名 | 说明 |
|----------|-----------|------|
| 模块入口 | `README.md` | 模块概览、成熟度、链接索引 |
| 资料摘要 | `资料摘要.md` | 原始资料的结构化提炼 |
| 设计方案 | `设计方案.md` | 业务设计（阶段2产出） |
| 正式PRD | `PRD.md` 或 `版本号-模块名-端.md` | 如 `5.9-道路救援-PC端.md` |
| 飞书原文 | `飞书原文-{主题}-{端}.md` | 如 `飞书原文-工单管理-PC端.md` |
| 流程图 | `流程{NN}-{名称}.drawio` | 如 `流程01-主业务流.drawio` |
| 知识沉淀 | `{主题}-知识沉淀.md` | 如 `商城订单到店安装-知识沉淀.md` |

> **铁律**：模块内不要在文件名中重复模块名。`08-工单管理/工单管理-资料摘要.md` 是错误的，正确写法是 `08-工单管理/资料摘要.md`。

### 10.3 管理类命名

### 10.4 时间锚定命名

适用于会议纪要、调研记录等以时间为核心锚点的文档：

| 文件类型 | 命名模板 | 示例 |

### 10.5 规范类命名

| 文件类型 | 命名模板 | 示例 |
|----------|---------|------|
| 通用规范 | `{规范主题}.md` | `Markdown文档输出规范.md` |

### 10.6 决策类命名

| 文件类型 | 命名模板 | 示例 |
|----------|---------|------|

### 10.7 临时文件命名

| 场景 | 命名 | 存放位置 |
|------|------|---------|
| 任务临时产物 | 任意，放在 `_temp/{TASK_ID}/` 下 | `_temp/T-20260518-17/` |
| 探索性草稿 | `草稿-{主题}-YYYYMMDD.md` | 项目目录或 `_temp/` |

### 10.8 命名硬规则（校验兜底）

| # | 规则 | 说明 |
|---|------|------|
| 10.8.1 | 中文优先 | 文件名使用中文。英文仅用于：专有名词（`README`; `PRD`）、编码标识（`T-20260518`）、版本号（`v3.2`） |
| 10.8.2 | 禁止空格 | 用短横线 `-` 连接多段，不用空格或下划线。例外：目录名保留已有空格（如 `{项目名} 项目首页.md` 历史遗留） |
| 10.8.3 | 禁止特殊字符 | 不得含 `/ \ : * ? " < > |`（文件系统限制） |
| 10.8.4 | 长度上限 | 文件名（含扩展名）不超过 80 字符 |
| 10.8.5 | 不重复上级目录名 | 文件名中不得包含其父目录名称（目录已是上下文） |

### 11.3 项目模块内部结构模板

每个项目模块目录（如 `10-项目/{项目名}/08-工单管理/`）的标准内部结构：

```text
{NN-模块名}/
├── README.md              ← 必须：模块入口
├── 资料摘要.md            ← 资料整理后产出
├── 设计方案.md            ← 业务设计阶段产出
├── {版本号}-{模块名}-{端}.md  ← 正式 PRD
├── 飞书原文-{主题}-{端}.md    ← 原始采集
├── 流程{NN}-{名称}.drawio     ← 流程图（可多个）
└── {主题}-知识沉淀.md         ← 可选：长期知识
```

> 不是所有文件都要一次产出。模块按成熟度逐步填充（骨架 → 资料摘要 → 设计方案 → PRD）。

### 11.4 放置硬规则（校验兜底）

## 12 目录防爆与拆分规范（生成式）

> 核心原则：文件夹和文件的创建要先按模板生成正确结构，再用校验脚本兜底发现异常。不要等目录爆炸后再靠人工整理。

### 12.1 新建目录决策树

创建任何新目录前，先走这棵树：

```text
你要新建目录？
 ├─ 只是为了放 1-2 个文件？→ 不建目录，放入已有分类
 ├─ 是临时任务产物？→ _temp/{task_id}/，7 天内归位或删除
 ├─ 是项目模块？→ 10-项目/{项目名}/{NN-模块名}/，按 §11.3 模板
 ├─ 是长期增长的方法论/专题库？→ 使用 §12.3 防爆结构
 ├─ 是归档历史版本？→ 60-归档/ 或专题内 90-archive/
 └─ 不确定？→ 先写到 _temp/{task_id}/README.md，完成后再定家
```

### 12.2 目录创建三问

三问至少满足两项，才允许新建长期目录：

| 问题 | 通过标准 |
|------|------|
| 会不会持续增长？ | 预期未来 1 个月内新增 ≥ 5 个文件 |
| 是否有清晰入口？ | 能写出 `00-MOC.md` 或 `README.md` 的目录说明 |
| 是否有明确分层？ | 能把文件分进 core / cases / reviews / archive 等稳定类别 |

如果三问只满足一项，先新建单文件；后续增长到阈值再拆目录。

### 12.3 专题库防爆结构模板

方法论、规范族、实战案例库这类会持续增长的专题，必须按下面模板建目录：

```text
{专题名}/
├── 00-MOC.md            # 唯一入口：当前版本、阅读顺序、文件索引
├── 01-core/             # 当前有效正文 / 主协议 / 主规范
├── 02-cases/            # 实战案例 / retrospective
├── 03-drills/           # 故障演习 / 压测 / 回归测试
├── 04-reviews/          # 评审 / 阶段评估 / 三方合稿
├── 05-spikes/           # 探索性方案 / 下一代实验
├── 90-archive/          # 旧版本 / 已替代文档
└── _drafts/             # 未定稿草稿，定稿后必须迁出
```

生成规则：

| 子目录 | 放什么 | 不放什么 |
|------|------|------|
| `00-MOC.md` | 入口、状态表、阅读路径、最新版本指针 | 长篇正文 |
| `01-core/` | 当前有效规范、协议、主文 | 评审、案例、草稿 |
| `02-cases/` | 已完成任务复盘 | 未来计划、故障演习 |
| `03-drills/` | 故障演习报告、压测结果 | 普通业务 retrospective |
| `04-reviews/` | 评审意见、阶段评估、合稿记录 | 当前有效正文 |
| `05-spikes/` | 未承诺落地的探索 | 已生效规范 |
| `90-archive/` | superseded / archived 文件 | 当前有效文档 |
| `_drafts/` | 临时草稿 | 超过 7 天无人认领的文件 |

### 12.4 文件创建决策树

创建新 `.md` 文件前，先判断是「更新」还是「新建」：

```text
你要写 Markdown？
 ├─ 已有同主题文件？→ 更新原文件，加章节/变更日志
 ├─ 是同一主题的新阶段？→ 更新原文件，用 ## Phase N
 ├─ 是同一主题的新评审？→ 放 04-reviews/，文件名带日期和评审对象
 ├─ 是一次实战复盘？→ 放 02-cases/，按案例编号命名
 ├─ 是故障演习？→ 放 03-drills/，按演习编号命名
 ├─ 是下一代探索？→ 放 05-spikes/，frontmatter 标 `maturity: spike`
 ├─ 是旧版本保留？→ 放 90-archive/，frontmatter 标 `status: archived`
 └─ 只是临时草稿？→ 放 _drafts/ 或 _temp/{task_id}/
```

### 12.5 拆分规范

拆分不是按阶段拆，而是按**阅读目的**拆。

| 拆分类型 | 何时拆 | 拆到哪里 | 必须保留 |
|------|------|------|------|
| 主文过长 | 单文 > 800 行或 > 30KB | `01-core/` 下 sibling doc | 主文保留摘要 + wikilink |
| 案例增长 | retrospective ≥ 5 个 | `02-cases/` | `00-MOC.md` 汇总样本分布 |
| 演习增长 | drill ≥ 3 个 | `03-drills/` | 演习矩阵和结论汇总 |
| 评审增长 | 同一主文 ≥ 3 份评审 | `04-reviews/` | 最新采纳状态表 |
| 探索未定稿 | 不确定是否落地 | `05-spikes/` | frontmatter 写 `maturity: spike` |
| 版本替代 | 新版已生效 | `90-archive/` | 原文件 frontmatter 或 MOC 标明替代者 |

禁止拆分方式：

| 禁止方式 | 正确方式 |
|------|------|
| `Phase1.md` / `Phase2.md` / `Phase3.md` | 同一文件内用 `## Phase 1` |
| `最终版.md` / `最新版.md` / `修改版.md` | 用版本号和变更日志 |
| 根目录平铺 20 个同主题文件 | 建 `00-MOC.md` + 防爆结构 |
| 以 Agent 名称拆文档 | 以阅读目的拆：core / cases / reviews / drills |

### 12.6 防爆阈值

达到以下阈值时，必须治理目录：

| 触发条件 | 动作 |
|------|------|
| 同一目录平铺文件 > 15 个 | 建 `00-MOC.md`，按 §12.3 分层 |
| 根目录出现 > 5 个同前缀文件 | 移入专题目录或子目录 |
| 单文 > 800 行且包含多个阅读目的 | 拆 sibling doc，主文留摘要 |
| `_drafts/` 文件 > 7 天未更新 | 归位、归档或删除 |
| `02-cases/` 每满 5 个案例 | 生成一份阶段汇总，提炼模式而非继续堆案例 |
| `04-reviews/` 出现互相矛盾意见 | 在 `00-MOC.md` 建采纳状态表 |

### 12.7 生成模板

新建专题库时，先生成入口：

```markdown
---
title: "{专题名} MOC"
type: moc
status: active
created: YYYY-MM-DD
updated: YYYY-MM-DD
---

# {专题名} MOC

## 当前有效版本

- 主文：[[01-core/{主文名}]]
- 最新状态：{一句话}

## 阅读顺序

1. 先读 [[01-core/{主文名}]]
2. 再读 [[01-core/{协议或规范}]]
3. 需要证据时读 [[02-cases/]]
4. 需要历史时读 [[04-reviews/]] 或 [[90-archive/]]

## 文件索引

| 分类 | 路径 | 用途 |
|------|------|------|
| core | `01-core/` | 当前有效正文 |
| cases | `02-cases/` | 实战复盘 |
| drills | `03-drills/` | 故障演习 |
| reviews | `04-reviews/` | 评审记录 |
| spikes | `05-spikes/` | 探索方案 |
| archive | `90-archive/` | 旧版本 |
```

### 12.8 校验兜底

校验只做兜底，不替代生成规范。输出后检查：

- [ ] 根目录是否新增了普通文档
- [ ] 新目录是否有 `00-MOC.md` 或 `README.md`
- [ ] 文件是否按阅读目的进入 core / cases / drills / reviews / spikes / archive
- [ ] 是否出现 Phase 拆分文件
- [ ] 是否出现 `最终版` / `最新版` / `修改版`
- [ ] `_drafts/` 和 `_temp/` 是否有生命周期说明
- [ ] 目录文件数是否超过 §12.6 阈值

## 13 质量检查清单

agent 输出文档后逐项自查：

**命名与放置（§10-§11）**：

- [ ] **文件名中文优先**：除 README/PRD/版本号/日期编码外，均用中文
- [ ] **文件名无空格**：多段用短横线 `-` 连接
- [ ] **不重复目录名**：文件名中不含父目录名称
- [ ] **放对目录**：按 §11.1 决策树归位，未堆在 vault 根或错误层级
- [ ] **模块内用固定名**：README/资料摘要/设计方案 等用标准文件名（§10.2）

**排版格式（§2-§8）**：

- [ ] **标题层级**：H1 仅出现一次（文档标题），正文从 H2 开始
- [ ] **标题编号**：>= 30 个标题的文档已添加层级编号（烘焙到文本）
- [ ] **表格渲染**：表格前有空行，列数 <= 7
- [ ] **列表格式**：无序用 `- `，嵌套 <= 3 层
- [ ] **Frontmatter**：`title` 字段存在，按文档类型含必填字段
- [ ] **图片语法**：本地图片用 `![[]]`，无外部 URL 图片残留

**图表（§9）**：

- [ ] **无 ASCII 框线图**：不含 `┌─┐│└─┘▼▲` 等字符拼的架构图/流程图/关系图（目录树例外）
- [ ] **图表用对工具**：Mermaid（<= 6 节点，带 handDrawn）/ drawio（泳道/复杂流程）/ SVG（全局架构/精确控制）/ Excalidraw（草图）
- [ ] **SVG 响应式**：手写 SVG 用 `viewBox` 不硬编码 width/height，字体用规范字体栈
- [ ] **Mermaid 手绘风**：所有 Mermaid 代码块首行含 `%%{init: {'look': 'handDrawn', 'theme': 'neutral'}}%%`

**粒度（§1）**：

- [ ] **文件粒度**：同主题未按阶段拆分为多个文件；新建文件有充分理由（超过 15KB/600 行，或用户明确要求）
- [ ] **大纲可读**：Obsidian 右侧大纲面板显示完整且层级清晰

**目录防爆（§12）**：

- [ ] **不平铺爆炸**：同主题文件未继续堆在一个根目录下
- [ ] **有入口文件**：长期增长目录含 `00-MOC.md` 或 `README.md`
- [ ] **按阅读目的拆分**：core / cases / drills / reviews / spikes / archive 分层清楚
- [ ] **草稿有生命周期**：`_drafts/` / `_temp/` 文件能在 7 天内归位或清理
