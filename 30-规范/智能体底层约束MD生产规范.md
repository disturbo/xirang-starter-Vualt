# 智能体底层约束 MD 生产规范

> 目的：统一“智能体入职时的底层约束 MD”怎么写、怎么生成、怎么验证。
> 
> 优先级：**V9 > 本规范 > Agent 个体差异 > 平台实现细节**。
> 
> 任何必须遵守的规则，**必须写在正文里**；链接只能做来源、注释和溯源，不能单独承担约束力。

---

## 0. 一句话总则

1. **V9 永远第一**：凡是运行时约束、写入声明、pre-flight、收工规则，优先服从 V9。
2. **正文才算数**：对 Agent 真正生效的约束，必须进入可直接加载的正文；不能只“指向某个链接”。
3. **源与镜像分离**：可编辑源文件是真源，Vault 中的展示/快照是只读镜像，不可反向当作规范源。

---

## 1. 适用范围

本规范适用于以下类型的“底层约束 MD”：

- `.prompt-src/prompt-base.md`
- `.prompt-src/v9-compliance-block.md`
- `.prompt-src/preflight-auto-template.md`
- `.prompt-src/agents/*.delta.md`
- `.claude/CLAUDE.md`
- `.claude/agents/*.md`
- `.codex/instructions.md`
- `~/.hermes/SOUL.md`
- `~/.openclaw/workspace/AGENTS.md`
- 其他承载 Agent 约束、路由、边界、可写范围的根文件

不适用于：

- 普通任务日志
- 单次执行记录
- 纯展示页
- 仅用于阅读的历史归档

---

## 2. 分层模型

| 层级 | 职责 | 可以写什么 | 不能写什么 |
|---|---|---|---|
| 基座层 | 提供全员共享的稳定规则 | 通用产出原则、路径边界、路由原则 | 个体专属职责 |
| 合规层 | 提供 V9 运行时契约 | 写入声明、pre-flight、收工规则 | 角色定位、业务职责 |
| 平台层 | 处理平台差异 | 平台命令、平台路径、启动方式 | 覆盖 V9 的硬约束 |
| 个体层 | 定义单个 Agent 的差异 | 角色、核心职能、不做、可写路径、触发器 | 把共性规则重复堆进每个文件 |
| 镜像层 | 供人阅读和对比 | 只读快照、索引、展示 | 反向成为运行时真源 |

**关键约束：**

- 共性规则尽量收口到基座层或合规层。
- 个体层只保留差异，避免每个文件都变成“长篇说明书”。
- 镜像层只能展示，不负责执行。

## 3. 文件类型与职责

### 3.1 共享基座文件

| 文件 | 作用 | 变更要求 |
|---|---|---|
| `.prompt-src/prompt-base.md` | 全局基类 | 修改后必须重新生成所有目标文件 |
| `.prompt-src/v9-compliance-block.md` | V9 合规块单一真源 | 任何合规变化先改这里 |
| `.prompt-src/preflight-auto-template.md` | 自动平台 pre-flight 模板 | 只放平台变量和通用流程 |

### 3.2 Agent 个体文件

| 文件类型 | 作用 | 推荐内容 |
|---|---|---|
| `.prompt-src/agents/*.delta.md` | 单个 Agent 的差异层 | 角色、职能、不做、路径、平台特性 |
| `.claude/agents/*.md` / `.codex/instructions.md` / `~/.hermes/SOUL.md` / `~/.openclaw/workspace/AGENTS.md` | 运行时根文件 | 直接可加载的最终约束正文 |

### 3.3 镜像与展示文件

| 文件类型 | 作用 | 约束 |
|---|---|---|
| `30-规范/智能体约束/*.md` | 只读快照 / 展示镜像 | 只能反映真实源，不得手改成“假源” |
| `02-项目管理/智能体状态/*.md` | 状态与运行痕迹 | 不能替代底层约束源 |

## 4. 必填元数据

### 4.1 Agent 个体源文件最小字段

每个 Agent 个体源文件，建议至少包含以下字段：

| 字段 | 必填 | 说明 |
|---|---:|---|
| `agent_id` | 是 | 稳定机器 ID，建议小写、无空格 |
| `agent_name` | 是 | 面向人阅读的名称 |
| `platform` | 是 | 运行平台或承载环境 |
| `role` | 是 | 一句话角色定位 |
| `cooldown` | 是 | 冷却 / 频率 / 按需触发方式 |
| `budget_level` | 是 | S / M / L / XL 或等价级别 |
| `weekly_budget_cny` | 建议 | 如果有成本上限，直接写明 |
| `status` | 是 | `draft / active / retired / deprecated` |
| `version` | 是 | 语义化版本或快照版本 |
| `created` | 是 | 创建日期 |
| `updated` | 是 | 最近更新日期 |

### 4.2 镜像文件最小字段

镜像/快照文件应额外声明：

- `source`
- `snapshot_date`
- `platform`
- `agent_id`

### 4.3 字段约束

- `agent_id` 必须稳定，不可随意更名。
- `status` 必须能表达“在用 / 草案 / 退役 / 历史镜像”。
- `source` 必须指向可追溯的源文件路径。
- 任何“历史原因、继承关系、替代关系”都建议显式写出：`inherits`、`supersedes`。

## 5. 正文骨架

### 5.1 运行时根文件必须遵守的顺序

1. frontmatter
2. V9 合规块
3. 一句话定位
4. 核心品格 / 工作风格
5. 项目上下文 / 业务边界
6. 硬约束
7. 能力边界 / 不做什么
8. 可写路径 / 授权范围
9. 触发器 / 调用方式
10. 约束记录 / 变更历史
11. 演进规则 / 版本说明

### 5.2 规范写法要求

- V9 合规块必须出现在任何角色说明之前。
- 如果平台有自动生成头，也只能作为“生成标识”，不能抢在 V9 之前塞入角色逻辑。
- 规则先写“必须做什么 / 不允许做什么”，再写解释和背景。
- 同一主题不要在多处重复展开成互相打架的版本。

### 5.3 推荐的个体层章节标题

- `## 一、身份声明`
- `## 二、核心品格`
- `## 三、项目上下文`
- `## 四、硬约束`
- `## 五、能力边界`
- `## 六、工作风格`
- `## 七、触发器`
- `## 八、约束记录`
- `## 九、演进规则`

如果文件偏“配置化”而非“叙事化”，也至少要保留这几个信息块：

- 身份 / 角色
- 核心职责
- 不做
- 可写路径
- 平台特性
- 来源与继承

## 6. 链接与引用规则

### 6.1 允许用链接做什么

- 说明来源
- 跳转到背景文档
- 指向历史版本
- 提供阅读路径

### 6.2 不允许用链接做什么

- 不能只放链接，自己不写约束
- 不能让“外链可读”替代“正文可执行”
- 不能把必须遵守的规则只放在某个展示页里

### 6.3 正确写法

如果某条规则必须被 Agent 遵守，应该同时满足：

1. 在正文里直接写出最小可执行规则
2. 在“来源/延伸阅读”里附上链接
3. 在镜像层保留说明，但不把镜像当成真源

### 6.4 失链容错

如果外部链接失效，文件仍应能独立说明：

- 这个 Agent 是谁
- 它能做什么
- 它不能做什么
- 它可以写哪里
- 它受什么约束

## 7. 生成链

### 7.1 标准生成链

```
.prompt-src/prompt-base.md
    + .prompt-src/v9-compliance-block.md
    + .prompt-src/preflight-auto-template.md
    + .prompt-src/agents/{agent_id}.delta.md
    ↓
最终运行时根文件（.claude / .codex / ~/.hermes / ~/.openclaw）
    ↓
30-规范/智能体约束/ 下的只读快照
```

### 7.2 生成原则

- 源文件先改，生成文件后出。
- 生成文件禁止手改。
- 只读快照只做展示，不回写源逻辑。
- 源 delta 允许携带 frontmatter 元数据；生成器在组装运行时正文时必须剥离这些元数据，只保留可执行正文。
- 如果平台必须保留本地命令或路径，优先放在平台层，不要塞进个体层的“背景废话”。

### 7.3 配置型平台的特别要求

像 `reasonix.toml` 这类非 Markdown 配置文件：

- 可以保留为运行时配置
- 但凡其内容影响 Agent 约束，必须有一份 Markdown 源说明
- Markdown 源说明是人读真源，配置文件是运行时落地

## 9. 验证标准

### 9.1 文档级验收

一个合格的底层约束 MD，至少应满足：

- frontmatter 完整
- V9 在正文最前
- 硬约束写在正文，不靠单独链接撑着
- 角色职责和不做边界清晰
- 可写路径可检查、可执行
- 源 / 镜像 / 展示层分离明确

### 9.2 生成级验收

对生成链的验收，至少包括：

- 源文件与生成结果能互相追溯
- 生成文件无手改漂移
- 只读快照与最终运行时文件一致
- 平台差异不覆盖 V9 语义

### 9.3 推荐测试

建议在修改后执行：

```bash
python3 .prompt-src/prompt-build.py --verify
```

如本次变更涉及本规范本身，再补做：

- 检查 `30-规范/README.md` 是否已收录
- 检查 `50-经验/Agent协作方法论/息壤V9-运行时契约卡.md` 是否已引用
- 检查 `30-规范/智能体约束/README.md` 的镜像说明是否仍准确

## 10. 变更与发布流程

### 10.1 推荐顺序

1. 先改源文件
2. 再生成运行时根文件
3. 再做验证测试
4. 测试通过后，再更新索引、镜像和 V9 引用

### 10.2 发布原则

- 若只是个体角色/路径变化，优先改个体层，不动 V9。
- 若改变了运行时握手、写入声明、pre-flight 语义，则必须回写 V9。
- 若新增/重命名 Agent，先建立源文件与镜像链，再补索引。

### 10.3 退役与继承

- 退役文件必须明确标注 `retired` 或 `deprecated`
- 新文件若继承旧文件，必须写清 `inherits`
- 若新文件取代旧文件，必须写清 `supersedes`

---

## 11. 实操判断清单

写文件前先问自己 5 个问题：

1. 这条规则是不是 V9 级别？
2. 这条规则是不是必须在正文里出现？
3. 它属于源层、运行时层，还是镜像层？
4. 这个链接失效后，文件还能不能独立工作？
5. 现在改的是源，还是只是展示页？

如果有任一答案不清楚，先停下来补齐，不要把“想法”误写成“规范”。

---

## 12. 结论

**底层约束 MD 的核心，不是“长”，而是“可直接执行、可生成、可验证”。**

只要记住三条就够了：

1. **V9 先行**
2. **正文承载硬约束**
3. **链接只做溯源，不做替身**
