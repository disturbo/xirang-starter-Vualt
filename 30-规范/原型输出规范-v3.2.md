## 一、规范来源与适用范围

### 1.1 规范来源

本规范基于以下输入整合：
- UI 设计团队 2026-05 新版设计规范（4 张核心页面截图）
- 现有规范 v1.6 有效设计令牌保留
- uniapp+vue3 技术栈组件化实现约束

### 1.2 适用范围

| 示例项目 EXAMPLE 全部 HTML 原型输出 | 设计稿（Figma/Sketch 源文件）|

| 手机端 H5 原型（uniapp 适配） | 测试用例、部署文档 |

### 1.3 技术栈约束

**交付团队技术栈：uniapp + vue3**

规范需符合以下技术约束：
- 组件化结构（与 uniapp 组件映射）
- 响应式适配（PC + 移动端共用原型）
- CSS 变量命名与 uniapp 变量命名一致

### 1.4 端型定义与区分（强制）

示例项目 EXAMPLE 原型必须明确标注**端型**，两端的布局、组件、交互有本质差异，**不可混用**。

| 维度 | PC 端（管理后台） | 助手端（手机 H5） |
|---|---|---|
| **用户** | 总部/门店管理人员 | 门店顾问/技师 |
| **设备** | 电脑 1366px+ | 手机 375px ~ 428px |
| **布局** | 侧边栏导航 + 多页签 + 内容区 | 底部 Tab 导航 + 单页/上下滑动 |
| **导航** | 左侧树形菜单，支持折叠 | 底部 3~5 个 Tab 图标 |
| **列表** | 表格（多列、排序、分页） | 卡片列表（单卡片多行信息） |
| **筛选** | 顶部多行筛选区（4列布局） | 顶部搜索栏 + 筛选下拉（点击展开） |
| **详情** | 分区块折叠（caret 标题） | 纵向展开，区块用卡片分隔 |
| **表单** | 多列网格（4列） | 单列纵向排列 |
| **操作** | hover 显示操作按钮 | 滑动/长按/点击展开操作 |
| **弹窗** | 居中模态框（600px/900px） | 底部上滑抽屉（全宽） |
| **字体基数** | 14px | 16px（最小可触控） |
| **按钮高度** | 32px | 44px（手指触控） |
| **输入框高度** | 32px | 44px |
| **页签** | 顶部页签栏（多开） | 底部 Tab（固定 3~5 个） |

### 1.5 原型工作包与迭代闭环（v3.2.8 新增）

> 本节借鉴 `product-design-system` 的“需求产物包 + 变更日志 + 复盘回写”方法，但只吸收其产物治理思路，不吸收其 MagicBox 视觉令牌和“纯单文件、无共享组件”技术路线。示例项目 EXAMPLE 仍以 `tokens.css`、`sidebar.js`、`topbar.js` 等共享组件为单一来源。

#### 1.5.1 原型输出不只是一批 HTML

每次新增、重构或大幅调整一个原型任务时，必须同步确认以下四类内容：

| 内容 | 落点 | 要求 |
|---|---|---|
| 页面清单 | 模块 README、设计方案、PRD 或任务交付说明 | 列明页面名称、端型、HTML 路径、入口关系；多页面流程必须说明从哪个页面进入哪个页面 |
| HTML 原型 | `prototype/v3.2/{pc\|h5}/pages/{module}/{page}.html` | 同名文件始终代表当前最终态，不在文件名里追加“最新版”“最终版”等过程词 |
| 导航与跳转 | `components/sidebar.js`、页面内 `href`、按钮 `onclick` | 全局可见页面接入共享导航；流程内页面至少从列表、详情或入口页可达 |
| 变更摘要 | Git commit、任务 Handoff、模块 README 或设计方案变更记录 | 一句话说明本轮变化；按截图还原时必须写明“按截图还原”；不写 CSS 类名等实现细节 |

> 不强制每个原型目录创建独立 `CHANGELOG.md`。原型仓库的日常历史以 Git commit 为准；跨页面、跨模块或影响规范的变化，再同步到模块 README、设计方案或本规范变更记录。

#### 1.5.2 最终态原则

- HTML 页面只保留当前方案，不在页面里堆叠已废弃的旧布局。
- 被替代方案通过 Git 历史、任务 Handoff 或设计方案变更记录追溯，不在当前原型中保留“旧版区域”。
- 同一业务页面不允许并存 `{page}.html`、`{page}-new.html`、`{page}-final.html`、`{page}-final2.html`。确需并行探索时，必须放入实验目录或在任务结束前收敛。
- 用户确认“按截图还原”后，视觉差异以截图为准；若与本规范数值冲突，先记录差异点，再决定是否升为规范 patch。

#### 1.5.3 模板优先原则

新建页面前不得从空白 HTML 直接开始，按以下优先级复用：

1. 同模块已完成页面；
2. 其他模块同类型页面（列表、详情、创建、审批、看板、配置）；
3. 本规范中的页面骨架与组件规范；
4. 助手端页面优先参考 [[示例项目项目-助手端UI输出规范]]；
5. 确无可复用对象时，才允许新建最小骨架。

复用时只继承成熟结构和交互模式，不继承已被指出的问题；所有颜色、间距、圆角、阴影必须回到当前 token。

#### 1.5.4 提交前闭环自检

交付原型前，至少完成以下检查：

- 文件头已声明规范版本、技术栈、端型。
- 生成或修改原型 HTML/CSS/JS 前，已读取本规范相关章节；PC 列表页至少核对 §4.2，PC 新增/编辑/详情页至少核对 §4.3。
- 页面清单已标明每个页面的类型：列表、创建、新增、编辑、详情、审批、看板、报表、配置等；同一 HTML 复用多模式时，必须标明默认模式和可切换模式。
- PC 端页面正确接入 `tokens.css`、`sidebar.css`、`sidebar.js`、`topbar.js`（如适用）。
- H5 页面未套用 PC 端表格、侧边栏、多页签结构。
- 列表 ID、查看、新增、返回等关键跳转可点击。
- 列表页已核对：筛选项标题内置、主操作在列表区右侧、普通列表不主动增加统计/KPI/概览卡片。
- 列表页已核对：字段、状态、行操作均可在详情页或节点页找到对应展示与动作；本期不做的业务不出现在列表列、状态或操作中。
- 列表页已核对：申请/审批状态口径唯一，不把同一流程的多个节点结果拆成多个筛选项或多列表状态。
- 新增页已核对：空白或默认待填状态可演示输入、添加、校验、删除、取消、保存/提交等关键交互。
- 详情页已核对：默认只读展示，不在主体信息区混入可编辑输入控件；需要登记、审批、取消等动作时，使用明确的操作入口、弹窗、抽屉或独立操作区。
- 流程型申请/审批页已核对：顶部步骤条完整展示已通过、当前、后续节点；节点点击仅用于原型演示状态切换；处理记录为节点结果的主要反馈，不额外堆叠重复提示条。
- 附件区已核对：使用公共附件样式，附件是独立文件列表或上传区，不用普通备注输入框伪装附件。
- PRD 侧栏已核对：完整需求模块展示 PRD 正文；流程图按 draw.io 泳道图规范展示，不用静态业务卡片冒充流程图。
- 弹窗、抽屉、筛选、分页、展开收起等核心交互可演示。
- 页面清单中的每个 HTML 路径真实存在，且入口关系能被用户走通。
- 如本轮来自截图、录屏或用户手绘，交付说明中注明来源和还原范围。

#### PC 列表页主操作与统计卡片边界（v3.2.19 新增 · 强制）

PC 普通业务列表页默认结构为：页面标题说明 → 筛选区 → 列表区。页面标题区只承载标题、面包屑和必要说明；新增、导出、批量处理、查看明细等主操作必须放在列表区标题栏或列表操作栏右侧。

不得在筛选区上方主动增加 KPI/统计/概览卡片。只有满足以下任一条件时才允许增加统计卡片：

- 用户明确要求展示统计卡片；
- PRD 已定义对应指标和口径；
- 页面本质是看板、报表或统计分析页。

角色/视角切换不属于主操作，不得混放在列表主操作区；仅 PRD 明确要求时，才以筛选条件、页签或独立数据视角区呈现。不要为了让页面“看起来完整”把普通工作列表做成半个看板。

#### PC 列表字段、状态与操作闭环（v3.2.22 新增 · 强制）

PC 普通业务列表页是进入详情、创建、编辑、审批等流程的入口，不是独立的信息孤岛。列表字段、状态、按钮必须与详情页和当前业务阶段互相校验。

**字段闭环**：
- 列表中展示的业务字段，必须能在详情页、当前节点页或只读信息区找到对应字段；若列表需要展示某个资源、周期、客户、单据或状态，详情页必须同步补齐。
- 详情页存在但列表不需要扫视的字段可以不放入列表；列表不得出现详情页完全没有承接的字段。
- 字段必须支撑当前业务正常开展，优先覆盖单号、关联业务单、申请门店、申请人、客户车辆、服务原因、服务周期、服务资源、当前节点、状态、申请/更新时间等真实流转字段。
- 本期不实现的子业务，不在列表列、状态 pill、行操作中占位。例如本期只做申请、编辑、审核流程时，不提前放积分发放、结算确认、提醒确认等后续业务。

**操作闭环**：
- 行内操作必须来源于详情页可执行动作，如查看、编辑、审核、撤回、调整天数、提前结束等；详情页没有入口或当前阶段不可执行的动作，不放在列表操作列。
- 导出是列表或模块级全局操作，放在列表标题栏/操作栏右侧；不得作为单条记录操作。
- 主按钮文案应使用真实业务动作，如“申请”“新建申请”；点击后必须进入当前模块的创建/流程入口。若创建、编辑、详情复用同一 HTML，必须用 `mode`、`state`、`id` 等参数区分，不得跳到过时的孤立表单页。

**数据口径与页签**：
- 由登录账号、所属门店、总部/门店角色决定的数据范围，不做成筛选项或可切换页签；页面可以在说明文案或 PRD 中解释数据口径。
- 只有用户确实需要主动切换业务视角，且 PRD 明确该视角可切换时，才展示视角筛选或页签。
- 状态页签只在 PRD 定义了任务池或状态分组时使用；普通列表不为了显得“完整”增加状态 tab。

**状态口径唯一化**：
- 申请/审批类列表优先使用一个业务总状态或当前节点口径，如草稿、审批中、退回修改、已通过、已驳回；不要同时放“服务审批”“天数审批”“申请状态”等多套状态筛选。
- 多个审批节点的通过、退回、驳回结果应在详情步骤条、审核结果、审批意见记录或处理记录中展示；只有当某个审批结果是独立业务对象且用户需要单独检索时，才允许成为列表筛选项。
- 列表状态列应服务扫视和处理入口判断，不承担完整流程审计；完整节点历史放在详情页处理记录中。

#### PC 筛选项标题内置（v3.2.9 新增 · 强制）

PC 端列表页、报表页的筛选项必须使用“字段标题内置在控件边框内”的单行样式：字段名位于控件左侧，输入值、占位符、下拉值紧随其后，二者位于同一行、同一边框内。不得把筛选项标题作为独立文本悬浮在输入框上方或放在输入框外侧，也不得做成上下两行的浮动标签。

- 筛选项标题与输入值必须共用同一个边框、同一条基线，不得出现“标题一行、输入框另起一行”的视觉结构。

- 输入框占位符只写值提示，如 `请输入`；下拉首项只写业务值，如 `全部` 或 `请选择`，不得写成 `业务类型 全部`、`状态 请选择`。

- 控件聚焦态使用统一边框高亮，默认参考 `var(--func-blue)`；不得用加粗标题、红框或标题位移表达焦点。
- 查询、重置、导出、展开更多等操作按钮不属于筛选项，不套用内置标题结构。
- 日期范围、可搜索下拉、普通输入框、选择框应保持同一高度和内边距。
- PC 列表/报表筛选控件密度以技术支持列表页为基准：控件高 32px、字号 13px、左右 padding 10px；40px/44px 高度仅允许用于 H5 触控或特殊弹窗触控场景，不得带入 PC 列表筛选区。

#### 列表页**三类跳转行为**（v3.2.7 新增 · 强制）

| 触发元素 | 行为 | markup |
|---|---|---|
| ID 列链接 | 跳详情页（带 ID 参数） | `<a class="link-id" href="{detail}.html?id={ID}">{ID}</a>` |
| 操作列「查看」 | 跳详情页 | `<a class="row-link" href="{detail}.html?id={ID}">查看</a>` |
| 主按钮「+ 新增」 | 跳创建页 | `<button class="btn btn-primary" onclick="location.href='{create}.html'">+ 新增</button>` |

约定：
- `{detail}` = 同模块内的 `*-detail.html`；`{create}` = 同模块内的 `*-form.html` 或 `*-create.html`
- ID 参数用 `?id={X}` 不用 `#`，方便后续接真后端
- 创建页跳转**不带参数**（创建页是空白表单）
- 操作列若有"编辑/审核"等多种动作，每个 `.row-link` 都应带 `href`，不允许 `<span>` 占位（除非真的不可点击，用 `.row-link-muted`）

#### PC 新增 / 编辑 / 详情页类型门禁（v3.2.21 新增 · 强制）

PC 端业务页面必须先声明页面类型，再生成结构。列表页进入「查看」或点击 ID 时进入详情态；点击「新增」时进入创建态；点击「编辑」时进入编辑态。三类页面可以复用同一个 HTML，但默认模式、标题、主操作、字段可编辑状态和交互脚本必须显式区分。

**详情页（detail）**：

- 默认用于静态展示已存在单据、业务对象或执行结果。
- 主体信息区使用纯文本、状态 tag、时间线、只读表格、附件预览等展示组件。
- 主体信息区不得出现可编辑 `input`、`select`、`textarea`、上传控件、可勾选 checkbox 或可直接修改的表格单元格。
- 如果详情页需要执行登记、审批、取消、作废、延长、重发等动作，必须通过明确的按钮、弹窗、抽屉或独立操作区承载；不得把可编辑表单混在详情信息区里。
- 详情页允许出现筛选控件的唯一场景：页面本质包含二级明细列表，且筛选区服务于该明细列表，不服务于主体详情字段编辑。

**新增页 / 创建页（create）**：

- 从列表「新增」进入，不带业务对象 ID，默认呈现空白或系统默认待填状态，不用填满的静态样例冒充新增。
- 必须展示动态交互剧本：输入/键入、添加明细或附件、删除明细或附件、必填校验、格式校验、取消/返回确认、保存草稿、提交反馈。
- 必填项、错误提示、禁用态、loading 或提交成功态至少覆盖本页面的核心链路。
- 如页面包含明细表、附件、联系人、执行节点等可变集合，必须提供添加和删除演示，不得只放固定静态行。

**编辑页（edit）**：

- 从列表「编辑」或详情页「编辑」进入，带业务对象 ID，展示已有数据的可修改状态。
- 必须与详情页在标题、按钮、字段状态上显式区分；不能用可编辑表单直接作为详情页。
- 必须提供保存、取消、变更校验和必要的删除/撤销/重置交互；业务不允许修改的字段应展示为只读。

**复用同一 HTML 时**：

- 必须在 DOM 或脚本中声明 `create` / `edit` / `detail` 等模式，且默认模式与入口一致。
- 不同模式的主按钮、底部栏、字段可编辑状态、校验逻辑和空/已有数据状态必须互斥。
- 禁止用一个填满数据的表单同时冒充新增、编辑和详情。

#### PC 流程型申请 / 审批详情页（v3.2.22 新增 · 强制）

适用于申请、审核、登记、调整、结束、结算等有节点流转的 PC 业务页面。此类页面不是普通静态详情页，必须先让开发和测试看懂“当前在哪个节点、前后节点是什么、当前节点能做什么”。

**顶部步骤条**：
- 页面顶部必须展示完整业务步骤，不只展示当前节点。已通过、当前、后续节点都要列出来。
- 每个步骤至少展示节点名称、节点说明、操作人、操作时间、联系方式；后续节点的时间可写“待审批”“通过后生成”等业务口径。
- 节点用圆点表达。已通过节点可用勾选图标；当前节点使用品牌红填充并可加浅色外环；未到达节点使用浅灰描边。
- 节点之间的连线必须表达进度：已通过节点之间用较深中性灰，未到达节点之前用浅灰；不要整条线使用纯品牌红，也不要让线消失。
- 步骤节点本身不套卡片线框；节点下方信息按列排布，避免每个节点再放一组重复的摘要框。

**原型演示交互边界**：
- 为了让开发和测试理解不同状态，原型允许点击步骤节点切换到对应演示状态。
- 必须在功能说明或 PRD 侧栏中写明：节点点击只用于原型演示，不代表真实系统允许跳过审批或随意切换状态。
- 点击节点后，页面标题、当前节点、字段可编辑状态、按钮、处理记录必须同步变化，不能只切换步骤条颜色。

**节点页面状态**：
- 提交/创建节点：字段可编辑，展示保存草稿、提交、取消等操作；可以演示关联业务单搜索、附件添加/删除、必填校验。
- 审批节点：申请字段只读，审批意见通过弹窗、抽屉或独立审批区记录；按钮只展示当前节点可执行动作，如审批通过、退回修改。
- 编辑态：从详情进入，明确展示“编辑申请”标题和保存/取消按钮；保存后回到详情只读态。
- 详情态：只读展示业务事实、审核结果、执行结果和处理记录，不混入可直接修改的表单控件。

**处理记录**：
- 除提交申请节点外，流程进入后续节点时应常驻展示处理记录，帮助开发和测试理解已发生动作。
- 处理记录使用纵向时间线：节点圆点位于时间列左侧，连线垂直贯穿记录；时间列和内容列对齐，内容区展示动作标题和简短说明。
- 处理记录视觉使用中性灰为主，当前或关键节点可用品牌红点缀；不要使用整条纯红粗线。
- 处理记录是节点操作结果的主要反馈。节点下方不要再叠加“已提交成功”“已推进到下一节点”等重复绿色提示条，也不要再放“当前状态 / 下一节点 / 页面模式”这类摘要框。

**附件与可变集合**：
- 附件区必须使用公共附件组件样式，包括附件标题、非必填/必填说明、文件名、大小、上传时间、预览/删除等操作。
- 附件是独立文件列表或上传区，不用普通输入框、备注 textarea 或只读字段伪装附件。
- 申请页如允许上传附件，必须演示添加和删除；详情页展示附件预览或下载入口；非必填附件需明确标注。

**字段与业务完整性**：
- 流程型详情页字段应能支撑业务闭环。申请类页面至少核对：关联业务单、申请门店、申请人、服务原因、服务周期、资源/服务方式、资源状态、VIN/车牌、客户姓名/电话、备注/说明、附件、审批意见、处理记录。
- 申请门店、申请人等由登录账号带出的字段，应展示默认值和来源口径，不作为普通筛选项或手工输入项处理。
- 当前阶段不做的后续业务，不提前在详情页堆无动作区块；确需说明边界时，写入 PRD 或功能说明。

### 4.6.5 看板 KPI 词典（保险看板）

> **来源**：保险看板 5.1 评审 · 在 §4.6.4 公式弹层基础上落地的一组**强制口径**，所有保险看板原型都必须用相同 `data-expr` / `data-note` 文案。

| 指标 | `data-expr` | `data-note`（口径备注） |
|---|---|---|
| 新保渗透率 | 新车新保单数 ÷ 新车交付台次 × 100% | 当期签单的新车保单去重台次 / 当期新车交付台次 |
| **保单回传率**（v3.2.1 新增） | 已回传保单数 ÷ 应回传保单数 × 100% | 保司系统 T-1 已回传 / EXAMPLE 当期签单台次 |
| 驾乘险渗透率 | 投保驾乘险台次 ÷ 新保签单台次 × 100% | 仅统计当期新保中包含驾乘险险种的台次 |
| 新车单均保费 | 新车保费合计 ÷ 新保签单台次 | 保费含交强险 + 商业险，剔除驾乘险与附加险 |
| 续保率 | 实际续保台次 ÷ 应续保台次 × 100% | 应续保 = 上一保单到期前后 60 天窗口内的台次 |
| 修保比 | 事故车产值 ÷ 保险保费产值 | 比值越高代表事故车业务对保险业务的杠杆越大 |
| 事故车产值 | 维修类型 = 保险 的工单结算金额合计 | 含工时 + 备件 + 附加费，剔除外协部分 |
| 配件折扣率 | 实际备件结算金额 ÷ 备件原价合计 × 100% | 仅统计保险事故车工单中的备件 |
| **油漆面工时单价**（v3.2.1 新增） | （维修类型=保险 ∧ 维修项目=喷漆）结算金额合计 ÷（维修类型=保险 ∧ 维修项目=喷漆）油漆面数 | 单位 元/面；用于对比不同门店保险喷漆作业的单价水平 |
| 签单台次（合计） | 新保签单台次 + 续保签单台次 | 去重至 VIN-保单期 维度 |

**强制规则**：
- ✅ 上表是**唯一可信源**，PRD / 后端字段命名变化时**必须同步更新本节**
- ✅ 任何新增的看板 KPI，在落地原型前必须先把 `expr + note` 写入本表
- ✅ 当 KPI 数量超过 8 个时，使用 5 列栅格（5×2 或 5×3），不要勉强塞进 4 列
- ❌ 不要在不同原型里出现同一指标的不同口径（违反就是 BUG）

### 4.14 PRD 需求详情侧栏（v3.2.10 新增 · PC 强制）

PC 端原型必须支持“原型界面 + PRD 原文”并排查看，用于评审时同步核对页面与定稿需求。该能力由共享组件 `components/prd-sidecar.js` 提供，页面不得手写重复侧栏。

#### 4.14.1 布局规则

```html
<div class="layout">
  <aside class="sidebar">...</aside>
  <div class="main">...</div>
  <aside class="dms-prd-panel">...</aside>
</div>
```

- PRD 区域必须是 `.layout` 的直接子元素，与 `.sidebar`、`.main` 并列，不允许放进 `.main` 内容区。
- PRD 区域使用白底直铺，不再额外套灰底或卡片背景。
- PRD 区域默认宽度 420px，允许用户拖拽左边界调整，宽度范围 280px ~ 720px。
- 当 PRD 隐藏时，`.main` 自动占满剩余空间；再次显示时恢复上一次宽度。

#### 4.14.2 按钮联动

- 顶栏用户姓名右侧必须出现 `需求详情` 按钮。
- 点击按钮切换 PRD 区域显示 / 隐藏，并同步按钮 active 状态与 `aria-expanded`。
- 按钮状态保存到 `sessionStorage`，刷新当前浏览器会话时保持用户选择。
- 725 报表专题可使用专题 PRD 原文；625 页面按模块展示同一份模块 PRD 原文。

#### 4.14.3 PRD 内容来源

| 来源 | 规则 |
|---|---|
| Vault 定稿 PRD | 优先展示 `~/Desktop/obsidianVault/10-项目/基线/{模块}/PRD.md` Markdown 原文 |
| 页面级覆盖 | 同一模块存在独立页面功能 PRD 时，可按文件名覆盖模块级原文 |
| 无 PRD | 显示“当前模块尚未配置 Vault PRD 映射”，不得伪造需求 |

PRD 区域必须按 §4.14.3.2 的三类视图口径展示内容，不得在业务页面内手写第二套 PRD 侧栏。若启用 `归档PRD` 视图，该视图必须展示 Vault Markdown 原文全文，并渲染成正常阅读态 HTML；不得直接展示 `.md` 源码格式或 YAML frontmatter，不允许把归档 PRD 改写成摘要、提炼要点或二次生成内容。头部可额外展示标题、版本状态、来源路径和模块/页面级映射说明。

#### 4.14.3.1 完整模块 PRD 与流程图展示（v3.2.22 新增 · 强制）

当原型对应完整新增模块时，PRD 侧栏默认只展示“功能说明”。功能说明用于定位页面区块，并承载背景目标、业务流程、角色权限、字段口径、交互规则、异常场景和验收规则等页面评审必需信息；不得再默认常驻 `归档PRD` Tab。

**PRD 展示**：
- 新增模块默认展示 `功能说明`：功能说明必须覆盖背景与目标、业务流程、用户故事/角色权限、字段说明、交互说明、异常场景、验收关注点等内容，并在各 section 中配置明确 `prdRef`。
- 迭代页面默认展示 `本期调整 + 功能说明`：本期调整只写本轮差异，功能说明写页面稳定结构与定位说明。
- `归档PRD` 仅在改动既有页面、需要对照历史/基线 PRD 原文时启用；不得作为迭代页面和新增模块的默认常驻 Tab。
- PRD 侧栏中展示的内容必须能追溯到 Vault PRD 或页面级 PRD 配置，不用口头摘要冒充正式 PRD。

**流程图展示**：
- PRD 中的业务流程图必须遵循示例项目 PRD draw.io 流程图规范：输出 `.drawio` 源文件，按角色/系统分泳道，节点使用中文业务动作短语，连线使用正交线。
- 判断出口必须标注条件，如“通过”“退回”“不通过”；退回/返回线使用红色虚线。
- 流程图节点表达“动作/活动”，状态机节点表达“状态”，二者不能混用。
- 原型侧栏可以展示 draw.io 预览图、导出的 SVG/PNG 或可缩放画布，但不得用一组静态业务卡片、普通看板列或伪泳道来冒充流程图。
- 流程图过宽时按“主流程 + 子流程”或“阶段 A + 阶段 B”拆分，不通过缩得看不清来塞进侧栏。

#### 4.14.3.2 PRD 展示区三类视图口径（v3.2.24 新增 · 强制）

`本期调整`、`功能说明`、`归档PRD` 是三种不同评审视图，不是所有页面都必须同时展示。

| Tab | 使用场景 | 默认适用页面 | 内容约束 |
|---|---|---|---|
| 本期调整 | 展示本轮相对既有模块、既有页面或既有 PRD 的差异点 | 迭代页面、补丁页面、改造页面 | 只写本期新增、删除、变更、禁用、字段调整、交互变化和验收关注点；不得重复完整功能说明，不得塞历史 PRD 原文 |
| 功能说明 | 展示当前页面的稳定功能结构、区块定位、字段、交互、异常和验收口径 | 所有接入 PRD 展示区的页面；新增模块只展示此 Tab | 必须与页面 `data-prd-target`、功能说明 section、`prdRef` 保持一致；字段级规则进表格，不在原型画布堆说明文本 |
| 归档PRD | 改动既有页面时，对照历史/基线 Vault PRD 原文 | 仅在明确需要历史/基线对照的改动页面启用 | 展示 Vault Markdown 原文全文和来源路径；不得二次摘要；不得替代本期调整和功能说明 |

**页面类型默认 Tab：**

| 页面类型 | 默认 Tab |
|---|---|
| 迭代页面 | `本期调整` + `功能说明` |
| 新增模块 / 新增页面 | `功能说明` |
| 既有页面改动且需对照原始口径 | `本期调整` + `功能说明` + `归档PRD` |
| 仅有归档资料、尚未配置功能说明 | 可临时展示 `归档PRD`，但不得作为交付终态 |

**配置规则：**

- `currentAdjustments` 存在时，视为迭代页面，默认展示 `本期调整 + 功能说明`。
- `featureOnly: true` 或无 `currentAdjustments` 时，默认只展示 `功能说明`。
- 只有显式配置 `showArchive: true` 时，才展示 `归档PRD` Tab。
- `归档PRD` 打开后只用于对照历史/基线 PRD；本轮评审意见必须沉淀到 `本期调整` 或 `功能说明` 中。

#### 4.14.4 原型区 / PRD 展示区边界隔离（v3.2.12 新增 · 强制）

PC 端打开“需求详情”时，页面被划分为两个独立业务域：

| 区域 | DOM 所属 | 内容边界 | 样式边界 |
|---|---|---|---|
| 原型区 | `.main` | 只承载业务原型、页面交互、模拟数据 | 业务按钮、底部栏、弹窗、浮层、遮罩仅在 `.main` 内生效 |
| PRD 展示区 | `.dms-prd-panel` | 只承载 Vault PRD 原文和 PRD 阅读控件 | 使用 PRD 阅读样式，不继承业务表单、底栏、弹窗、操作按钮样式 |

**强制实现规则：**

- `.main` 与 `.dms-prd-panel` 是同级区域，二者的 DOM、滚动容器、z-index 层级必须分离。
- 原型区的 `position: fixed` 元素必须约束到 `.main` 可视宽度内；优先使用 `.main` 内部 `position: sticky` 或绝对定位，避免直接按 viewport `right: 0` 铺满整屏。
- 底部固定对象（如 `.form-footer`、`.bottom-tabbar`、`.sticky-footer`、`.action-bar-fixed`、费用统计栏、保存/打印按钮组）不得覆盖 PRD 展示区。PRD 打开时，其右边界必须停在 `.main` 右边界。
- 原型区弹窗、抽屉、浮层、popover、遮罩默认只覆盖 `.main`。除非明确是“全局系统弹窗”，不得遮住 `.dms-prd-panel`。
- PRD 展示区内不得出现原型业务按钮、费用统计、保存/打印、底部页签、业务浮动工具条；原型区内也不得嵌入 PRD 正文、PRD 表格或 PRD 阅读控件。
- PRD 展示区宽度变化或隐藏/恢复时，原型区固定元素必须重新计算边界，不能保留旧宽度导致跨区覆盖。

**推荐 CSS 约束：**

```css
.layout {
  display: flex;
  min-height: 100vh;
}

.main {
  position: relative;
  min-width: 0;
  overflow: hidden;
}

.main-scroll {
  height: calc(100vh - 56px);
  overflow: auto;
}

.form-footer,
.bottom-tabbar,
.action-bar-fixed {
  position: sticky;
  left: 0;
  right: 0;
  bottom: 0;
  z-index: 20;
}

.dms-prd-panel {
  position: relative;
  z-index: 30;
  flex: 0 0 var(--prd-panel-width, 420px);
}
```

**提交前必须截图自检：**

- 打开 PRD 展示区后，底部保存栏、费用统计栏、底部页签不能越过 `.main` 右边界。
- 拖拽 PRD 展示区宽度到最小 280px 和最大 720px 后，原型区固定元素仍不能覆盖 PRD。
- 触发原型区弹窗/下拉/更多菜单后，浮层不能遮挡 PRD 正文。
- 隐藏 PRD 后，原型区恢复占满剩余空间；再次打开 PRD 后，不出现旧宽度残留。

#### 4.14.5 公共区域 Shell 化与需求定位浮标（v3.2.15 新增，v3.2.16 补充 · 强制）

PC 端可吸收助手端桌面评审 Shell 的经验：公共区域稳定存在，业务页面只负责内容区，减少跳转闪烁和重复组件漂移。

**公共区域规则：**

- `topbar.js`、`sidebar.js`、`prd-sidecar.js` 视为页面 Shell 公共能力；业务页面不得复制第二套顶栏、侧栏或 PRD 面板。
- 标准 Shell 固定为四块：`菜单栏`、`顶部栏`、`原型展示区`、`PRD 展示区`。后续 PC / 助手端迭代默认在该框架上推进，只替换原型展示区和 PRD 映射内容。
- 页面切换优先保持顶部栏、左侧菜单和右侧 PRD 展示区不重载，只替换 `.main` 内容区；若当前静态文件路由仍会整页跳转，也必须复用同一公共组件，并通过 URL 参数或本地状态恢复菜单展开、PRD 宽度和搜索状态。
- PC 左侧菜单只负责模块树、展开收起和激活态；顶部搜索负责快速定位页面。模块页面较多时，不在业务页内放临时跳转按钮，也不在 PC 侧栏另放搜索框。
- 助手端桌面评审 Shell 可以保留左侧“模块 / 页面搜索”，因为助手端页面树包含三级状态和弹窗；该能力不迁移到 PC 侧栏。
- PRD 展示区与 `.main` 同级，不进入业务页面 DOM；PRD 展示区隐藏、显示、拖拽宽度时，`.main` 内固定元素和定位浮标必须重新计算边界。
- PRD 展示区必须作为一个整体参与布局：标题区、正文区、背景和滚动容器同属一个高层级面板；缩放或拖拽时不得出现“标题压在原型上、背景留在底层”的分裂状态。

**需求定位浮标规则：**

- 需求定位浮标使用编号标记，编号必须与 PRD 功能说明小节一致。
- 浮标应放在 `.main` 内的定位层，使用业务区块坐标计算位置；不得使用 viewport 固定坐标，避免滚动、缩放或 PRD 拖拽后漂移。
- 定位层默认 `pointer-events: none`，浮标自身可点击；打开需求定位后，表格、页面、抽屉仍应能滚动。
- 浮标层级高于业务内容，低于 modal、drawer、popover、loading mask。
- 单页定位点建议不超过 12 个；字段级规则放在 PRD 功能说明表格里，不在原型上堆满浮标。

#### 4.14.5.1 助手端评审角色场景导航（v3.2.25 新增 · 强制）

助手端桌面评审 Shell 中，账号角色属于“原型评审场景”，不是手机业务页面内可由用户自行切换的生产功能。凡需要对比不同账号角色下的数据范围、字段或按钮，统一按以下规则实现：

- 左侧菜单的模块为一级、业务页面为二级、该页面的评审账号角色为三级；角色项必须挂在对应业务页面下，不得与真实业务页面并列。
- 点击三级角色项后，通过明确的场景参数（如 `?role=manager`）刷新原型展示区；激活态必须按页面路径与场景参数精确匹配，避免多个角色同时高亮。
- 手机业务页面可以静态展示“当前账号角色”和“当前数据范围”，但不得提供角色切换按钮、Action Sheet、弹窗、下拉选择器或隐藏手势。
- 生产系统账号角色必须由四统一登录态、组织与数据权限、实际处理人及单据事实共同确定，不得把评审场景参数实现为生产环境越权入口。
- 状态变更、业务路径选择等真实业务交互仍放在手机页面内；仅供评审的状态或路径模拟器必须显式标注“原型评审”，不得伪装为生产按钮。
- 三级角色菜单、页面搜索与激活态使用同一菜单数据源；搜索结果必须能够直接定位到具体角色场景。
- 页面脱离桌面 Shell 单独打开时，允许采用一个明确的默认角色兜底，但仍不得在手机页面内补回角色切换控件。

```text
客诉工单（一级）
└─ 客诉单管理（二级）
   ├─ 用户关爱经理（三级评审角色）
   ├─ 关爱经理（兼当前处理人）（三级评审角色）
   ├─ 当前处理人（三级评审角色）
   ├─ 建单人本人（三级评审角色）
   └─ 其他数据权限角色（三级评审角色）
```

#### 4.14.6 PRD 联动标注接入规则（v3.2.17 新增 · 强制）

本节合并质检模块全量推行后的正式口径（PC 5 页 + H5 3 页已全部接入，2026-06-21 验证通过）。后续 PC 页面接入 PRD 联动标注时，以本节为主规范；试点文档仅作为评审记录和样板说明。

**统一 ID：**

- 页面 DOM、功能说明配置和 PRD 卡片使用同一个语义 `id`。
- DOM 写法：`data-prd-target="quality.check.order-info"`。
- 配置写法：`{ id: "quality.check.order-info", title: "车辆与工单信息" }`。
- hash 由工具自动派生，规则为 `.` 转 `-`，例如 `quality.check.order-info` -> `#quality-check-order-info`。
- 新页面统一使用 `{module}.{page}.{area}` 或 `{module}.{page}.{area}.{action}`。
- 存量短命名可兼容；试点后新增页面继续使用短命名视为 lint 错误，v4.0 前完成存量迁移。

**PRD 溯源：**

- 每个功能说明 section 必须配置 `prdRef`，格式为 `{PRD文件名}#{章节编号}`，例如 `31-服务工单管理-PRD.md#5.3.2`。
- 不允许写“见PRD”“参考工单模块文档”等模糊引用。
- 若功能说明包含归档 PRD 尚未明确承诺的内容，必须标记 `pendingPrdConfirm: true`。
- 模块验收前必须清零 `pendingPrdConfirm`，或登记为 PRD 待补事项。

**纯逻辑规则：**

```js
{
  id: "quality.check.submit-rule",
  target: null,
  title: "提交前校验规则",
  prdRef: "09-车间质检与超时预警-PRD.md#5.4"
}
```

- PRD 有规则但页面没有独立 UI 区块时，配置 `target: null`。
- PRD 面板显示“无页面锚点”，回到原型按钮置灰。
- 不生成页面浮标，不为凑锚点新增无业务意义 DOM。

**动态节点代表标注：**

- 重复表格、检查项、图片证据、明细列表等区域只标代表节点，不逐条打点。
- 支持 `data-prd-delegate="container|first|active"`。
- `container` 采集容器自身；`first` 取第一个满足 `offsetParent !== null` 的可见业务子节点；`active` 取当前激活、展开或选中的业务子节点。
- 全部不可见时不渲染浮标；`data-prd-delegate` 拼写错误视为 lint 错误。

**iframe 与嵌入态：**

- PC Shell 主路径为同源 iframe DOM 直读；`postMessage` 仅作为兼容方案，不作为本期主链路。
- 所有 PC 原型样板页面必须走同一 origin 部署；不可访问 `iframe.contentDocument` 时，Shell 输出 `[EXAMPLE] iframe 非同源，需求定位功能不可用`，降级为仅展示 PRD 面板，不渲染浮标。
- Shell 在 iframe load 后注入 `iframe.contentWindow.__EXAMPLE_EMBEDDED__ = true`；页面自身也应通过 `window.parent !== window` 或 `window.__EXAMPLE_EMBEDDED__` 判断嵌入态，避免双 sidebar、双 PRD 面板。

**重采与性能：**

- 滚动、窗口 resize、PRD 面板折叠/展开、PRD 面板拖拽、弹窗/抽屉显示隐藏后，浮标坐标必须重算。
- 坐标重算使用 `requestAnimationFrame` 节流；高频 DOM 变化使用 debounce，避免每次 mutation 立即全量计算。
- 目标预算：单页 10 个定位点内，重算耗时控制在 16ms 内。

**lint 建议：**

- `id`、`data-prd-target`、功能说明 section 是否一致。
- `prdRef` 是否存在且格式合法，建议正则：`^[^#]+\.md#\d+(\.\d+)*$`。
- `pendingPrdConfirm` 是否遗留。
- `target: null` 是否没有误生成浮标。
- `data-prd-delegate` 是否属于 `container | first | active`。

#### 4.14.8 模块 PRD 标注接入验收标准（v3.2.18 新增 · 强制）

本节定义模块级 PRD 联动标注的接入流程和硬门槛。质检模块（PC 5 页 + H5 3 页）为首个全量达标样本，2026-06-21 通过全部校验。

**标准流程（四步）：**

```text
Step 1: 基础设施 lint
  → node scripts/prd-lint.js --module {module} --infra
  → 验证 pageMap 覆盖、moduleMap 映射、resolvePageKey 可达
  → FAIL 时先补齐基础设施，不进入 Step 2

Step 2: 补 DATA + DOM 锚点
  → prd-annotations.js 补齐 bindings + sections（含 prdRef）
  → HTML 页面补齐 data-prd-target 锚点
  → 纯逻辑规则配置 target: null，不伪造 DOM

Step 3: 全量 lint
  → node scripts/prd-lint.js --module {module}
  → 必须 PASS（退出码 0），否则不进入 Step 4

Step 4: Smoke + 人工验收
  → node scripts/prd-smoke.js --module {module}
  → 必须 PASS
  → 人工确认：Shell 打开/独立打开/带参打开/页面切换，
    浮标位置、PRD 定位、目标闪烁、console 无报错
```

**硬门槛（任一不满足 = 接入未完成）：**

| 门槛 | 检查方式 | 容忍度 |
|---|---|:---:|
| `prd-lint.js --module xxx` 全量 PASS | 自动化 | 0 FAIL |
| `prd-smoke.js --module xxx` PASS | 自动化 | 0 FAIL |
| binding ↔ DOM 双向校验 | prd-lint Check 3 + 4 | 0 FAIL |
| `pendingPrdConfirm` 残留 | prd-lint Check 6 | 0 条 |
| prdRef 格式合法且非空 | prd-lint Check 5 | 0 FAIL |
| pageMap 覆盖所有含锚点页面 | prd-lint Check 1 | 0 FAIL |

**六项 lint 检查说明：**

| # | 检查项 | 规则 |
|:---:|---|---|
| 1 | pageMap 覆盖率 | 含 `data-prd-target` 的 HTML 文件必须在 `prd-docs.generated.js` pageMap 中有条目 |
| 2 | DATA key 匹配 | pageMap 条目必须在 `prd-annotations.js` DATA.pc 或 DATA.h5 中有配置 |
| 3 | binding → DOM | 配置中每个 binding（非 `target:null`）必须在 HTML 中有对应 `data-prd-target` |
| 4 | DOM → binding | HTML 中每个 `data-prd-target` 必须在配置 bindings 中有对应条目 |
| 5 | prdRef 格式 | 每个 section 必须有 `prdRef`，格式正则：`^[^#]+\.md#\d+(\.\d+)*$` |
| 6 | pendingPrdConfirm | 不允许存在未清理的 `pendingPrdConfirm: true` |

**lint 脚本位置：**

```text
prototype/v3.2/scripts/prd-lint.js      — 数据层静态校验（已就绪）
prototype/v3.2/scripts/prd-smoke.js     — 浏览器 Smoke 验证（Codex 负责）
```

**用法：**

```bash
# 单模块校验
node scripts/prd-lint.js --module quality

# 全量校验（所有已接入模块）
node scripts/prd-lint.js

# 详细输出
node scripts/prd-lint.js --module quality --verbose
```

**浏览器 Smoke 验证矩阵（每模块必须覆盖）：**

| 场景 | 检查点 |
|---|---|
| Shell 打开（`pc/index.html?page=...`） | 浮标渲染、PRD 定位、回跳闪烁 |
| 独立打开（直接访问页面 URL） | prd-sidecar 面板显示正确 |
| 带业务参数（`?phase=final&id=xxx`） | 浮标子集正确、参数未丢失 |
| 带 hash（`#section-anchor`） | PRD 面板定位到对应卡片 |
| 页面切换（从上一页导航到目标页） | 无残留状态、iframe URL 正确 |
| 底部 Tab 切换（H5） | PRD drawer 重新加载、无串页 |
| console | 无 JS 报错 |

**Smoke 验证同时检查的七维度：**

1. 地址栏 URL（Shell `?page=` 参数）
2. iframe 实际 src
3. 页面标题/关键按钮文案
4. PRD 面板标题和卡片列表

### 5.1.4 容器扁平化（v3.2.6 新增 · 强制）

> **来源**：用户对照"营销服务平台"截图明确要求"主区域的白色卡片底部应该是没有边框和底部阴影"。

#### 原则

主区所有"白卡片"作为信息容器，**只用底色对比表达分组**（白卡片 vs `#F5F7FA` shell 底），**禁止**使用：

- ❌ 外部 `border`
- ❌ 外部 `box-shadow`

仅保留**容器内部**的视觉分隔（这些是结构线，不是装饰线）：
- ✅ `.panel-header { border-bottom: 1px solid var(--border-light) }` —— 区分卡片头与正文
- ✅ 表格 `thead` 下的 `border-bottom` —— 区分表头与数据
- ✅ 表格行间的 `td { border-bottom }` —— 行分隔
- ✅ 配置区块内嵌输入框的边框 —— 表单元素本身的边框

#### 受控类名清单

```
.filter-section   .table-wrapper   .panel
.kpi-card         .config-section  .form-body
.detail-section   .dashboard-card  .chart-card
.table-dense
```

以上类名命中的元素必须 `border: none; box-shadow: none;`。`sidebar.css` 已用 `body X` 高优先级规则统一覆盖各页内联 CSS，新页不必再写。

#### 反例

```css
/* ❌ v3.2.5 及之前的常见做法（v3.2.6 起作废） */
.panel       { border:1px solid var(--border-light); box-shadow:var(--shadow-sm); }
.kpi-card    { border:1px solid var(--border-light); box-shadow:var(--shadow-sm); }
.table-wrapper { border:1px solid var(--border-light); box-shadow:var(--shadow-sm); }

/* ✅ v3.2.6 现行 */
.panel, .kpi-card, .table-wrapper { background: var(--bg-card); /* 仅靠白底色与 #F5F7FA shell 对比 */ }
```

#### 三栏无界一体（同步强制）

```css
.sidebar       { border-right:  none; }   /* v3.2.6：去 */
.topbar        { border-bottom: none; }   /* v3.2.6：去 */
.sidebar-brand { border-bottom: none; }   /* v3.2.6：去 */
.sidebar-brand { height: 56px; }          /* v3.2.6：与 topbar 等高 */
.topbar        { height: 56px; }          /* v3.2.5 起 */
```

视觉效果：侧栏顶部品牌区与主区顶栏在视觉上拼接成**一条 56px 高、`#F5F7FA` 满底的水平横条**，没有任何分隔线。
