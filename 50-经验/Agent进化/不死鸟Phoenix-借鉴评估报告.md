# 不死鸟 Phoenix — 示例项目 EXAMPLE 借鉴评估报告

## 一、文档消化概要

不死鸟 Phoenix 是 Lucasmantou 开源的一个 AI Agent 完整架构设计，基于 Hermes 框架构建。核心思想是「浴火不灭，迭代永生」——让系统在运行中自我进化，而非依赖人工维护。

### 11 大板块速览

| 板块 | 核心思想 | 与我们当前做法的对应 |
|------|---------|-------------------|
| Core 配置中心 | 全局配置+状态+任务调度 | config.yaml + SOUL.md |
| Router 路由引擎 | 五档路由，双维度分类 | delegate_task 子任务分发 |
| Executor 执行管道 | 8阶段：拆解→审批→压缩→信用检查→调用→压缩→缓存→并行 | 脚本执行流程 |
| Memory 记忆系统 | 四层：短期/事实/长期/结构化 | MEMORY + session_search + Vault |
| Self-heal 自愈 | 抗体库+进化引擎 | 每次模块交付后沉淀经验教训 |
| Integration 集成 | 多平台网关 | 飞书→Vault 同步 |
| Security 安全 | P0/P1/P2 三级权限 | 品牌合规一票否决 |
| Adapt 自动适配 | 版本差异检测+自动修复 | OpenClaw 同步机制 |
| Sandbox 沙箱 | Docker 隔离 | 临时 Python 脚本 |

| GitHub 集成 | Issue/PR 全流程 | 项目管理 |

## 二、可直接借鉴（6项）

### 借鉴方案 1：自动融合引擎 → 规范版本升级自动化

**不死鸟做法**：Auto-Fusion Engine 在 Hermes 新版本发布后，自动扫描→对比→决策(P0/P1/P2)→融合→验证→报告。

**示例项目 EXAMPLE 映射**：每次 yijing-prd-spec 或品牌规范升级时，我们目前是手动评估影响范围、手动更新所有已产出 PRD。借鉴后：

```
规范升级（如 v3.2.1 → v3.3.0）
    ↓
① 扫描：遍历所有已产出模块，识别版本引用
② 对比：逐模块对比新旧规范差异
③ 决策：P0（结构变更，必须升级）/ P1（内容增强，建议升级）/ P2（格式调整，可选升级）
④ 融合：对 P0 模块自动应用变更，P1 标记建议，P2 记录跳过
⑤ 验证：抽查3-5个模块确认升级正确
⑥ 报告：生成升级报告，列出已升级/待升级/跳过的模块清单
```

**落地优先级**：P0。我们刚手动完成了 30 个模块的飞书源文件拆分和规范 v3.3.0 升级，这正是这个引擎的价值所在。

**实现方式**：创建一个 `规范升级检查` skill，包含模块扫描、差异识别、自动 patch 和报告生成。

---

### 借鉴方案 2：抗体库 → PRD 质量校验自动化

**不死鸟做法**：8个内置抗体，匹配「错误模式 → 修复方案」，越用越聪明。

**示例项目 EXAMPLE 映射**：我们的 PRD 产出有大量硬约束——品牌字眼（仅示例项目/X9）、品牌色（#861B2F）、18位定长编码、列表按钮≤4个。目前靠人工检查。借鉴后：

```
PRD 产出完成
    ↓
抗体库自动扫描
    ├─ 抗体1：品牌字眼扫描 → 检测"协作助手奕派""协作助手纳米"等违规词 → 自动修复或标记
    ├─ 抗体2：品牌色检查 → 检测 #E60012 等非示例项目色 → 自动替换或标记
    ├─ 抗体3：编码格式 → 检测非18位编码 → 标记
    ├─ 抗体4：按钮数量 → 检测超过4个操作按钮的行 → 标记
    ├─ 抗体5：字段表完整性 → 检测缺少「字段名/类型/必填/校验规则」的行 → 标记
    └─ 抗体6：章节完整性 → 检测6章骨架是否齐全 → 标记缺失章节
```

**落地优先级**：P0。品牌合规类的抗体最紧迫——你已经三次纠正我的品牌字眼错误，这个抗体直接消灭此类错误。

**实现方式**：品牌约束已经写入 SOUL.md 硬约束区，可进一步创建 `prd-antibody-scan` skill，在输出 HTML 原型和 Markdown PRD 后自动运行。

### 借鉴方案 3：Feature Registry → 模块能力注册表

**不死鸟做法**：`feature_registry.json` 记录 78 个能力的融合状态、版本、优先级、依赖。

**示例项目 EXAMPLE 映射**：30 个示例项目 EXAMPLE 模块目前没有一个统一的「状态注册表」。每个模块的 PRD 版本、原型版本、差异点清单进度、飞书源状态都是分散的。借鉴后：

```json
{
  "modules": [
    {
      "id": "01-PDI管理",
      "prd_version": "v2.0",
      "prototype_version": "v1.0",
      "feishu_source": "已拆分",
      "difference_list": "已完成",
      "status": "已交付",
      "dependencies": [],
      "last_updated": "2026-04-25"
    },
    {
      "id": "03-保险管理",
      "prd_version": "未启动",
      "prototype_version": "未启动",
      "feishu_source": "已拆分",
      "difference_list": "未启动",
      "status": "待推进",
      "dependencies": ["01-PDI管理"],
      "last_updated": "2026-05-16"
    }
  ]
}
```

**落地优先级**：P1。当前靠 `dms-three-carrier-sync` skill + Vault 目录结构勉强够用，但随着模块增多，需要一个单一事实来源。

**实现方式**：在 Vault `10-项目/示例项目EXAMPLE/` 下创建 `module-registry.json`。

**维护机制**：
- **责任方**：Hermes 主动维护（每次产出 PRD/原型/差异点清单后自动更新对应模块条目）
- **触发时机**：PRD 版本变更、原型版本变更、差异点清单状态变更、模块交付状态变更时
- **兜底校验**：`dms-three-carrier-sync` skill 每次同步时交叉比对注册表与实际文件状态，发现不一致时提醒修正
- **首次初始化**：Phase 2 启动时，由 Hermes 扫描全部 30 个模块目录，反向生成初始注册表

### 借鉴方案 4：Skill Reviewer → 模板版本管理

**不死鸟做法**：技能评分（基础50+质量40+使用20=110），Jaccard 查重，30天未使用+评分<30 自动清理。

**示例项目 EXAMPLE 映射**：我们的 PRD 模板、原型模板、skill 文件也会堆积。借鉴后：

- 对 `yijing-prd-spec` 的每个模板文件进行评分（使用频率、产出质量）
- 检测重复模板（如旧版品牌规范模板 vs 新版）
- 30天未引用且评分低的模板自动标记为可归档

**落地优先级**：P2。当前模板数量少，暂时不需自动化。日后模板增多再启用。

---

### 借鉴方案 5：故障处理卡 → 常见问题预案

**不死鸟做法**：4类故障（网络/API/资源/逻辑）× 标准处理流程。

**示例项目 EXAMPLE 映射**：我们在协作中遇到的常见问题应该有预案：

| 故障类型 | 症状 | 预案 |
|---------|------|------|
| 双写不一致 | Hermes 产出但 OpenClaw 未同步 | 触发 `dms-three-carrier-sync` 全量比对 |
| 品牌字眼污染 | PRD 中出现"协作助手奕派" | 运行品牌抗体扫描，自动修复 |
| Vault 图片污染 | PPT/Word 导入产生 rId*.png | 运行 `obsidian-vault-cleanup` |
| 模块目录缺失 | 新模块找不到目录 | 检查 `module-registry.json` + 自动创建 |
| 规范版本漂移 | PRD 引用旧版规范 | 触发借鉴方案1的自动融合 |
| 端口配置错误 | Hermes/OpenClaw 服务无响应（launch.sh 7898↔7897 混淆、PWA 8648↔9119 混淆） | 检查 `~/.hermes/launch.sh` 代理端口 + `.openclaw/config.yaml` 端口配置，对照标准值表验证 |

**落地优先级**：P1。目前靠记忆和经验处理，标准化后可减少遗漏。

### 借鉴方案 6：渐进式/延迟加载 → Skill 按需加载

**不死鸟做法**：ProgressiveLoader（缓存+频率优先级）+ DeferredToolLoader（注册不加载）。

**示例项目 EXAMPLE 映射**：每次对话开始时，Hermes 加载全部 available skills。大部分 skill 实际上用不到。借鉴后：

- 常用 skill（yijing-prd-spec、dms-three-carrier-sync）预加载
- 低频 skill（obsidian-vault-cleanup、enterprise-system-field-collection）延迟加载，仅在触发词匹配时才加载
- 统计每个 skill 的使用频率，动态调整加载优先级

**落地优先级**：P2。目前的 skill 数量不影响启动速度，未来 skill 超过 30 个时启用。

## 三、待讨论（2项）

### 讨论 1：记忆系统四层架构是否引入

**不死鸟做法**：短期（会话）+ 事实（偏好）+ 长期（SQLite）+ 结构化（用户画像）。

**示例项目 EXAMPLE 现状**：我们有 MEMORY（对应事实）+ session_search（对应长期）+ Vault（对应结构化）+ 对话上下文（对应短期）。功能上已覆盖四层，但未显式分层管理。

**讨论点**：是否需要显式引入四层架构？好处是更清晰的管理边界，成本是引入 SQLite 和 JSON 结构维护的额外负担。建议暂时不引入——当前 Hermes 原生 MEMORY + session_search + Vault 三层已经足够。等后续记忆膨胀到需要结构化查询时再考虑。

---

### 讨论 2：熔断器是否适用于多智能体协作

**不死鸟做法**：连续3次失败 → 熔断60秒 → 半开试探 → 恢复/继续熔断。

**示例项目 EXAMPLE 映射**：当 OpenClaw 或 Codex 连续调用失败时，是否应该自动熔断并切换到备用方案？

**讨论点**：我们的协作模式中，如果一个 Agent 反复失败，通常是配置问题而非瞬时故障——需要人工介入而非自动恢复。建议暂时不引入熔断器，改为「连续失败告警」机制——3次失败后主动通知用户决策。

## 四、不适用（3项）

| 不适用项 | 原因 |
|---------|------|
| 五档路由/模型矩阵 | 示例项目 EXAMPLE 不是 AI 推理系统，不需要按任务复杂度自动选择模型。我们只有一个模型（你指定的），路由决策由你手动控制。 |
| 信用监控/欠费切换 | 示例项目 EXAMPLE 不直接调用第三方付费 API，不涉及余额监控和自动切换 Provider。 |
| Docker 沙箱隔离 | 我们的脚本在本地执行，风险可控（品牌合规是内容风险，非系统风险）。不需要 Docker。 |
