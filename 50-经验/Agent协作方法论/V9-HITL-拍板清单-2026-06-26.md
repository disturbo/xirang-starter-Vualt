# V9 HITL 拍板清单

> 定位：把 V9 已经在实践中的人类拍板点写成明文护栏。它不增加普通任务摩擦；只有触及系统边界、分发边界、账号边界、验收边界时才要求人工确认。

## 核心原则

| 原则 | 含义 |
|---|---|
| 绿灯无感 | 普通 M0-M3、无写入问答、无异常巡检不增加流程 |
| 红灯硬拦 | 触及高风险边界时，未获人工确认不得声称完成 |
| submitted 不等于 accepted | Agent 可提交，验收必须由 reviewer 或负责人确认 |
| 自演进不自放权 | Agent 可提出规则修改，不得自行把约束改松 |

## 必须人工拍板的动作

| 场景 | 例子 | 未拍板时允许做什么 | 未拍板时禁止做什么 |
|---|---|---|---|
| 改 V9 核心规则 | 修改 gate、hook、handshake、状态机、反射器冷却策略 | 写提案、做只读分析、建临时验证 | 直接合入并宣布生效 |
| 改 starter 分发边界 | 新增可分发文件、删除模板、调整敏感词允许范围 | 本地草稿、扫描报告 | 推送公开仓库 |
| 接入账号/秘钥/真实计费 | 飞书 webhook、LLM billing API、GitHub token | 设计接口、写无秘钥 mock | 写入真实 secret 或上线自动拉账单 |
| 部署常驻进程 | launchd、cron、后台 watcher、自动写文件任务 | 给部署模板、人工执行说明 | 未确认就安装/加载 |
| 删除/归档大量文件 | 批量删除项目资料、归档整目录、迁移正式路径 | 列影响清单、生成 dry-run | 直接执行破坏性操作 |
| `submitted -> accepted` | 任务验收、方案通过、外部仓库发布认可 | 标记 submitted/reviewing | Agent 自己标 accepted/done |
| 放宽权限或 scope | 修改自身 write_scope、扩大白名单、跳过门禁 | 说明阻塞原因并请求授权 | 手改自己的约束后继续执行 |
| 跨 Vault / 外部仓库写入 | starter、GitHub Pages、其它本地仓库 | 读状态、列 diff、准备补丁 | 未确认就推送或改默认分支 |

## 建议人工拍板的动作

| 场景 | 触发条件 | 建议处理 |
|---|---|---|
| P0/P1 active 巡检项 | `health-latest.json` 出现 active p0/p1 | 先报告，再登记看板或开任务 |
| 规则冲突 | 同一领域两个 primary 或现行规范冲突 | 指派 owner 决定真源 |
| 成本异常 | 预算熔断、token 激增、真实计费异常 | 人确认是否继续 |
| 高噪声告警 | 新巡检源上线后 active 激增 | 人确认阈值与冷却策略 |

## 验收身份规则

| 字段 | 说明 |
|---|---|
| `owner` / `author` | 当前执行者或产物作者 |
| `reviewer` | 被指定的验收方 |
| `accepted_by` | 实际确认 accepted 的人或 Agent |

硬规则：

1. `accepted_by` 必须存在，且不得等于 `owner` / `author`。
2. `reviewer` 未明确时，默认验收方为人工Reviewer。
3. Agent 可把任务推进到 `submitted`，但不能自行推进到 `accepted`。
4. `accepted` 后才能把对外分发、正式规则、任务完成口径写成“已验收”。

## 和 V9.4 的关系

本清单是 V9.4 自证阶段的前置护栏。后续状态机硬化时，至少要把以下规则机器化：

- `submitted -> accepted` 必须校验 `accepted_by != owner/author`。
- 修改自身 write_scope 必须进入人工拍板路径。
- 真实 secret、真实计费、常驻部署必须进入人工拍板路径。
