# V9.4.1 实施设计 v1.1

> 定位：Codex 已评审 `accepted_with_changes`，本 v1.1 逐条吸收 4 项 finding；T-20260626-60 已按本设计实施并通过 eval/反射器验证。
> 一句话：把 V9.4 的「能发现」补成「能拦住」——但**只对能真正硬拦的路径声称硬拦，旁路如实标注、交给反射器事后兜底**。

## 变更日志（v1.0 → v1.1，吸收 Codex 4 项）

| # | Codex finding | 本版处理 |
|:--:|------|------|
| P1-1 | pre-write 看不到写入内容，认不出裸改 accepted | Fork A 增加"hook 解析候选内容"硬要求；RED 必覆盖 Write 全量 + Edit |
| P1-2 | write_scope 锁只拦 Write/Edit，Bash 写文件旁路 | 改口径为"封堵 Write/Edit 裸改"，Bash 写列为已知未覆盖，交反射器事后发现 |

| P2-2 | `V9_GATE_DISABLE` 通用 env 逃生阀=新旁路 | 删除 env 阀，改人工手动恢复（卸 hook/改配置/外部开关），不入 agent 可写路径 |

## 一、现状（勘探确认）

| 事实 | 含义 |
|------|------|
| gate-enforce 有 pre-start/pre-write/pre-end，**无 pre-accept** | 缺验收转移拦截点 |
| **无 accept 入口**：验收=手改任务卡 `review_status: accepted` + 填 `accepted_by` | 转移是裸文件编辑，无校验 |
| `v9-task-state-check.py` 是事后扫描器（reflex 源 6，advisory） | 能发现 ACCEPTED_BY_SELF/MISSING，不拦写入 |
| pre-write hook 仅解析 `file_path`，未读 content/new_string | **裸改内容判定缺数据源（P1-1 根因）** |
| `.codex/hooks.json` 中 pre-write 只挂 `Write\|Edit`，Bash 只跑 session-guard | **Bash 写文件不经 pre-write（P1-2 根因）** |
| vault 是 git 仓库且有规律提交 | git pre-commit 触发可行 |

## 二、两个设计分叉与裁决

### Fork A：self-accept 怎么拦？→ `v9_accept` 命令 + hook 内容级裸改拦截

- **`v9_accept <task_id> <accepted_by>`**：读整张卡 → 生成候选 accepted 版本 → 跑 `v9-task-state-check` 校验（accepted_by 非空且 ∉ {owner, author}；reviewer 非空）→ 通过才原子写 `review_status/accepted_at/accepted_by`。
- **裸改拦截（吸收 P1-1）**：pre-write 不能只靠 `gate-enforce --file`（那只能看旧文件）。必须：
  1. 扩展 hook 解析候选内容：`Write` 取 `tool_input.content`（全量）；`Edit` 取 `old_string/new_string`，**对当前文件做替换重建候选全文**（new_string 是片段，单看判不了 accepted_by）。
  2. 候选全文落临时文件 → 交 `v9-task-state-check` 校验 → 若结果含 `review_status: accepted` 且 accepted_by 非法 → 阻断（提示走 v9_accept）。
- 这样裸手改任务卡把 review_status 改成 accepted 会被拦，强制走 v9_accept。

### Fork B：eval-runner 触发 → pre-commit + v9_accept 双管，且 v9_accept 实时跑

- **git pre-commit**：改 `.standards/` 或 `02-项目管理/脚本/` 时跑 eval，失败阻断 commit。
- **v9_accept 前置（吸收 P2-1）**：harness 类任务验收时**实时跑 eval**（不读旧 latest）。
- **新鲜度证明**：`harness-eval-latest.json` 写入被测脚本集的 hash + max(mtime)；任何"读 latest"的判断都先校验报告是否针对当前代码，过期视同未测。
- 二者互补：pre-commit 防带病入库，v9_accept 实时跑防未测验收。

## 三、write_scope 自改锁（吸收 P1-2，口径收窄）

- **能硬拦的**：pre-write 拦截对 `02-项目管理/智能体状态/*.md` 中 `write_scope:` 行的 **Write/Edit** 改动。handshake 走 bash awk 不经工具层 hook，不受影响（边界干净）。
- **拦不住的（如实标注）**：Bash（shell/perl/python）直接写状态文件**绕过 pre-write**（当前 Bash 只挂 session-guard）。**不声称完全封死。**
- **兜底**：Bash 旁路改动由反射器 `scope-tamper` 第 7 源**事后发现**（p1/advisory）。RED fixture 加一条"Bash 写状态文件"样本，作为**已知未覆盖风险**显式登记，而非假装拦住了。

## 四、实施顺序：对门禁做 TDD（先红后绿）

gate-enforce 是承重墙，直接改有堵死全系统的风险。先红后绿：

1. **先给 eval-runner 加 negative fixture（应 RED），必须覆盖这 4 类**：
   - `Edit` 裸改 review_status→accepted → 应拦
   - `Write` 全量覆盖含 review_status: accepted（非法 accepted_by）→ 应拦
   - `Bash` 写状态文件改 write_scope → **已知未拦**，fixture 断言"反射器事后能发现"（而非 pre-write 拦住）
   - 拿**旧 eval 报告**验收新改动 → 应被新鲜度校验拦
2. **再实现门禁**，直到上述 fixture 达到预期（该绿的绿、该红的红、已知未覆盖的如实标注）。
3. **灰度裁决（实施校准）**：原建议为 warn 2 天或 3 次成功 v9_accept 后翻 block；实施时因 19/19 harness eval、hook 冒烟、且拦截范围收窄到 `review_status: accepted` 的 self-accept 热路径，改为直接 block。误伤恢复仍走人工卸 hook/改配置。

## 五、逃生阀（吸收 P2-2，改人工）

- **不上** `V9_GATE_DISABLE` 通用环境变量——agent 能在自己命令里设置它，等于新的"自己把约束改松"旁路。
- 真要逃生：**人工手动步骤**——临时卸载 hook / 手动改配置 / 带审计的本机外部开关，且**不纳入 agent 可写路径**。

## 六、五个评审问题的最终裁决（Codex 已答）

1. Fork A 选 v9_accept 对；裸改封堵**必须在 hook 层解析候选内容**，不能只靠 gate-enforce --file。（已写入二·Fork A）
2. Fork B 双触发不冗余；但 v9_accept 要**实时跑 eval**或校验 hash。（已写入二·Fork B）
3. write_scope 有 **Bash 旁路**，自改锁**不宣称完全封死**。（已写入三）
4. 灰度在实施阶段裁决为**直接 block**：只拦 accepted 转移中的 self-accept/缺验收字段，且已有 eval 与 smoke 覆盖；不再另加 warn 状态机。（已写入四）
5. `V9_GATE_DISABLE` **不上**，逃生靠人工手动恢复。（已写入五）

## 七、风险与回滚

| 风险 | 缓解 |
|------|------|
| 新门禁误伤正常验收/编辑 | warn 灰度；positive fixture 确保不误杀 |
| hook 重建候选全文有 bug | Edit 重建逻辑纳入 eval fixture；Codex 复核 |
| Bash 旁路被恶意/误用 | 如实标注 + 反射器事后发现，不假装拦住 |
| 堵死全系统 | 小步提交可 revert；逃生靠人工卸 hook（非 env） |
