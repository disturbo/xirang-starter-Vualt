## 0 · 什么是息壤

**一句话**：AI Agent 团队的作战手册。定义了谁做什么、怎么流转、出错了谁修、怎么证明活干完了。

不是理论框架，是操作规程——每个 Agent 启动时读这一份，就知道自己在团队里的位置和行为边界。

**V9 核心突破**：将合规判定从 V8 的"六档分类"简化为**一个二元判断**——写文件还是不写文件。写文件就声明，不写就直接回复。所有复杂规则都是这条铁律的操作化展开。

**息壤的核心能力**：

| 维度 | 息壤做了什么 |
|------|------|
| 角色分工 | 6 个原子 Agent 各有职责边界，不越权 |
| 流程管道 | 六步流程：拆分→计划→执行→监控→检核→验收 |
| 通信协议 | CLI 直连（同步）+ Vault 文件（持久化审计）双层架构 |
| 合规框架 | 二元触发器 + M3/M4/M5 声明制度 + Gate 门禁自动拦截 |
| 错误处理 | 五级升级链 + 回滚补偿 + 不死鸟自愈 |
| 成本治理 | 预算分级 + 熔断机制 + usage token 事件 + 可观测周报 |
| 质量门禁 | pre-write-hook + gate-enforce + 产物自检三件套 |
| 自证回归 | harness eval-runner + positive/negative fixture，证明工具会拒绝坏样本 |
| 反射器巡检 | launchd 常驻 + `health-latest.json` + `sources_run` 八源自省，区分真静默与假静默 |
| 验收治理 | `review_status` 双状态 + `v9_accept`，防止 Agent 自验收 |
| Handoff 治理 | `v9-handoff-check.py` 检查显式交接任务是否可接手 |

## 0.1 ·「息壤」命名释义

「息壤」出自《山海经·海内经》鲧治水神话。息壤是能自行增生、取之不竭的神土。核心意象是**会自己生长的基础材料**。

| 《山海经》息壤意象 | 方法论对应 |
|------|------|
| 自行生长的土 | task card、retrospective、规则、脚本在实践中持续增殖 |
| 用来应对洪水 | 应对多 Agent 协作中的上下文洪水、任务洪水、漂移洪水 |
| 不是普通材料，而是基础设施 | 不是单篇文档，而是入口、门禁、状态表、事件流、度量系统 |
| 鲧的失败：有神土也不能无治理地堵 | 不能只堆文档，必须有运行时激活、路由、升级和复盘 |
| 后续治水走向疏导与定九州 | 目标不是塞进一个 Agent，而是拆分、分流、验收、沉淀 |

「息壤」不是「无限扩张」的隐喻，而是「可生长且需治理」的隐喻。

## 0.2 · 前提：项目记忆系统

息壤的前提不是必须拥有 Obsidian Vault，而是必须有一个**可持久化的项目记忆系统**。

| 能力 | 为什么需要 |
|------|------|
| 可持久化 | 任务、资料、决策、产物不能只留在聊天记录里 |
| 可检索 | Agent / 人接手时能重新找到上下文 |
| 可链接 | 需求、资料、方案、PRD、决策、复盘能互相引用 |
| 可审计 | 谁基于什么资料做了什么判断，有记录可追溯 |
| 可演化 | 模板、规范、案例、门禁能随着实践持续生长 |

三种部署形态：

| 形态 | 适用对象 | 载体 |
|------|------|------|
| 团队版 | 多 Agent / 多同事 / 多模块长期项目 | Obsidian Vault + CLI + 状态表 + 事件流 |
| 单人版 | 个人产品经理、单 Agent 协作 | 一个结构化项目文件夹 |
| 轻量项目包 | 没有 Vault 或临时项目 | 普通文件夹 / 云文档目录 |

无 Vault 时最小项目包：

```
项目包/
├── 00-项目说明.md
├── 01-资料/
├── 02-需求卡.md
├── 03-资料摘要.md
├── 04-设计方案.md
├── 05-评审记录.md
├── 06-PRD.md
└── 07-决策日志.md
```

## 0.3 · 底层理论基石：Agent 12 原理

> 息壤每个设计决策都可追溯到 Agent 的底层原理。

### 四层模型映射

| 原理层 | Agent 原理 | 息壤架构层 | 实现方式 |
|:---:|------|:---:|------|
| 基座层 | Message数组 / 上下文窗口 / 自回归生成 | L3 基础设施层 | Vault 文件系统 + TokenManager |
| 控制层 | 系统提示 / 预填充 / 停止序列 | L1 Agent 层 | SOUL 人格 + format-constrainer + ToolCall |
| 能力层 | CoT / Few-Shot / Tool Use / RAG / ReAct | L2 六步流程层 | 任务分解 + Skill + LLM Wiki + GBrain + TaskExecutor |
| 编排层 | Multi-Agent 编排 | L1 分子池 + L2 流程编排 | Subagent + 六步管道 + 通信协议 |

### 关键设计判断

| 息壤做了什么 | 为什么这么做 | 对应原理 |
|------|------|:---:|
| Subagent 返回 ≤500 字摘要 | 上下文窗口稀缺，必须隔离 | 上下文窗口 |
| 每个 Agent 独立启动清单 | System Prompt 定义行为边界 | 系统提示 |
| 六步每步有输出模板 | 自回归无"事实核查"，结构锁死边界 | 自回归生成 |
| Skill 清单 + frontmatter 必填 | 样板比规则更有效 | Few-Shot |
| 不死鸟 Phoenix 自愈 | ReAct 循环死锁检测 | ReAct |
| LLM Wiki 三层资料结构 | RAG 分块：Source→Summary→Published | RAG |
| 错误升级链 5 级 | Multi-Agent 错误传播放大 | Multi-Agent 编排 |

**五个工程判断**：

1. **上下文隔离 > 统一上下文** — Subagent 核心价值是隔离，不是并行
2. **结构化模板 > 自然语言约束** — frontmatter + 硬约束可验证
3. **反馈闭环 ≠ 死循环** — ReAct 必须设 max_steps + 重复检测熔断
4. **RAG 精度 > RAG 广度** — 三层结构控制分块粒度
5. **显式定义 > 隐式学习** — Skill 清单是持久化 Few-Shot 示例库

## 1 · V9 核心：二元触发器与合规框架

### 1.1 设计动机

V8 合规层的核心问题：
1. M0-M5 六档判定过重，Agent 认知负担大
2. 格式不统一，6 Agent 跨 4 平台各自维护
3. 验证困难，无法程序化检测

V9 核心创新：**将合规入口简化为一个二元判断**。

### 1.2 二元触发器

```
收到消息 → 第一判断：「这个任务会写文件吗？」
  不写 → 直接回复（零合规开销）
  写   → pre-flight（声明 + 亮灯 + 执行）
```

> 没有第三种情况。闲聊不是任务，不需要建卡。

### 1.3 唯一铁律

> **写了文件但没声明 = 违规。**

所有复杂规则（档位/scope/gate/handoff）都是这条铁律的操作化展开。

### 1.4 不写文件的场景（零合规开销）

1. 解释概念 / 纯问答 / 方法论讨论
2. 讨论方案（未到执行）/ 头脑风暴
3. 评审 / 比较 / 核对但不落盘
4. 日常闲聊 / 询问下一步
5. 巡检无异常 / 状态查询

### 1.5 灰区判定

| 信号 | 判定 |
|------|------|
| 有具体对象 + 明确产出物 | 写文件 → pre-flight |
| 咨询语气（"怎么推进"/"能不能做"）| 不写文件 → 直接回复 |
| 无法判定 | 问用户确认，1 轮内决定 |

### 1.6 豁免

以下操作免声明：
- 追加运行日志一行（M3 收工）
- heartbeat 更新（状态文件 last_heartbeat 字段）

### 1.7 执行中扩展

执行中发现要写更多文件 → 暂停、补充声明、再继续。
每次写入前自问：「我声明过要写这个文件吗？」没有 → 先声明。

## 2 · 档位系统（M3/M4/M5）

> 确定"要写文件"后，档位是"事后标注"——决定声明格式和流程重量。

### 2.1 三档定义

| 档位 | 场景 | 文件数 | 时间 | 声明格式 |
|:---:|------|:---:|:---:|------|
| M3 | 单文件修改，<20min | 1 | <20min | 一行声明 |
| M4 | 多文件产出/交付物 | 2+ | 20min-2h | 完整 `V9 已激活：` 块 |
| M5 | 跨 Agent / >2h / 需拆分 | 多 | >2h | M4 + 预算 + 拆分计划 |

### 2.2 判定决策树

```
要写文件？
  ├── 只改 1 个文件 + <20min ──→ M3
  ├── 改多文件 / 有明确交付物 ──→ M4
  └── 跨 Agent / >2h / 需拆分 ──→ M5
```

### 2.3 各档规格对照

| 维度 | M3 | M4 | M5 |
|------|-----|-----|-----|
| 状态文件更新 | 不更新 | 亮灯+熄灯 | 亮灯+熄灯+heartbeat |
| 事件流 | 不写 | start+end | start+heartbeat+end |
| 看板 | 不更新 | 更新 | 更新+拆分 |
| 运行日志 | 写一行 | 不写（有 task card） | 不写（有 task card） |
| task card | 不建 | 建 | 建+budget |
| Handoff | 不写 | 有下游时写 | 必写 |

### 2.4 灰区速判

| 场景 | 档位 |
|------|:---:|
| 追加一行到已有文件（日志/事件流） | M3 |
| 修复一个文件的 bug（<50行改动） | M3 |
| 改 1 个文件但牵涉看板更新 | M4（看板也是文件）|
| 批量修改 3+ 文件的同一字段 | M4 |
| PRD + 原型 + 看板登记 | M5 |
| 需要调其他 Agent 协作 | M5 |

### 2.5 升降档规则

| 触发 | 动作 |
|------|------|
| M3 发现需写第 2 个文件 | 升为 M4，补完整声明 + 亮灯 |
| M4 发现需跨 Agent 协作 | 升为 M5，补预算 + 拆分 |
| M4/M5 执行中发现只需改 1 文件 | 不可降档（已亮灯，完整收工） |

## 3 · 写入声明与 Pre-flight 流程

### 3.1 M3 声明（一行）

```
V9 写入声明：{文件路径} | {动作摘要}
```

示例：`V9 写入声明：02-项目管理/运行日志/2026-05-28.md | 追加今日任务记录`

**M3 收工**：追加一行到 `02-项目管理/运行日志/YYYY-MM-DD.md`：
```
- HH:MM | M3 | 动作摘要 | 结果 | 产物路径(可选)
```

### 3.2 M4 声明（完整块）

```
V9 已激活：
- 档位：M4
- 任务：{任务名}
- 写入范围：{将写入的文件/路径列表}
- 验收方：{用户 / 具体Agent名}
```

**M4 Pre-flight 三步**：
1. **亮灯** — 更新状态文件 status→busy + 追加 task_start 事件
2. **声明** — 输出上方格式块
3. **执行** — 开始工作

**M4 收工三件套**：
1. 产物清单：列出所有写入文件 + 一句话描述
2. 自查结果：路径合规 / frontmatter / 无装饰性emoji / 无越权
3. 验收建议：验收方 + 检查点 + 风险假设
4. 更新状态文件 status→idle
5. 追加 task_end 事件
6. 如有成本：`python3 .standards/agent-cost-events.py append`
7. 看板 Handoff（如有下游）

### 3.3 M5 声明

```
V9 已激活：
- 档位：M5
- 任务：{任务名}
- 预算：{预估 token/时间}
- 写入范围：{路径}
- 拆分计划：{子任务数} 个子任务
- 验收方：{验收链}
```

M5 额外要求：子任务用 subtask-record.py 记录 + 长任务写 heartbeat + 必须写 Handoff。

### 3.4 失败判定（5 类）

| 类型 | 表现 | 处理 |
|------|------|------|
| 范围溢出 | 写了声明外的文件 | 暂停→补充声明→继续 |
| 格式缺失 | 产出无 frontmatter | 补写 |
| 品牌违规 | 错误品牌名/色值 | 立即修正 |
| 升档不足 | M3 写了多文件但未升 M4 | 补声明+亮灯 |
| 静默写入 | 写了文件完全无声明 | **最严重** — 回退+重新声明 |

## 4 · 六脉体系：六个子系统

> 息壤 = 六脉合一。每条脉是一个独立子系统，贯穿所有 Agent 和流程步骤。
> 六脉是"规矩"，不是"动作"。

### 4.1 六脉速览

| 脉 | 子系统 | 一句话 | 负责人 |
|:--:|--------|--------|--------|
| ① | **Claude Design 工艺** | 方案设计和 PRD/原型大块产出的工程方法 | 青霉素 |
| ② | **驾驭工程** | Agent 的可靠性、可观测性、治理 | 阿莫西林 |
| ③ | **不死鸟 Phoenix** | 错误自愈：抗体扫描、崩溃恢复、向量化诊断 | WorkBuddy |
| ④ | **LLM Wiki** | 三层资料结构 + frontmatter + Dataview 可查询 | 红霉素 |
| ⑤ | **GBrain** | 语义搜索 + Brain Score + cron dream 自动维护 | Claudian |
| ⑥ | **Skill 清单** | 各平台 skill 目录 + 能力声明 + 发现机制 | 红霉素 |

### 4.2 六脉约束层

```
六脉约束层（贯穿）
  │
  ├──→ L1 Agent 层：每个 Agent 启动时加载哪些 skill？遵循哪些 frontmatter 约定？
  ├──→ L2 流程层：每步做完后输出什么格式？存哪里？怎么通知下一步？
  ├──→ L3 分子层：子 Agent spawn 时必须注入哪几脉的约束包？
  └──→ L4 基础设施层：GBrain index、LLM Wiki 三层目录、Skill 清单更新周期
```

### 4.3 脉① Claude Design 工艺

> 方案设计和 PRD/原型大块产出的工程方法。核心理念：**价值在逼近过程，而非一次性产物**。

**3 Phase × 10 Step 工作流**：

```
Phase 1: 构建 Design System（资料→画像→Review）
  Step 1  资料收集（公司/资源/风格，all optional）
  Step 2  分析等待（有信息的等待体验，todo 进度透明）
  Step 3  画像 Review（纯对话修改）

Phase 2: 需求收敛 → 探索对齐
  Step 4  动态需求问卷（非固定模板，基于上下文实时生成）
  Step 5  参考系对标（"类似 XX 的方式"坐标映射）
  Step 6  方向分叉（A/B/C 方案，用户选一个）

Phase 3: 产物生成 → 实现
  Step 7  逻辑确认稿（结构 > 视觉，纯结构无设计）
  Step 8  实现计划（进度条重置，清晰阶段切换）
  Step 9  高保真 v1 + 参数化面板（可调参数的实例）
  Step 10 迭代修正
```

**5 个贯穿设计选择**：

1. **Todo 是分形的** — 不同粒度嵌套，保持进度透明
2. **阶段切换重新生成计划** — 9 步→5 步时进度条重置
3. **每步交互形式不同** — 表单→todo→对话→确认稿→参数化面板
4. **结构→多态渲染** — 同一结构的不同保真度形态
5. **规则源自实战踩坑** — System Prompt 每条规则都有对应教训

**对息壤的实际落地**：
- 每个模块产出 `SKILL.md`（文件级上下文契约）
- PRD 阶段 2 后加"探索→实现"切换信号
- 多方案时列 A/B/C 分叉而非单一推荐
- HTML 原型加可调参数面板

### 4.4 脉② 驾驭工程

> Agent 的可靠性、可观测性、治理。确保系统"真的在跑"而非"文档写了但没启用"。

**三层可观测性**：

| 层 | 载体 | 更新频率 | 用途 |
|---|---|---|---|
| 状态层 | `02-项目管理/智能体状态/*.md` | 任务开始/结束 | 谁在忙、谁空闲、谁出错 |
| 事件层 | `智能体事件.jsonl` | 每个生命周期节点 | 审计追溯、时间线分析 |
| 指标层 | `v8-health-metrics.py` 报告 | 周度 | 完成率/耗时/错误率/重试率 |

**门禁体系（4 个检查点）**：

| 检查点 | 工具 | 时机 |
|--------|------|------|

**治理闭环**：状态表 → 事件流 → 健康指标 → 周报 → 规则迭代 → prompt-build 分发 → 回到状态表。

### 4.5 脉③ 不死鸟 Phoenix

> 错误自愈子系统。当 Agent 遇到错误时，先自动匹配已知模式修复，而非直接升级到人。

**8 个内置抗体模式**：

| 抗体 | 触发条件 | 自动修复动作 |
|------|---------|-------------|
| 404-ban | 访问被禁 | 切换 Provider |
| timeout-retry | 网络超时 | 指数退避重试（1s→2s→4s→8s） |
| rate-limit-wait | 频率限制 | 指数退避等待 |
| auth-refresh | 认证失败 | 刷新 Token |
| json-parse-fix | JSON 格式错误 | 自动修复格式 |
| context-trim | 上下文过长 | 自动压缩/截断 |
| model-switch | 模型不可用 | 按降级链切换（opus→sonnet→haiku） |
| generic-catch | 未知错误 | 触发 10 步系统化排查 |

**10 步排查流程**：
1. 记录错误详情 → 2. 分类（HTTP 状态码 + 模式）→ 3. 检查熔断器 → 4. 匹配抗体库 → 5. 尝试降级模型 → 6. 执行修复 → 7. 验证结果 → 8. 记录过程 → 9. 更新抗体库 → 10. 生成错误报告

**进化引擎**：自动分析成功/失败案例，优化抗体库匹配权重。新的错误模式在修复后自动入库。

**与错误升级链的对接**：不死鸟处于 L1 层——L0.5 重试耗尽后，先到 Phoenix 自动匹配；Phoenix 无解才升级到 L2（Owner 修复）。

### 4.6 脉④ LLM Wiki

> 三层资料结构。核心理念（源自 Karpathy）：LLM 写/维护 wiki，人类提供 source 和提问。Wiki 是持续复利的资产，不是每次重新生成。

**三层架构**：

| 层 | 路径 | 内容 | 所有权 | PRD 可用 |
|---|---|---|---|---|
| **Source（原始源）** | `20-资料/业务文件/` | docx/xlsx/会议纪要/截图 | 头孢采集 | 否（仅参考） |
| **Summary（摘要层）** | `10-项目/{模块}/资料摘要.md` | 结构化提取、去重、标注来源 | 头孢加工 | 是（优先） |
| **Published（发布层）** | `10-项目/{模块}/PRD.md`、设计方案 | 经评审的终稿 | 青霉素/红霉素 | 是（终态） |

**成熟度五档**：

| 档位 | 含义 | 模块数（示例） |
|:---:|------|:---:|
| 骨架占位 | 仅有 README 和目录结构 | 12 |
| 业务理解已完成 | 资料摘要完成 | 13 |
| 业务理解+流程已完成 | 设计方案初稿 | 1 |
| 已设计方案 | 评审通过 | 2 |
| 已发布PRD | 开发可用 | 5 |

**Frontmatter 必填字段**：
- `status`（draft/review/published）
- `version`
- `created` / `updated`
- `owner`（Agent ID）
- `maturity`（五档枚举）
- `module`（归属模块）
- `source_docs`（原始资料引用）

**质量验证工具**：
```bash
python3 02-项目管理/脚本/llm_wiki_check.py --mode strict --path 10-项目/示例项目/
# 3 种模式：basic（结构）/ non-placeholder（内容一致性）/ strict（警告=失败）
```

### 4.7 脉⑤ GBrain

> 语义搜索引擎。将 Vault 中的 Markdown 内容向量化，提供语义级检索能力。

**核心架构**：

| 组件 | 技术 | 作用 |
|------|------|------|
| 嵌入模型 | bge-m3（Ollama 本地） | 1024 dims，8192 context，多语言 |
| 存储引擎 | PGLite（嵌入式 Postgres） | 本地运行，无 Docker |
| 检索方式 | 混合搜索（vector + full-text） | 语义相似 + 关键词精确 |
| 维护机制 | dream（全量）+ sync（增量） | cron 自动执行 |

**运维命令**：

```bash
gbrain init --repo ~/Desktop/obsidianVault     # 初始化
gbrain source add --name wiki --path ~/wiki/   # 注册源
gbrain dream --repo ~/Desktop/obsidianVault    # 全量嵌入（6h 一次）
gbrain sync --repo ~/Desktop/obsidianVault     # 增量同步（30min 一次）
gbrain search "PRD 输出规范"                    # 语义搜索
gbrain status                                   # Brain Score + 覆盖率
gbrain doctor                                   # 健康检查
```

**Brain Score**：衡量 Vault 语义索引健康度的综合指标。包含：页面覆盖率、嵌入新鲜度、语义链接密度。

**与 LLM Wiki 的配合**：
- LLM Wiki 提供结构化内容（三层 Markdown）
- GBrain 提供语义检索入口（向量化索引）
- Agent 工作流：`gbrain search` 找到相关文档 → `Read` 文档内容 → 基于内容产出

**核心 Skills 分类**：

| 类别 | Skills | 平台 |
|------|--------|------|
| 工作流 | start-task / ingest-source / publish-wiki / handoff-task / review-contradictions | Vault |
| 采集/转换 | feishu-collection（CLI-first） / markitdown / paddleocr-text-recognition / paddleocr-doc-parsing / agent-reach / enterprise-field-collection / web-research | 共享 / Hermes / Vault / Reasonix / Hermes Desktop |
| 趋势研究 | last30days（最近30天社区/平台热度） | 共享 |
| PRD | yijing-prd-spec v3.3.5 / prd-brand-audit / generate-diagram | 共享 / Hermes / Vault |

| 代码 | flowforge（Spec→Plan→Code→QA） | 共享 / OpenClaw |
| 运维 | gbrain / obsidian-batch-wikilink-update | OpenClaw/Hermes |

**OCR 与多模态识图铁律**：

凡从图片、截图、扫描件、图片 PDF 中提取信息，必须在输出里标明来源，不允许把 OCR 结果、视觉理解和业务推理混成一段无来源结论。

| 标签 | 含义 | 可作为事实的范围 |
|------|------|------------------|
| `[OCR:PaddleOCR-local]` | 本地 PaddleOCR / helper 抽出的文字 | 文案、字段名、编号、金额、日期、状态、按钮文字 |
| `[OCR:PaddleOCR-api]` | PaddleOCR 云 API 抽出的文字/结构 | 表格、公式、版面 Markdown、文档结构 |
| `[Vision:multimodal]` | 多模态模型对画面的观察和理解 | 布局、图标含义、视觉层级、交互关系、设计质量 |
| `[Hybrid]` | OCR 事实 + 视觉/业务推理后的综合判断 | PRD/竞品分析/流程推断，但必须能追溯到上游事实 |
| `[Unverified]` | 未被 OCR 或视觉直接确认 | 只能作为待确认项 |

执行规则：

1. 字段名、金额、编号、日期、状态、按钮文案，以 OCR/parser 为准；OCR 低置信或缺失时标 `needs human check`。
2. 布局、图标意图、视觉层级、交互路径、设计质量，以多模态视觉或人工复核为准；PaddleOCR 不能替代视觉理解。
3. Reasonix / Hermes Desktop 如果只调用 PaddleOCR，只能说“文字识别结果显示”，不能说“我看到/我看懂这张图”。
4. OCR 与多模态冲突时同时保留，不静默裁决：精确文字优先 OCR，视觉/语义解释优先 Vision，并标注人工复核。
5. 交接或沉淀到 PRD/资料摘要时，必须保留标签，避免下游 agent 把推理当原文。

**跨平台共享机制**：

```
~/.skills-manager/skills/          ← 共享主目录（所有跨平台 skill 实体）
  ├── feishu-collection/
  ├── agent-reach/
  ├── last30days/
  ├── markitdown/
  ├── paddleocr-text-recognition/
  ├── paddleocr-doc-parsing/
  ├── yijing-prd-spec/
  ├── taste-skill/
  └── flowforge/

~/.codex/skills/{slug}                         ──→ symlink → ~/.skills-manager/skills/{slug}
~/.openclaw/skills/{slug}                      ──→ symlink → ~/.skills-manager/skills/{slug}
~/.workbuddy/skills/{slug}                     ──→ symlink → ~/.skills-manager/skills/{slug}
~/.hermes/skills/{分类}/{slug}                 ──→ symlink → ~/.skills-manager/skills/{slug}
~/Desktop/obsidianVault/.skills/{slug}         ──→ symlink → ~/.skills-manager/skills/{slug}
~/Library/Application Support/reasonix/global-workspace/.agents/skills/{slug} ──→ symlink → ~/.skills-manager/skills/{slug}
~/Library/Application Support/hermes-desktop/skills/{slug}                    ──→ symlink → ~/.skills-manager/skills/{slug}
```

路径事实源：`[[agent-paths]]`。能力索引：`[[Skill-Inventory]]`。ClawHub / Codex installer 只负责获取或创建 skill；一旦 skill 需要多智能体共享，实体必须迁入 `~/.skills-manager/skills/{slug}`。

**Skill 共享安装铁律**：

1. 安装前先查 `Skill-Inventory.md`、`.skills/RESOLVER.md` 和各平台目录，确认没有同名分叉。
2. 多智能体通用 skill 只允许有一个共享实体：`~/.skills-manager/skills/{slug}`。
3. Codex / OpenClaw / Hermes / WorkBuddy / Vault / Reasonix / Hermes Desktop 的入口只挂 symlink，不各自复制实体目录。
4. 平台专属 skill 可以留在平台目录，但必须在 Skill Inventory 标注“平台私有”或“分叉版”。
5. 安装或升级后同步更新 `Skill-Inventory.md`、`.skills/RESOLVER.md`、相关 slash command 和 `agent-paths.md`。
6. 已有 CLI 时，skill 做“薄路由”：记录调用顺序、路径规则、权限坑和降级策略，不再重复实现 CLI。`feishu-collection` 当前以 `lark-cli` 为执行器。
7. 版本型规范 skill 必须全平台同步到最新版。`yijing-prd-spec` 当前统一为 v3.3.5 共享完整版。

**Skill 生命周期**：Active（生产可用）→ Experimental（实验中）→ Passive（按需调用）→ Deprecated（归档）

### 5.3 路由决策原则

> 有限资源只在其能力不可替代时才消耗。

- 能力匹配相当 → 选资源消耗最小的

## 6 · 动态分子 Agent（Subagent）

### 6.1 定义

| 维度 | 原子 Agent（持久层） | 分子 Subagent（动态层） |
|------|------------------------|--------------------------|
| 数量 | 6，固定 | 0~N，动态 |
| 生命周期 | 持久，跨会话 | 瞬态，用完即销 |
| 调度 | 需全局协调（状态表） | 父 Agent 局部管理 |
| 决策权 | 有（在职责边界内） | 无（只执行，不决策） |
| 写权限 | vault 全范围（按职责边界） | 父 Agent 限定的路径分区 |

### 6.2 Spawn 决策矩阵

| 流程步骤 | 用 Subagent？ | 模式 | 原因 |
|------|:---:|------|------|
| Step 1 工作拆分 | 可选 | Fan-Out | 并行读多模块上下文 |
| Step 2 计划编排 | 不用 | — | 计划需完整上下文 |
| Step 3 工作执行 | 核心 | Fan-Out / Agent Pool | 并行生成多产物 |
| Step 4 执行监控 | 不用 | — | 监控需全局视图 |
| Step 5 交付物检核 | 推荐 | Fan-Out | 三项审核互不依赖 |
| Step 6 测试验收 | 可选 | Inline | 逐项验证 |

### 6.3 硬约束（不可违反）

1. **嵌套深度 = 1**：子 Agent 不可再 spawn 孙 Agent
2. **最大并行 ≤ 6**：超过需排队或合并
3. **不可写 00-MOC/ 和 30-规范/**：只有主 Agent 有权
4. **不可做决策**：决策必须回到父 Agent
5. **返回值 ≤ 500 字摘要**：上下文隔离是核心价值
6. **路径互不重叠**：两个子 Agent 不可同时写同一文件

### 6.4 子 Agent 生命周期状态机

```
SPAWNED → RUNNING → COLLECTED → DESTROYED
                ↘ FAILED → RETRIED → COLLECTED
                ↘ TIMEOUT → DESTROYED
```

**重试决策**：

| 失败原因 | 策略 |
|---------|------|
| 网络超时 | 直接重试 |
| 上下文超限 | 拆更细 |
| 模型太弱 | 换强模型 |
| 权限不足 | 回收自做 |
| 已重试 ≥2 次 | 升级不死鸟 |

### 6.5 约束注入模板

父 Agent spawn 子 Agent 时注入约束包（由 `.standards/xirang-spawn.py` 自动生成）：
1. 写入范围：只写指定目录
2. 品牌规范：主色 #861B2F、辅色 #2D9C4F、字体 PingFang SC
3. 输出铁律：禁 emoji、frontmatter 必填、Markdown 规范
4. 违反优先级：P0 路径 > P1 格式 > P2 品牌 > P3 内容
5. 返回格式：结构化摘要 ≤500 字

### 6.6 降级：无 Subagent 能力时

| 场景 | 降级方案 |
|------|---------|
| 执行 Agent 无 spawn 能力 | 串行执行（约束和规则不变） |
| 任务需并行但 Agent 不能 | 主 Agent 拆分后分发给多个 Agent |

### 7.1 双层通信架构

```
┌──────────────────────────────────────────────────────────────┐
│  CLI 直连层（主传输层 — 主动通信 / 同步）                      │
│                                                               │

│  hermes agent --message "..."                  → Hermes      │
├──────────────────────────────────────────────────────────────┤
│  Vault 文件层（持久化层 — 状态/审计）                          │
│                                                               │
│  看板 / 状态表 / 事件流 / 决策日志                             │
└──────────────────────────────────────────────────────────────┘
```

### 7.2 五种通信模式

| 层级 | 方向 | 载体 | 实时性 | 典型场景 |
|------|------|------|:---:|------|
| CLI直连 | 原子↔原子 | CLI 进程调用 | 同步 | 任务委派、审核 |
| A↔A | 原子间状态 | vault 看板 + 状态文件 | 拉取 | Handoff、决策留痕 |
| A→M | 原子→分子 | spawn prompt + 约束包 | 推送 | Subagent 执行 |
| M→A | 分子→原子 | 结构化摘要 | 推送 | 子 Agent 回传 |
| M↔M | 分子↔分子 | `_temp/{task-id}/` 暂存区 | 拉取 | 中间产物共享 |

### 7.3 CLI 直连 vs Subagent 选择

| 需求 | 用 CLI 直连 | 用 Subagent |
|------|:---:|:---:|
| 需要对方独有的 skill/知识 | 是 | — |
| 纯并行拆分（同质任务） | — | 是 |
| 需要独立决策判断 | 是 | — |
| 需要严格约束和路径控制 | — | 是 |
| 被调方有完整上下文/记忆 | 是 | — |
| 一次性任务，用完即弃 | — | 是 |

### 7.4 消息队列

消息类型：`task_handoff` / `review_request` / `status_update` / `error_report` / `budget_alert`

## 8 · 六步流程

> 六步骨架继承自 V6，V9 不改变流程结构。每步有明确的输入/输出/门禁。

```
Step 1           Step 2           Step 3           Step 4           Step 5           Step 6
工作拆分 ──→ 计划编排 ──→ 工作执行 ──→ 执行监控 ──→ 交付物检核 ──→ 测试验收
```

### Step 1 · 工作拆分

| 维度 | 内容 |
|------|------|
| 主责 | 青霉素拆任务目标→可执行子任务 |
| 辅助 | 阿莫西林提供上下文（模块 README、资料摘要、PRD 现状） |
| Subagent | 可选 Fan-Out：spawn explore-agent × N 并行读多模块摘要 |
| 输入物 | 用户需求（对话/飞书/会议纪要）+ 模块 README |
| 输出物 | Task Card（`02-项目管理/任务卡/YYYY-MM/T-YYYYMMDD-NN.md`） |
| Gate | `pre-start`：task card 合法性检查 |

**Task Card 必填字段**：`task_id` / `title` / `module` / `task_size`(S/M/L/XL) / `owner` / `status` / `priority` / `budget` / `paths.allowed_write_roots` / `deliverables`

### Step 2 · 计划编排

| 维度 | 内容 |
|------|------|
| 主责 | 青霉素编排 todo + 依赖关系 + 时间估算 |
| Subagent | 不用——计划需完整上下文，拆开会失一致 |
| 输入物 | Task Card + 相关模块 README + 规范文件 |
| 输出物 | task.md 中补全执行计划（步骤表 + 依赖图 + target_hours） |
| Gate | 无（计划阶段不做门禁） |

**执行计划格式**：

```markdown
| # | 步骤 | 负责方 | 产物 | 状态 |
|---|------|--------|------|------|
| 1 | 资料摘要 | 头孢 | 资料摘要.md | pending |
| 2 | 设计方案 | 青霉素 | 设计方案.md | pending |
| 3 | 方案评审 | 阿莫西林 | 评审记录 | blocked_by:2 |
```

### Step 3 · 工作执行

| 维度 | 内容 |
|------|------|
| 主责 | 青霉素（大块产出）或红霉素（代码/治理） |
| 辅助 | Claudian 并行执行批量技术任务 |
| Subagent | 核心场景——Fan-Out / Agent Pool 并行生成多产物 |
| 输入物 | 执行计划 + 资料摘要 + 规范模板 |
| 输出物 | PRD / 原型 / 脚本 / 配置（带 frontmatter） |
| Gate | `pre-write`：路径/格式/品牌/scope 校验 |

**产出物标准结构**（以 PRD 为例）：
1. 业务流程（泳道图）→ 2. 角色权限矩阵 → 3. 用户故事表 → 4. 功能说明（7 段式：菜单路径/原型图/功能说明/数据说明/交互说明/导入导出/异常场景）→ 5. 接口需求 → 6. 变更日志

### Step 4 · 执行监控

| 维度 | 内容 |
|------|------|
| 主责 | 阿莫西林周期性检查进度和状态表 |
| 辅助 | GBrain 扫描异常、不死鸟自愈、V9 第一反射器定时巡检 |
| Subagent | 不用——监控需全局视图 |
| 输入物 | 状态表 + 事件流 + heartbeat + task card + 规范管辖权索引 |
| 输出物 | `health-latest.json` + 异常日志 + 状态表更新 |
| Gate | 无（监控是被动层） |

**监控指标**：heartbeat 是否过期（>120s）、子任务是否超时、成本是否达阈值、`sources_failed` 是否为空。

**健康判定口径**：会话启动时读取 `02-项目管理/巡检/health-latest.json`。`summary.active=0` 只表示没有新增待上报项；必须同时满足 `sources_failed=[]`，才表示反射器八源都已运行且当前健康。若 `active=0` 但 `sources_failed` 非空，视为"假静默"：不是没事，而是有巡检源没看全。

### Step 5 · 交付物检核

| 维度 | 内容 |
|------|------|
| 主责 | 头孢主导审核 |
| Subagent | 推荐 Fan-Out——品牌/规范/字段三项互不依赖，可并行 |
| 输入物 | Step 3 产出物 + 规范文件 |
| 输出物 | 检核意见（通过 / 打回 + 问题清单） |
| Gate | 品牌合规 + frontmatter 完整 + 路径正确 |

**三项审核检查清单**：
- 品牌：品牌用词 / 色值(#861B2F) / 编码规则 / 按钮数量
- 规范：frontmatter 必填 / 章节骨架完整 / 字段表格式
- 字段：数据来源标注 / 类型用业务语言 / 业务规则列非空

### Step 6 · 测试验收

| 维度 | 内容 |
|------|------|
| 主责 | 头孢 + 阿莫西林 |
| Subagent | 可选 Inline：逐项验证 |
| 输入物 | 检核通过的产物 + 验收标准 |
| 输出物 | 验收报告 + retrospective（可选） |
| Gate | 功能正确性 + 交付物状态从 submitted → verified；任务验收状态由 submitted → accepted |

**验收后动作**：
- 通过 → deliverable state = `verified` → 看板更新 → Handoff
- 打回 → deliverable state = `rejected` → resubmit_count++ → 回到 Step 3

**任务验收状态机**：
- `status: done` 只表示 Agent 执行收工，不等于用户验收。
- `review_status: submitted` 表示已提交 reviewer。
- `review_status: accepted` 必须由 `accepted_by != owner/author` 的验收方确认。
- accepted 转移使用 `v9_accept <task_id> <accepted_by>`；不得裸手改 `review_status: accepted`。
- M5 或显式 `handoff_required: true` 的任务，收工前必须有可接手 Handoff：status、产物、验证结果、next action。

## 9 · 五级错误升级链

```
子 Agent / 任务失败
  │
  ├─ L0.5  父 Agent 重试 / 换模型 / 拆更细 / 回收自做（≤2 次）
  │        ↓ 重试耗尽
  ├─ L1    不死鸟 Phoenix 自动自愈（抗体扫描 + 已知错误匹配）
  │        ↓ 无匹配抗体
  ├─ L2    Owner Agent 修复（出错的 Agent 自己修）
  │        ↓ 修不了
  ├─ L3    阿莫西林裁决（综合上下文 + 跨模块判断）
  │        ↓ 裁决无解
  └─ L4    人工Reviewer拍板（人力介入）

中间层：WorkBuddy 监听
  - 任何原子 Agent 状态变成 error → WorkBuddy 收到信号
  - WorkBuddy 诊断 → 尝试修复 → 成功则重置 idle → 失败则升级 L3
```

### 回滚补偿策略

```
任务失败 / 产物有误
  ├─ 无产出 → 无需回滚，直接重做
  ├─ 产出不完整 → 删除残缺文件 → 重做
  ├─ 内容错误但结构完整 → 就地修复（Edit）
  ├─ 影响了其他文件 → 级联修复
  └─ 写到错误位置 → mv 到正确路径
```

**回滚铁律**：
1. 先备份再删除
2. 批量保留已完成的部分
3. 跨文件修改原子化
4. 禁区写入零容忍

## 9.5 · 外部 Agent 接入协议

> 不在六原子列表内的 Agent 如何安全接入息壤体系。

### 9.5.1 外部 Agent 定义

不满足以下**任一条件**即为「外部 Agent」：
- 不在六原子列表
- 无 CLI 接口
- 无 Vault 持久访问
- 跨会话无记忆

### 9.5.2 四条最低要求

| # | 要求 | 说明 |
|---|------|------|
| 1 | CLAUDE.md 前置声明 | system prompt 第一段必须是铁律摘要（≤20 行） |
| 2 | 路径白名单 | 默认仅写 `_temp/cowork-handoff/{task-id}/` |
| 3 | 三检义务 | 写入后自查：无 emoji、frontmatter 齐全、品牌色合规 |
| 4 | 事后补办 | 留 YAML 补办清单 `_temp/cowork-handoff/{task-id}.md` |

### 9.5.3 启动注入文本

发起人把以下文本作为外部 Agent prompt 第一段注入：

```
[铁律] 本任务适用 V9 外部 Agent 接入协议，task_id={task-id}。
你只能写入 _temp/cowork-handoff/{task-id}/，不得直接写正式路径。
写入后必须自查：无 emoji、frontmatter 齐全、品牌色合规、路径未越权。
完成后必须提交 _temp/cowork-handoff/{task-id}.md 作为 YAML 补办清单。
产物在阿莫西林验收前均视为未验收。
```

### 9.5.4 YAML 补办清单格式

```yaml
---
task_id: T-YYYYMMDD-NN
agent: Cowork
status: submitted
temp_root: _temp/cowork-handoff/{task-id}/
deliverables: []
self_check:
  no_emoji: unknown
  frontmatter_ok: unknown
  brand_color_ok: unknown
  path_whitelist_ok: unknown
openclaw_review:
  required: true
  status: pending
---
```

### 9.5.5 信任边界

| 外部 Agent 可做 | 外部 Agent 不可做 |
|------|------|
| 暂存区创建/修改文件 | 直接写 00-MOC/ / 30-规范/ / 40-决策/ |
| 声明待审项 | 自行验收并移动产物到正式路径 |
| 申请豁免（用户授权 + ≤5 文件） | 无授权时自行豁免 |

### 9.5.6 责任边界

| 角色 | 责任 |
|------|------|
| 发起人 | 创建 task card、注入铁律、指定暂存区和验收人 |
| 外部 Agent | 按白名单写暂存区、三检、提交补办清单 |
| 阿莫西林 | 验收产物、pre-write-check、补 Handoff、移正式路径 |
| 人工Reviewer | 豁免直接写正式路径、跨模块任务最终拍板 |

### 9.5.7 兜底机制

外部产物视为「未验收」→ 阿莫西林 cron 扫描 `_temp/cowork-handoff/` → pre-write-check → 补 Handoff → 移正式路径。超 7 天未处理则告警。

未注入铁律的外部 Agent 产物降级为「待补登记」，不得直接标 done。

## 11 · Gate 与 Hook 强制机制

> 即使 Agent 忘记合规流程，硬件门禁也会拦截。

### 11.1 架构

```
Agent 写文件操作
  │
  ▼
┌──────────────────────┐
│  pre-write-hook.sh   │  ← Claudian PreToolUse 自动触发
│  (Layer 0+1)         │
├──────────────────────┤
│  gate-enforce.py     │  ← Hook 内部调用
│  (P0 硬阻断 / P1-P3) │
└──────────────────────┘
  │
  ▼ 通过 → 允许写入
  ✗ 阻断 → 返回错误信息
```

### 11.2 gate-enforce.py v1.1.0 规则

| 规则 ID | 优先级 | 触发条件 |
|---------|:------:|---------|
| AGENT_BUSY | P0 | Agent 已 busy 时再次激活 |
| TASK_BLOCKED | P0 | 任务 blocked_by 非空 |
| NO_TASK_ID | P0 | spawn 时无 task_id |
| FUSE_BLOWN | P0 | 成本达上限 |
| SCOPE_EXCEEDED | P0 | 文件路径不在 write_scope 内 |
| ACCEPTED_BY_SELF | P0 | 任务卡 accepted 候选中 `accepted_by == owner/author` |
| STALE_EVAL | P0 | harness 类验收使用旧 eval 报告或 hash/mtime 不匹配 |
| PATH_FORBIDDEN | P0 | 写入禁止目录 |
| MISSING_DELIVERABLES | P0 | 收工缺产物 |
| **WRITE_WITHOUT_V9_PREFIX** | **P1** | **无 task_id 写非豁免路径（V9 新增）** |
| BUDGET_WARNING | P1 | 预算已用 60%+ |
| FRONTMATTER_MISSING | P1 | 产物缺 frontmatter |
| EMOJI_DETECTED | P2 | 检测到装饰性 emoji |
| BRAND_COLOR | P3 | 品牌色不合规 |

### 11.3 V9 豁免路径

以下路径在无 task_id 时不触发 WRITE_WITHOUT_V9_PREFIX：
- `02-项目管理/运行日志/` — M3 收工日志
- `02-项目管理/智能体状态/` — heartbeat 更新

### 11.4 Hook 层级

```
Layer 0:   不可篡改路径（task-card.yaml 只允许 Bash 创建）
Layer 0.6: 任务卡 accepted 转移候选解析（Write.content / Edit 重建全文）
Layer 1A:  禁止路径硬拦截（非 busy 时阻断）
Layer 1B:  任务卡授权验证 + gate-enforce（busy 时完整门禁）
```

白名单（永远放行）：`_temp/`、`02-项目管理/运行日志/`、`.obsidian/`

### 11.5 调用方式

```bash
python3 .standards/gate-enforce.py pre-write \
  --file "10-项目/示例项目/file.md" \
  --task-id "T-20260528-01" \
  --write-scope "10-项目/示例项目/" \
  --json
# exit 0 = 通过  |  exit 1 = P0 硬阻断  |  exit 2 = 参数错误

python3 .standards/gate-enforce.py pre-accept \
  --task-id "T-20260627-46" \
  --require-fresh-eval \
  --eval-report "02-项目管理/巡检/harness-eval-latest.json" \
  --json
```

任务卡验收正门：

```bash
source .standards/v8-handshake.sh
v9_accept T-YYYYMMDD-NN 人工Reviewer --json
```

`v9_accept` 的顺序固定：读旧卡 → 生成 accepted 候选 → `pre-accept` 校验 → 原子写回。Agent 不得通过普通 Write/Edit 裸改 `review_status: accepted`。

### 11.6 第一反射器：常驻巡检与自省

Gate/Hook 负责"写入前拦截"，第一反射器负责"写入后评估"。它不替代门禁，也不直接修改正式看板；它只把系统健康信号写入隔离目录，供会话启动 checklist 解读。

| 项 | 规则 |
|------|------|
| 常驻服务 | macOS launchd `com.xirang.v9reflex`，每日 09:17 运行 |
| 聚合脚本 | `02-项目管理/脚本/v9-reflex-check.py` |
| 唯一输出区 | `02-项目管理/巡检/` |
| 最新快照 | `health-latest.json` |
| 冷却状态 | `reflex-state.json` |
| 防污染边界 | 自动化只写巡检目录，不自动写看板、运行日志、模块文档 |

八个巡检源：

| source | 来源 | 作用 |
|------|------|------|
| `project-ops` | `project-ops-check.py --json` | 任务卡、运行日志、完成状态一致性 |
| `agent-state` | `agent-state-lint.py --json` | Agent 状态 schema |
| `heartbeat` | 内置检查 | busy 但心跳超阈值 |
| `policy-conflict` | `v9-policy-conflict-check.py --json` | 规范管辖权冲突扫描 |
| `starter-leak` | `v9-starter-leak-check.py --json` | 对外 starter 泄漏扫描 |
| `task-state` | `v9-task-state-check.py --json` | 任务验收状态扫描 |
| `scope-tamper` | `v9-scope-tamper-check.py --json` | write_scope Bash 旁路扩权事后扫描 |
| `handoff` | `v9-handoff-check.py --json` | Handoff 可接手性扫描 |

快照必须包含自省字段：

```json
{
  "sources_run": [
    {"source": "heartbeat", "status": "ok", "findings": 0}
  ],
  "sources_ok": 8,
  "sources_failed": []
}
```

`heartbeat=ok(0)` 的含义是"跑了且干净"，不能与"没跑"混淆。会话启动 checklist 的健康判断必须同时看两个数：

1. `summary.active`：有没有新的待上报异常。
2. `sources_failed`：反射器是否真的把每个源都看过。

只有 `summary.active=0` 且 `sources_failed=[]` 才是真静默。`sources_failed` 非空时，即使 `active=0`，也必须先修巡检源。

### 11.7 Harness 回归测试与自证

V9.4 以后，harness 工具本身必须可测试。测试目标不是评价 Agent 产出质量，而是证明门禁、巡检、状态机、分发扫描这些机械规则能拒绝已知坏样本。

| 规则 | 含义 |
|------|------|
| positive/negative 分账 | 报告必须同时展示干净样本通过数和坏样本拦截数 |
| 先坏样本 | 新门禁先写 negative fixture，再实现转绿 |
| 临时 fixture | eval 样本写系统临时目录，不污染正式 Vault |
| 新鲜度校验 | harness 类任务 accepted 前，eval 报告必须覆盖当前脚本 hash/mtime |
| 绿灯无感 | pre-commit 只在 staged 文件触达 `.standards/` 或 `02-项目管理/脚本/` 时触发 |

当前命令：

```bash
python3 02-项目管理/脚本/v9-harness-eval-runner.py
python3 02-项目管理/脚本/v9-harness-eval-runner.py --write-latest
```

验收读法：`passed` 只是表面；更关键的是 `positive` 和 `negative_blocked` 两个分账。 如果 negative 数为 0，即使全绿也不得上线。

### 11.8 任务验收状态机与 Handoff

V9 将“执行完成”和“验收通过”拆成两条状态：

| 字段 | 含义 |
|------|------|
| `status` | Agent 执行状态：ready/in_progress/done/blocked/cancelled |
| `review_status` | 验收状态：draft/submitted/reviewing/changes_requested/accepted/rejected/not_required |

硬规则：

1. `status: done` 不等于 `review_status: accepted`。
2. `review_status: accepted` 必须有 `accepted_by`、`accepted_at`、`acceptance_result: accepted`。
3. `accepted_by` 不得等于 `owner` 或 `author`。
4. 2026-06-27 起的新卡，`submitted` / `reviewing` / `changes_requested` / `rejected` / `accepted` 必须有 `submitted_at`。
5. `changes_requested` 必须有 `acceptance_result: changes_requested` 和可执行 `acceptance_note`。
6. accepted 转移必须走 `v9_accept` 或同等候选校验路径。
7. M5 或显式 `handoff_required: true` 的 done 任务必须有可接手 Handoff。

Handoff 最小可接手字段：

| 字段 | 目的 |
|------|------|
| status | 让接手方知道当前状态 |
| 产物路径/产物清单 | 让接手方能找到结果 |
| 验证结果/自查结果 | 让接手方知道是否可信 |
| next action | 让接手方知道下一步做什么 |

只读检查：

```bash
python3 02-项目管理/脚本/v9-task-state-check.py --json
python3 02-项目管理/脚本/v9-handoff-check.py --json
```

## 13 · 成本治理

> 多 Agent 并行 + Subagent spawn 场景下，token 消耗可在数分钟内失控。
> V9.4.3 口径：真实 usage token 可通过事件流记录；真实平台 CNY 账单尚未接入。没有 `billing_status=connected` 且带平台 `cost_source` 的事件，`cost_cny` 只能视为估算/自报，不得当账单金额。

### 13.1 治理优先级

**结构性节省 > 脚本化门禁 > 事后审计 > 事前硬熔断**

| 层 | 决策问题 | 手段 |
|---|---|---|
| 结构层 | 做不做 / 谁做 / 多大粒度 | 路由、分级、外部 Agent 轻接入 |
| 执行层 | 怎么算 / 怎么拦 / 怎么复盘 | 成本事件流、cost-fuse、周报 |

### 13.2 预算分级

| 级别 | 场景 | token 上限 | 成本上限(CNY) |
|------|------|:--:|:--:|
| S | 格式修复、状态更新 | 100K | 0.5 |
| M | PRD 产出、资料采集 | 500K | 5.0 |
| L | 全模块重构、方法论重写 | 2M | 20.0 |
| XL | 需阿莫西林审批 | 5M | 50.0 |

### 13.3 熔断规则

| 阈值 | 状态 | 动作 |
|:---:|------|------|
| <60% | green | 正常执行 |
| 60-99% | warning | 降级轻量模型（P1 advisory） |
| 100% | blown | 停止子 Agent + 通知人工Reviewer（P0 硬阻断） |

### 13.4 成本事件流

所有成本记录统一写入 `02-项目管理/agent-cost-events.jsonl`：

```bash
python3 .standards/agent-cost-events.py append \
  --task-id T-20260528-01 \
  --agent claudian \
  --model sonnet-4 \
  --tokens 15000 \
  --cost-cny 0.12 \
  --phase execution \
  --source runtime
```

Phase 枚举：`routing` / `context` / `execution` / `review` / `handoff` / `retry`

`cost_cny` 的语义是本阶段治理口径下的增量估算/自报金额。真实计费接入前，成本周报必须显式输出：

```json
{
  "billing_status": "usage_only | estimated | connected",
  "billing_note": "明确说明 usage token 与 CNY 账单是否已接真实来源"
}
```

V9.4.3 起，`agent-cost-events.py append` 支持 `--input-tokens` / `--output-tokens` / `--usage-source` / `--billing-status` / `--cost-source`。`billing_status=usage_only` 只表示 token 来自模型 usage 字段；`billing_status=connected` 必须提供平台成本来源，否则事件校验拒绝。

核心原则：
- **生命周期事件与成本事件分离** — `task_end` 的 tokens/cost 固定填 0
- **真实成本统一入口** — 全部通过 `agent-cost-events.py append` 写入
- **事件流 append-only** — 不修改已写入事件

### 13.5 模型选择原则

- 默认 DeepSeek（¥1/百万 token）
- 复杂设计/长上下文 → Claude Opus（¥4-12/百万 token）
- 嵌入 → bge-m3 本地免费
- 切高价模型须说明理由

### 13.6 周降级策略

| 触发条件 | 动作 |
|---------|------|
| 周成本达 80%（¥160） | 后续任务默认 S 级 |
| 周成本达 100%（¥200） | 禁止 spawn；强制 DeepSeek |
| 周成本达 150%（¥300） | 仅阿莫西林可操作，其余暂停 |

### 13.7 可观测性

```bash
python3 .standards/v8-cost-observability.py --days 7 --json  # 成本周报
python3 .standards/v8-health-metrics.py                     # 健康指标
python3 .standards/event-rotate.py rotate --days 7          # 事件归档
```

### 16.3 运行时激活契约

> 文档存在不等于方法启用。V8 入口测试的教训：协议写在文档里，但 Agent 实际行为中没有触发拆分、路由、汇报、升级。

#### 未激活的 7 个信号

当某个 Agent 以 V9 名义接收任务，但未触发以下行为，判定为「V9 未激活」：

| 应触发行为 | 未激活信号 |
|------|------|
| 写入声明 | 写了文件但无 `V9 写入声明` 或 `V9 已激活` |
| 建立或绑定 task card | 任务只存在于对话里，无 task_id |
| 写入自身状态 | 状态文件仍为 idle，current_task 为空 |
| 追加事件流 | 无 task_start / task_end 事件 |
| 路由其他 Agent | 明显超出自身职责仍单体硬做 |
| 主动汇报进度 | 长任务无 heartbeat |
| 卡死升级 | stalled 后无 error 事件、无升级动作 |

#### 三层激活

每个入口平台必须完成三层，缺一不可：

| 层 | 目的 | 最低实现 | 效果 |
|------|------|------|------|
| Prompt 激活 | 让 Agent 知道 V9 | 启动文件含 V9 合规块 | 提醒型（可能被忽略） |
| Tool 激活 | 让 Agent 能执行 V9 | 可调用 handshake / gate / event | 执行型（有能力做） |
| Watchdog 激活 | 让 Agent 卡住时被发现 | heartbeat 过期自动升级 | 阻断型（强制做） |

只完成 Prompt 激活 = 仍是「提醒型规则」；Tool + Watchdog 后才进入「阻断型运行系统」。

#### 各入口验收问题

| 入口 | 验收问题 |
|------|------|
| Claudian | 从 `.claude/CLAUDE.md` 进入时，是否亮灯打点并执行门禁？ |
| 阿莫西林 | 从用户消息进入时，能否自动建卡、拆分、路由、汇报？ |
| 头孢 | 从 SOUL / cron / CLI 进入时，是否写状态、事件和 Handoff？ |
| 红霉素 | 从本地任务进入时，是否对齐 task card 和门禁？ |
| 外部 Agent | 只读 prompt 注入时，是否被限制在暂存区并提交补办清单？ |

任一入口未通过验收，不得宣称"V9 已在该入口启用"。只能宣称「V9 文档存在」或「协议层可用」。

#### P1 修复方向（入口未激活时）

1. 先补 Runtime Adapter：入口脚本、task card 绑定、状态写回、事件流
2. 再补 Watchdog：heartbeat 过期、session stalled 时自动升级
