# V9.5 月度迭代 Ops 方案

> 一句话目标：以示例项目 EXAMPLE 月度迭代为主战场，把 V9 从任务级反射器推进到迭代级 AgentOps。先让迭代记忆可读、可查、可拦、可复盘，再谈完整工具注册表和真实成本。

## 0. 边界声明

本文起草时是 V9.5 第一阶段方案；经后续“继续”推进，已进入试点实施：新增只读 `v9-iteration-ops-check.py`，并将 `iteration-ops` 接入第一反射器；新增 `v9-status-summary.py` 作为 Obsidian 插件/桌面端之前的稳定状态聚合接口，并加入 latest 新鲜度检查，过期 health/eval 不得显示 green；`status-latest.json` 已冻结为 `schema_version=v1` 契约，包含 `paths`、`ui.badges`、`ui.actions` 和 schema contract eval；`review.md` 晋升闭环已落为迭代 review 模板与 eval 规则；preview gate 已增加入口空白/空壳页的静态渲染信号检查；双时间字段已在当前控制面文件上机械化；`agent_assignments` 已升级为角色/owner/responsibility/status/fallback 结构检查，不可用角色缺 fallback 时给出 advisory；`valid_for / iteration_root / baseline_root` 已作为 Memory Contract 锚点进入只读校验，`valid_from/valid_until/supersedes` 的时间顺序与引用存在性已进入元数据完整性检查和 eval；智能体写入边界已加入默认写区、基线例外、manifest 和封版保护契约检查；封版归集清单已加入归集目标、原则、台账列和完成条件契约检查；材料迁移 manifest 已加入先登记、台账列、引用更新和搬迁后检查契约检查；遗留项台账已成为第 7 个迭代管理控制面文件，并加入台账列、超期规则与 review 闭环契约检查；review 已加入遗留项回填与状态晋升建议回填章节，要求连接遗留项台账、`close_decision` 与 `SCOPE_STATUS_ADVANCE_AVAILABLE` 人工拍板；`scope_status` 状态机、状态转换证据、晋升建议、review 接受后的反写一致性与冻结后新增范围项检查已落为规则和 eval，scoped/released/reviewed 均已有专项正反样本；review 决定进入 checker/eval 时必须同步 `eval_status` 与 Eval 回填 done 行，决定进入 V9 正文时必须同步 eval done、规则晋升候选 done 证据，并要求 checker/eval 在同一 review 中同步接受且 done，决定进入 skill/runbook 时必须同步 Skill 回填新增项 done 行，均已落为一致性规则和 eval；基线区 git 变更的封版授权检查已落为只读 P1 规则和 eval；跨迭代遗留超过 2 轮的风险提示已落为 advisory 规则和 eval。仍不修改 V9 正文、starter 或门禁脚本。

用户可见语言约束已进入真实 prompt 源 `.prompt-src/prompt-base.md`，并通过 `prompt-build.py --apply / --apply-block / --verify` 下发到 Codex、Claude agents、Claude.md、Hermes、OpenClaw 等实际约束文件；`30-规范/智能体约束/` 仅作为映射快照，不作为约束真源。状态面板插件和 `status-latest.json` UI label 已中文化：用户可见的标题、按钮、提示、报错、状态摘要默认中文，机器字段和 schema key 保留英文。

经对照 LifeOS 开源版 `$HOME/Downloads/obsidian-lifeos-main`，插件定位已从“状态探针”升级为 `V9 Workbench`，完整产品路线见 [[50-经验/Agent协作方法论/V9-Workbench综合插件方案-2026-06-27]]：注册 Obsidian 侧栏 View，只读聚合 `status-latest.json`、`10-项目/` 和迭代工作台，已实现项目进展、Agent 编排、任务/待办、日历提醒、笔记状态监控、近 35 天修改热力图和 AI 上下文入口。当前版本仍不接真实模型、不写 Vault、不运行巡检脚本。

本阶段只做三类事：

1. 承认并制度化现有示例项目 EXAMPLE 月度迭代结构。
2. 定义 Iteration Memory Contract 和只读检查规则。
3. 给后续 `v9-iteration-ops-check.py`、flyfish preview gate、review 晋升闭环排实施顺序。

不做：

1. 不另造 `IterationOps/` 或新项目根目录。
2. 不把所有 Agent 工程概念一次性写进 V9 正文。
3. 不在未验证前把新规则接成硬门禁。
4. 不碰当前工作区里与本方案无关的脏改动。
5. 不把截图、巡检快照、运行日志、临时预览证据等过程文件写入 Vault；Vault 只保存成果文件、索引、方案和管理事实。

运行态输出默认放在 Vault 外：

```text
~/Desktop/沙箱/v9-runtime/
```

可用 `XIRANG_V9_RUNTIME_DIR` 或 `XIRANG_V9_INSPECT_DIR` 覆盖。

## 1. 现有目录结构承认

V9.5 不新造地基。当前 `10-项目/` 已经形成月度迭代治理的基本结构：

| 现有入口 | V9.5 定位 | 说明 |
|---|---|---|
| `10-项目/README.md` | 项目级当前 View | 声明当前基线、当前迭代和操作入口 |
| `10-项目/基线/` | 稳定事实 View | 保存已封版的当前稳定事实源 |
| `10-项目/迭代/260725迭代/` | 当前迭代 Ledger | 保存 260725 迭代工作稿、需求清单、模块稿、过程记录 |
| `10-项目/迭代/260725迭代/迭代管理/README.md` | 迭代工作台 | 汇总范围状态、基建入口、工作规则 |
| `260725-需求范围划定草案.md` | Scope Ledger | 记录本月范围来源、裁剪和确认过程 |
| `260725-模块变更台账.md` | Change Ledger | 记录模块级变化、影响面和状态 |
| `260725-材料迁移manifest.md` | Movement Ledger | 记录跨目录材料搬迁和来源去向 |
| `260725-封版归集清单.md` | Release View | 记录哪些迭代产物准备吸收到基线 |
| `260725-遗留项台账.md` | Carryover Ledger | 记录跨迭代遗留项、连续遗留次数和关闭/拆分/升级决定 |
| `260725-智能体写入边界.md` | Policy | 定义 Agent 默认读写区和禁止动作 |

V9.5 的目录原则：

1. `10-项目/README.md` 是当前迭代解析入口。
2. `基线/` 是稳定事实源，不是普通任务工作区。
3. `迭代/{迭代号}迭代/` 是当前过程记忆，不复制完整基线树。
4. `迭代管理/` 是本迭代的机器可读控制面。
5. 封版前，Agent 默认只能写迭代区；只有封版归集任务可以写基线。

## 2. Iteration Memory Contract

Iteration Memory Contract 是 V9.5 的 P0。它把月度迭代里的事实、状态、边界和复盘统一成机器可读协议。

### 2.1 三层记忆

| 层 | 内容 | 当前对应 |
|---|---|---|
| Ledger | 原始过程账本，不轻易重写 | 需求范围草案、模块变更台账、材料迁移 manifest、模块工作稿 |
| View | 从 Ledger 派生的当前视图 | 项目 README、迭代工作台、封版归集清单、模块基线索引 |
| Policy | 控制读写和晋升的规则 | 智能体写入边界、V9 Gate/Hook、HITL 拍板清单 |

规则：

1. Agent 读取当前事实时，优先读取 View，再追溯 Ledger。
2. Agent 写入新工作时，默认写 Ledger。
3. Agent 改写稳定事实时，必须走 Policy 和封版归集。
4. `review.md` 只负责复盘和晋升建议，不能绕过 eval 直接改规则。

### 2.2 推荐 frontmatter

迭代管理文件、关键模块工作稿和复盘文件应逐步补齐以下字段。第一阶段只定义方案，不批量改历史文件。

```yaml
project: 示例项目EXAMPLE
iteration: "260725"
iteration_root: "10-项目/迭代/260725迭代"
baseline_root: "10-项目/基线"
status: draft
scope_status: planning
valid_for: "260725"
observed_at: "2026-06-27T09:00:00+08:00"
recorded_at: "2026-06-27T09:10:00+08:00"
valid_from: "2026-06-25"
valid_until: null
supersedes: null
carryover_to: null
owner: Codex
reviewer: 用户
```

字段约定：

| 字段 | 说明 |
|---|---|
| `project` | 项目名，当前为 `示例项目EXAMPLE` |
| `iteration` | 迭代号，必须用字符串，避免前导零或日期样式被解析错 |
| `iteration_root` | 当前迭代根目录 |
| `baseline_root` | 当前基线根目录 |
| `status` | 文件自身状态，如 `draft / active / released / archived` |
| `scope_status` | 迭代范围状态，如 `planning / scoped / frozen / released / reviewed / aborted` |
| `valid_for` | 本结论服务的迭代或时间窗 |
| `observed_at` | 事实发生或被观察的时间 |
| `recorded_at` | 写入 Vault 的时间 |
| `valid_from` / `valid_until` | 结论有效期 |
| `supersedes` | 替代的旧结论或旧文件 |
| `carryover_to` | 未完成事项带到哪个后续迭代 |

路径锚点约定：`iteration_root` 与 `baseline_root` 优先写 vault 内相对路径，保证成果文件可迁移；checker 必须兼容相对路径和绝对 `--project-root` 调用，不能要求成果文件改写为本机绝对路径。

### 2.3 双时间字段

V9.5 必须区分事实时间和写入时间：

| 字段 | 解决的问题 |
|---|---|
| `observed_at` | 防止 Agent 把旧观察当作新事实 |
| `recorded_at` | 防止 Agent 不知道某条记忆何时进入 Vault |

判定原则：

1. 同一事实冲突时，优先看 `valid_for` 是否匹配当前迭代。
2. `valid_for` 匹配时，再比较 `observed_at`。
3. `recorded_at` 只说明记录新旧，不自动代表事实更新。
4. 无双时间字段的旧文档可读，但不能直接作为覆盖当前迭代的强事实。

## 3. agent_assignments

V9.5 不要求把多 Agent 编排写死进 V9 核心。每个迭代声明自己的职责映射即可。

推荐放置位置：

1. `10-项目/迭代/{迭代号}迭代/迭代管理/README.md`
2. 或独立迭代卡，例如 `迭代管理/{迭代号}-agent-assignments.md`

推荐结构：

```yaml
agent_assignments:
  scope_definition:
    owner: 爪爪
    responsibility: 需求范围划定、范围冻结建议
    status: active
  prd_and_prototype:
    owner: 小虫
    responsibility: PRD 工作稿、原型说明、视觉交付入口
    status: active
  code_implementation:
    owner: 咬咬
    responsibility: 代码实现、验证记录、技术风险回填
    status: unavailable
    fallback: Codex
  research_and_data:
    owner: 喷水娃
    responsibility: 外部资料采集、证据索引、材料 manifest
    status: active
  iteration_coord:
    owner: WorkBuddy
    responsibility: 迭代节奏、交接、冲突发现、月末复盘组织
    status: active
  v9_harness_review:
    owner: Codex
    responsibility: V9 规则、只读检查、eval、反射器接入建议
    status: active
```

规则：

1. `agent_assignments` 是迭代契约，不是永久组织架构。
2. 每个职责至少有 owner 和 responsibility；`status` 推荐显式写 `active / unavailable / paused / blocked`。
3. 当某个关键职责显式不可用时，必须写 `fallback`，否则 `v9-iteration-ops-check.py` 给出 advisory。
4. 涉及封版、改规则、接账号、部署常驻、验收 accepted 的动作仍走 HITL。
5. 未声明 owner 的关键职责，`v9-iteration-ops-check.py` 首版只 advisory，不硬拦。

### 4.2 首批规则

| 规则 ID | 触发条件 | 首版等级 | 后续方向 |
|---|---|---:|---|
| `ITERATION_ENTRY_MISSING` | `10-项目/README.md` 指向的当前迭代目录不存在 | p1 | 保持硬异常 |
| `ITERATION_MANAGEMENT_DOC_MISSING` | README、范围草案、变更台账、manifest、封版清单、写入边界、遗留项台账缺任一 | p1 | 保持硬异常 |
| `ITERATION_FIELD_MISSING` | 当前迭代关键 markdown 缺 `iteration` 字段 | advisory | 观察后可升 p1 |
| `DOUBLE_TIME_MISSING` | 新增关键文件缺 `observed_at` 或 `recorded_at` | advisory | 新机制稳定后升 p1 |
| `BASELINE_WRITE_WITHOUT_RELEASE` | `10-项目/基线/` 存在 git 变更，但当前迭代未发布/复盘，或封版归集清单未声明 `baseline_write_authorized: true` | p1 | 已有只读检查与正反 eval；pre-write 硬拦后置 |
| `SCOPE_STATUS_TRANSITION_INCOMPLETE` | `scope_status=scoped/released/reviewed` 但缺对应确认时间或决策引用 | advisory | scoped/released/reviewed 均已有正反 eval；稳定后可按状态升 p1 |
| `SCOPE_STATUS_ADVANCE_AVAILABLE` | 当前状态已具备下一状态证据字段，但 `scope_status` 尚未晋升 | advisory | 已有 planning->scoped、frozen->released 样本；只提示人工确认，不自动改字段 |
| `ITERATION_REVIEW_SCOPE_ADVANCE_LOOP_INCOMPLETE` | review 的状态晋升建议回填缺规则 ID、当前状态、建议状态或接受/拒绝/延后决定 | advisory | 已有 negative eval；用于把 checker 建议交给人工拍板 |
| `SCOPE_STATUS_ACCEPTED_BUT_NOT_APPLIED` | review 已接受状态晋升，但迭代工作台 `scope_status` 尚未更新为建议状态 | advisory | 已有 negative eval；只提示人工反写，不自动改字段 |
| `REVIEW_ACCEPTED_RULE_WITHOUT_EVAL` | review 决定进入 checker/eval，但 `eval_status` 未完成或 Eval 回填缺 done 行 | advisory | 已有 negative eval；用于防止规则晋升绕过 eval |
| `REVIEW_DECISION_MATRIX_INCONSISTENT` | review 决定进入 V9 正文，但 checker/eval 未在同一 review 中同步接受且 done | advisory | 已有 negative eval；用于防止跨列晋升状态分裂 |
| `REVIEW_ACCEPTED_V9_BODY_WITHOUT_EVIDENCE` | review 决定进入 V9 正文，但缺 `eval_status=done`、Eval 回填 done 或规则晋升候选 done 记录 | advisory | 已有正反 eval；防止承重文本绕过证据链 |
| `REVIEW_ACCEPTED_SKILL_WITHOUT_WRITEBACK` | review 决定进入 skill/runbook，但 Skill 回填缺新增项 done 行 | advisory | 已有正反 eval；用于防止流程型经验只停留在口头决定 |
| `SCOPE_ADDED_AFTER_FREEZE` | `scope_status=frozen/released/reviewed` 后，纳入类范围项超过 `scope_included_count` 冻结基准 | p1 | 已有正反 eval，冻结时必须登记 `scope_frozen_at` 与 `scope_freeze_ref` |
| `CARRYOVER_LEDGER_CONTRACT_INCOMPLETE` | 遗留项台账缺台账列、`carryover_count` 规则、`close_decision` 或 review 晋升闭环 | advisory | 已有 negative eval；稳定后可升 p1 |
| `CARRYOVER_TOO_LONG` | `carryover_to` 存在、`carryover_count>2` 且状态未关闭 | advisory | 已有正反 eval；月末 review 后决定是否升级或拆分 |
| `ITERATION_REVIEW_CARRYOVER_LOOP_INCOMPLETE` | review 的遗留项回填缺台账链接、`close_decision` 或关闭/拆分/升级动作 | advisory | 已有 negative eval；用于闭合 review -> 遗留项台账 -> rule/eval/skill |
| `VISUAL_PREVIEW_MISSING` | HTML/原型/网页类产物无 preview 记录 | advisory | P1 接 flyfish 后升 p1 |
| `PROTOTYPE_COVERAGE_AUDIT_MISSING` | 已声明原型，但缺正式需求到原型的覆盖审计 | advisory | 入口可达不能替代需求覆盖证据 |
| `PROTOTYPE_COVERAGE_COUNTS_INVALID` | 覆盖数非整数/负数，或 `covered + partial + missing != total` | p1 | 防止覆盖口径失真 |
| `PROTOTYPE_REQUIREMENT_GAPS` | 正式需求中 `missing > 0` | p1 | 已有 42/22/12/8 负样本；不自动修改原型 |
| `PROTOTYPE_REQUIREMENT_PARTIAL` | 正式需求中 `partial > 0` | advisory | 提示字段、动作或状态闭环未完整 |
| `ITERATION_FACT_CHAIN_INCONSISTENT` | 工作台、范围核对、范围草案、模块台账、模块 README 或 Review 的范围/映射/原型事实不一致 | p1 | 已有一致链正样本和模块回填缺失负样本；防止只修仪表盘 |
| `REVIEW_MISSING_AFTER_RELEASE` | `released` 后 N 天仍无 review.md | advisory | 可配置 N，默认 7 天 |
| `AGENT_ASSIGNMENTS_MISSING` | 当前迭代无职责映射 | advisory | 等多人协作稳定后再升 |
| `AGENT_ASSIGNMENT_FALLBACK_MISSING` | 关键职责显式不可用但缺 fallback | advisory | 已有正反 eval；用于处理 Agent 临时不参与或阻塞的降级路径 |

### 4.3 绿灯无感、红灯硬拦

延续 V9.4 原则：

1. 绿灯无感：所有规则通过时，只更新巡检 JSON，不打扰普通任务。
2. 红灯硬拦：触及基线越权写入、封版前覆盖、冻结后偷偷扩范围时，必须 p1。
3. 先只读检查：脚本首版不改文件、不自动补字段、不自动搬迁。
4. 先 eval 后接反射器：没有 positive/negative fixture 前，不进硬门禁。

## 5. flyfish viewer preview gate

视觉产物的风险不是“有没有文件”，而是“是否真的能看、入口是否能交接、是否出现空白页”。V9.5 P1 把 flyfish viewer 纳入 preview gate。

### 5.1 适用范围

首批纳入：

1. HTML 原型。
2. 可浏览网页。
3. H5 / PC 静态页面。
4. 明确要求用户视觉验收的产物。

暂不纳入：

1. 普通 Markdown PRD。
2. drawio 源文件。
3. 无视觉验收要求的纯数据文件。

### 5.2 推荐元数据

```yaml
visual_artifact:
  type: html
  path: "10-项目/迭代/260725迭代/09-车间质检与超时预警/assistant-preview/index.html"
  preview_tool: "flyfish viewer"
  preview_status: checked
  checked_at: "2026-06-27T10:30:00+08:00"
  checked_by: Codex
  viewport:
    - desktop
    - mobile
  fallback: "local preview result + external/temp evidence, not stored in Vault"
prototype_coverage_status: partial
prototype_requirement_total: 42
prototype_covered_count: 22
prototype_partial_count: 12
prototype_missing_count: 8
prototype_coverage_checked_at: "2026-07-17T09:19:40+08:00"
prototype_coverage_ref: "260725-需求范围核对.md#7-原型覆盖审计2026-07-17"
```

### 5.3 Gate 规则

P1 首版规则：

1. Handoff 必须提供 preview 入口，或声明 `visual_preview: not_applicable`。
2. `v9-iteration-ops-check.py` 能发现视觉产物缺 preview 记录。
3. 缺 preview 先 advisory，连续复发或进入验收前升 p1。
4. flyfish viewer 检查失败时，必须记录阻塞原因；如需截图等过程证据，只能放在 Vault 外的沙箱或临时区，不进入成果文件管理区。
5. preview gate 只证明入口可交接；正式需求覆盖必须另行登记 `covered / partial / missing`，且三者之和等于正式需求总数。
6. `missing > 0` 时保持 P1；`partial > 0` 时保持 advisory。只有两者均为 0 才能声明 `prototype_coverage_status: complete`。

后续可增强：

1. 页面非空白检查。
2. 移动端/桌面端视口检查。
3. 控件重叠和溢出检查。
4. 与 review.md 中的视觉问题联动。

## 6. review.md 晋升闭环

月末复盘不能只是总结，它是 V9 自我进化入口。

### 6.1 推荐位置

优先位置：

```text
10-项目/迭代/{迭代号}迭代/迭代管理/{迭代号}-review.md
```

如果团队希望固定名，也可以在迭代管理目录放：

```text
10-项目/迭代/{迭代号}迭代/迭代管理/review.md
```

无论命名如何，frontmatter 必须有：

```yaml
project: 示例项目EXAMPLE
iteration: "260725"
type: iteration_review
valid_for: "260725"
observed_at: "2026-07-25T18:00:00+08:00"
recorded_at: "2026-07-25T20:00:00+08:00"
```

### 6.2 复盘分类

review.md 中的问题分三类：

| 类型 | 处理方式 |
|---|---|
| 一次性问题 | 记录原因和处置，不晋升规则 |
| 规律性问题 | 草拟规则补丁，进入 eval |
| 高风险边界问题 | 走 HITL，必要时先临时硬拦 |

### 6.3 晋升路径

```text
review.md 记录问题
  -> 分类：一次性 / 规律性 / 高风险
  -> 规律性问题草拟规则补丁
  -> 补 positive fixture 与 negative fixture
  -> 跑 v9-harness-eval-runner 或独立 iteration eval
  -> 通过后进入脚本、反射器或 skill
  -> 更新 V9 变更记录
  -> 必要时再写入 V9 正文或 starter
```

### 6.4 规则 / eval / skill 的分工

| 晋升目标 | 适用问题 |
|---|---|
| 规则 | 可以用确定性条件判断的问题，如缺字段、越权写基线 |
| eval | 需要证明新规则不会误伤历史正样本、能拦住坏样本的问题 |
| skill | 涉及复杂操作流程、文档生产规范、跨工具步骤的问题 |

硬约束：

1. Agent 可以提出晋升建议，但不能自行放松约束。
2. 任何从 review.md 晋升为硬拦的规则，必须先有 negative fixture。
3. 任何进入 starter 的规则，必须通过泄漏扫描和版本同步检查。
4. 任何涉及 accepted 语义、基线改写、账号接入、常驻部署的规则变更，必须 HITL。

## 7. status-latest v1 契约

`status-latest.json` 是 Obsidian 插件和桌面端之前的稳定读取面。它只由 `v9-status-summary.py --write-latest` 写入 Vault 外 runtime，不写入 Vault 成果区。

默认位置：

```text
~/Desktop/沙箱/v9-runtime/巡检/status-latest.json
```

可用 `XIRANG_V9_RUNTIME_DIR` 或 `XIRANG_V9_INSPECT_DIR` 覆盖。

### 7.1 顶层字段

| 字段 | 含义 |
|---|---|
| `schema_version` | 当前固定为 `v1`；UI 必须先判断版本 |
| `check` | 生产者，当前为 `v9-status-summary` |
| `generated_at` | 状态聚合生成时间 |
| `status` | 总状态：`green / yellow / red` |
| `current_iteration` | 当前迭代号 |
| `paths` | UI 可打开的稳定路径锚点 |
| `parts` | 三个来源的详细状态：`health / harness_eval / iteration_ops` |
| `ui` | UI 直接消费的 headline、badges 和 actions |

### 7.2 paths

`paths` 是 UI 跳转的唯一稳定入口。插件或桌面端不要自行拼路径。

| key | 指向 |
|---|---|
| `runtime_dir` | Vault 外巡检 runtime 目录 |
| `status_latest` | 当前状态聚合文件 |
| `health_latest` | 反射器 health latest |
| `harness_eval_latest` | harness eval latest |
| `repo_root` | Vault 根目录 |
| `project_root` | `10-项目` 根目录 |
| `iteration_root` | 当前迭代根目录 |
| `management_root` | 当前迭代管理目录 |
| `iteration_workbench` | 当前迭代工作台 README |

### 7.3 ui

`ui.badges` 固定为三类：

| id | label | target | detail_path |
|---|---|---|---|
| `health` | `Reflex` | `health_latest` | `parts.health` |
| `harness_eval` | `Eval` | `harness_eval_latest` | `parts.harness_eval` |
| `iteration_ops` | `Iteration` | `iteration_workbench` | `parts.iteration_ops` |

`ui.actions` 首版固定为四个打开动作：

| id | kind | target |
|---|---|---|
| `open_iteration_workbench` | `open_file` | `iteration_workbench` |
| `open_health_latest` | `open_file` | `health_latest` |
| `open_harness_eval_latest` | `open_file` | `harness_eval_latest` |
| `open_status_latest` | `open_file` | `status_latest` |

### 7.4 约束

1. UI 只展示和跳转，不直接改 V9 正文、基线或承重脚本。
2. `red` 可以触发醒目提示，`yellow` 只提示需要关注，`green` 默认无感。
3. `paths` 中的 key 比具体路径更稳定；UI 应存 key，不存绝对路径。
4. 修改 `schema_version=v1` 的字段形状前，必须先增加 eval 或升级到 `v2`。

## 10. 升级信号与文档 review

### 10.1 从场景协议升级到 OS 层的信号

V9.5 仍以示例项目 EXAMPLE 月度迭代为主战场。只有出现以下信号时，才把场景协议抽象成 V9 OS 层：

| 信号 | 升级动作 |
|---|---|
| 连续 2 个示例项目月度迭代保持 `iteration-ops=green` 且 advisory 噪声可解释 | 将 Iteration Memory Contract 晋升为 V9 正文候选 |
| 至少 2 个不同项目复用同一套 `迭代管理/README + 写入边界 + review` 控制面 | 抽象通用 IterationOps 模板 |
| `v9-iteration-ops-check.py` 中 70% 以上规则不再依赖示例项目专名 | 拆出项目无关 checker 核心 |
| `status-latest.json v1` 被 Obsidian 插件或桌面端稳定读取 1 个周期 | 冻结 UI contract，后续破坏性变更走 `v2` |
| 月末 review 连续产生可验证的 rule/eval/skill 晋升 | 将 review 晋升闭环写入 V9 正文 |

反向信号：如果规则需要大量项目专名、人工解释成本高、或月末 review 不能闭合，就继续留在场景协议，不急着抽象。

### 10.2 本文 review 周期

| 项 | 规则 |
|---|---|
| 有效窗口 | V9.5 试点期，至少覆盖 260725 一个完整月度迭代 |
| 常规 review | 每次月末 `{iteration}-review.md` 完成后同步检查本文 |
| 触发 review | 新增 p1 规则、`status-latest` schema 升级、插件/桌面端接入、跨项目复用时必须检查 |
| 过期判定 | 若连续 2 次 review 未更新且实际机制已变化，本文降为 historical，另开新方案 |
| 晋升路径 | 只把已通过 eval 且至少跑过一个真实迭代周期的机制写入 V9 正文 |
