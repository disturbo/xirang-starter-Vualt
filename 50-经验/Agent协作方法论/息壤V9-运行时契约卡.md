# 息壤 V9 运行时契约卡

> Agent 唯一加载物。所有规则浓缩于此，不需要记忆更多。

---

## 铁律 1：二元触发器

```
收到消息 → 「这个任务会写文件吗？」
  不写 → 直接回复（零合规开销）
  写   → pre-flight（声明 → 亮灯 → 执行）
```

没有第三种情况。

---

## 铁律 2：唯一违规定义

> **写了文件但没声明 = 违规。**

---

## 铁律 3：写入声明格式

| 场景 | 格式 |
|------|------|
| M3（单文件，<20min） | `V9 写入声明：{路径} \| {动作摘要}` |
| M4（多文件/交付物） | 完整 `V9 已激活：` 块 |
| M5（跨Agent/长任务） | M4 + 预算 + 拆分计划 |

---

## 铁律 4：豁免清单

以下操作免声明：
- 追加运行日志一行（M3 收工）
- heartbeat 更新（状态文件 last_heartbeat 字段）

其他任何文件写入都需声明。

---

## 铁律 5：灰区处理

| 信号 | 判定 |
|------|------|
| 有具体对象 + 明确产出物 | 写文件 → pre-flight |
| 咨询语气（"怎么推进"/"能不能做"）| 不写文件 → 直接回复 |
| 无法判定 | 问用户确认，1 轮内决定 |

---

## 铁律 6：不写文件的场景

1. 解释概念 / 纯问答
2. 讨论方案（未到执行）
3. 评审 / 核对但不落盘
4. 日常闲聊
5. 巡检无异常 / 状态查询

巡检状态查询只读 Vault 外运行态目录的 `health-latest.json`，默认位置为 `~/.xirang/v9-runtime/巡检/health-latest.json`，可用 `XIRANG_V9_RUNTIME_DIR` 或 `XIRANG_V9_INSPECT_DIR` 覆盖。运行态不得放在 macOS Desktop 受保护目录中，否则 launchd 可能无法写入。健康判定必须同时满足 `summary.active=0`、`sources_failed=[]` 与 `runtime_checks` 无 `failed/stale`；若任一条件不满足，不得报告“全绿”。当前反射器有九个治理源：project-ops / agent-state / heartbeat / policy-conflict / starter-leak / task-state / scope-tamper / handoff / iteration-ops；运行时自检不计入九源数量。

Harness 验收必须同时验证 trust set、`tested_hashes` 与当前文件 mtime；skill 多入口必须通过版本遮蔽检查。Phoenix 当前为 design/reference，无 scheduler/executor，不得计入运行能力或声称自动自愈。

---

## 铁律 7：执行中扩展

执行中发现要写更多文件 → 暂停、补充声明、再继续。
每次写入前自问：「我声明过要写这个文件吗？」

---

## 铁律 8：闲聊不是任务

闲聊不需要建卡，不需要声明，不需要收工。
`submitted` 不等于 `accepted`：未经验收方确认，不得声称"已验收"。

验收任务卡必须走 `v9_accept <task_id> <accepted_by>` 或同等候选校验路径；Agent 不得裸改 `review_status: accepted`，`accepted_by` 不得等于 `owner/author`。

M5 或显式 `handoff_required: true` 的 done 任务，必须有可接手 Handoff：status、产物、验证结果、next action。

2026-06-27 起的新任务卡，`review_status=submitted/reviewing/changes_requested/rejected/accepted` 必须写 `submitted_at`。`changes_requested` 必须写 `acceptance_note`，否则接手方无法行动。

---

## 铁律 9：starter 与成本口径

对外 starter 发布前必须跑：

```bash
python3 02-项目管理/脚本/v9-starter-leak-check.py --root <starter> --json --strict
```

成本事件可以记录真实 usage token；但 `billing_status=connected` 必须有平台 `cost_source`。没有平台成本来源时，`cost_cny` 只能是估算/自报，不得当账单。

Harness / gate / 巡检脚本改动后必须跑 `v9-harness-eval-runner.py`；看 `blocked_negative`，不能只看总通过数。

---

## 铁律 10：运行时不能假绿

> 脚本、plist、模型或数据库“存在”不等于机制正在运行；只认最近一次真实成功。

| 运行链 | 生效判据 | 失效阈值 |
|------|------|------|
| 第一反射器 | `com.xirang.v9reflex` 已加载，且 `health-latest.json` 持续刷新 | 快照超过 2 小时未更新 |
| GBrain CLI | 稳定源 0.33.0 可执行，且 `gbrain --version` 返回 `gbrain 0.33.0` | 命令缺失、包身份漂移、非零退出或超时 |
| 语义模型 | Ollama 可访问且 `bge-m3` 存在 | 模型探针失败 |
| GBrain sync | `maintenance-sync.json.status=success` | 超过 2 小时无成功记录 |
| GBrain dream | `maintenance-dream.json.status=success` | 超过 8 小时无成功记录 |
| Hermes One cron | `ticker_heartbeat` 持续刷新 | 超过 5 分钟无心跳 |
| 熵检测 v2 调度 | Hermes job `328aa7f7b498` 为 enabled、no-agent、周一 09:00，最近执行成功 | 任务缺失/暂停/漂移/最近执行失败 |
| 熵检测 v2 产物 | `entropy-shadow-state.json` 为 v2 shadow success，且最新影子报告存在 | 超过 216 小时无真实成功或无新报告 |

守护规则：

1. 第一反射器由 launchd 在登录时启动，并每 30 分钟巡检一次。
2. GBrain 只允许一个调度所有者：cron 每 30 分钟执行 sync、每 6 小时执行 dream。`com.gbrain.autopilot` 必须保持 disabled；常驻 autopilot 与 cron 同时存在视为 P1 调度冲突。
3. GBrain 外层守护不得使用无界 `KeepAlive=true`。每次 cron 任务必须记录真实成功时间；`sync` 只索引本地工作树并使用 `--no-pull`；`Skipped/cycle locked` 不得记为 success。
4. 熵检测由 Hermes One 的确定性 no-agent 脚本 `v9-entropy-shadow.py` 执行，不依赖 LLM 自行解释旧 skill；只写 shadow 报告，不建治理任务、不修改或删除笔记。
5. 第一反射器只由 `com.xirang.v9reflex` 调度；Hermes 中旧的重复 V9 巡检任务必须保持 paused。
6. OpenClaw Gateway 不再承担 V9 调度，默认 disabled 且无 `RunAtLoad/KeepAlive`；需要使用时仅人工启动，用毕关闭。
7. session guard 独立检查反射器 launchd 和快照新鲜度，避免“观察者自己死亡却仍显示旧绿灯”。
8. 任一运行时检查失败时，先恢复既有机制；不得用新增规则或方法论版本掩盖运行链故障。
