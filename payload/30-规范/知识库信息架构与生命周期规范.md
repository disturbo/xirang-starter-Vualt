# 知识库信息架构与生命周期规范

本规范定义通用 Vault 的目录职责、文件去向、链接与归档。具体项目的品牌、字段和业务规则必须进入项目目录，不能污染通用骨架。

## 目录职责

| 目录 | 唯一职责 | 不应放入 |
|---|---|---|
| `00-MOC/` | 导航、主题索引、能力清单 | 正文副本、过程日志 |
| `02-项目管理/` | 任务投影与项目管理入口 | 业务真源、人工改写的机器状态 |
| `10-项目/` | 活跃项目及其局部规则、交付物 | 跨项目通用规范 |
| `20-资料/` | 外部原始资料、来源记录和可追溯摘要 | 未标来源的结论 |
| `30-规范/` | 跨项目稳定、当前有效、能指导执行的规则 | 过程方案、测试报告、历史演变稿 |
| `40-决策/` | 有长期影响的选择、理由、替代方案和影响 | 普通会议流水账 |
| `50-经验/` | 可复用经验、教训与方法论宪法 | 一次性过程文件 |
| `60-归档/` | 已结束、已替代且仍需保留的内容 | 当前活跃真源 |
| `70-模板/` | 无个人与项目数据的可复制模板 | 已填写实例 |

## 文件判定

新建前依次回答：这是导航、业务成果、外部资料、跨项目规则、长期决策、可复用经验、历史归档还是模板？已有唯一真源时优先链接，不复制第二份。无法归类时先放项目内部的待整理区，不擅自新增顶层目录。

规范、方法论和模板采用稳定主题文件名；版本、状态和日期放入 frontmatter。临时文件、测试输出、转换缓存和候选包不进入实时知识库。

## 生命周期

- `draft`：允许讨论和修改，不能作为强制规则引用；
- `current`：当前可执行真源，必须有明确作用域与维护者；
- `superseded`：已被新真源替代，写明替代链接后移入归档或依靠 Git 历史保存；
- `historical`：只作背景，禁止反向覆盖 current；
- `archived`：项目或主题结束，不再出现在当前工作台。

同一规则域只保留一个 `current` primary。过程文件在结论进入当前真源、任务证据或 Git 后清理，不因“以后可能有用”长期占据规范与方法论目录。

## 链接、MOC 与孤儿页

1. 新建正文必须从至少一个 MOC、项目 README 或上位正文可达；模板和机器生成投影除外。
2. 重命名或移动前检索所有 Wiki 链接、Markdown 链接和嵌入；更新后运行断链检查。
3. MOC 只导航，不复制正文；每个列表项说明“为什么要点进去”。
4. 外部来源记录原始 URL/文件、获取日期和转化方式；整理结论与原始材料分层保存。
5. 每次发行检查孤儿 current 规范、同名 current 真源、空目录占位和失效附件。

## 打包与升级

知识库框架是 `seed_if_absent`：新用户获得完整骨架，旧用户缺什么补什么，已经存在的首页、MOC、模板、资料、经验和项目内容不被覆盖。息壤机器契约与明确登记的宪法文档才是 `managed_core`；插件运行配置和 workspace 状态属于 `user_mutable`，不进入发行包。

## 验收

- [ ] 文件位于唯一正确目录，未产生第二真源；
- [ ] current 文档有作用域、状态、版本或更新时间；
- [ ] 新页从导航可达，内部链接无断链；
- [ ] 无个人路径、账号、密钥、项目专属数据和运行缓存；
- [ ] 打包生命周期分类与真实升级行为一致。
