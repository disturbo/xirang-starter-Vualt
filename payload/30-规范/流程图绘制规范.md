# 流程图绘制规范

本规范用于跨项目稳定的业务流程、泳道流程和状态流转图。它约束语义、结构、连线和验收，不绑定品牌或具体业务；当目标是飞书画板时，必须执行本页的飞书原生对象门禁。

## 1. 先判断是否需要画图

适合画图：

- 三步以上的业务顺序；
- 两个以上角色或系统之间的交接；
- 存在判断、驳回、重试、异常或并行；
- 一个对象有明确状态迁移。

不适合画图：单一事实、简单清单、字段说明或没有顺序关系的分类。它们使用正文、表格或列表更清楚。

## 2. 选择最小充分格式

| 场景 | 推荐格式 | 交付要求 |
|---|---|---|
| 简单线性流程、随正文维护 | Markdown Mermaid | 源码留在正文，实际渲染通过 |
| 正式业务流程、复杂泳道 | Draw.io | 必须交付可编辑 `.drawio` 源文件 |
| 正式飞书流程图 | 飞书原生画板 | `table/frame + composite_shape + connector`，写后 raw 回读与预览验收 |
| 自由讨论、草图和空间关系 | Excalidraw | 保留可编辑源数据，不只交截图 |
| 状态迁移 | Draw.io 或 Mermaid | 同时提供状态字段表 |

PNG、截图和导出的静态 SVG只能作为预览，不能替代正式可编辑源文件。

会议纪要中识别出的流程先回到 [[会议纪要整理规范]] 保留来源、原文依据和未知项，再进入本规范建模；不得为了让图看起来完整而补写会议中没有的节点或规则。

## 飞书原生对象门禁

正式飞书流程图必须使用原生 `table/frame + composite_shape + connector`；Mermaid、PlantUML、SVG、图片和 DSL 只能作中间稿或诊断，不得以 `group`、散落 `text_shape` 或独立网格线拼成伪可编辑流程图。用户提供参考白板时，动手前先回读 reference raw 并导出预览，登记对象模型、表格结构、节点几何、字号、连接器绑定和路由指标。

写入正式画板使用顶层 `{ "nodes": [...] }` raw 结构。写后必须回读并至少确认：`unattached=0`、`nonOrthogonalSegments=0`、`crossings=0`、`text_shape=0`、`group/image=0`；随后导出预览检查文字截断、箭头、密度与阅读顺序。结构或视觉任一失败都不得报告完成。

## 3. 写图前先结构化

至少明确以下对象：

```yaml
title: 流程名称
actors:
  - id: actor-a
    name: 角色或系统
nodes:
  - id: n-start
    actor: actor-a
    label: 提交申请
    type: start|action|decision|data|exception|end|state
edges:
  - source: n-start
    target: n-review
    type: main|branch|reject|async
    label: ""
```

硬规则：

1. 节点ID唯一，所有边的起止节点真实存在；
2. 动作节点使用清晰的动词短语，状态节点使用名词；
3. 每个判断至少有两个出口，每个出口都有条件文字；
4. 异常、驳回和重试必须有明确去向，不能停在线上；
5. 图里出现的角色、状态和关键条件能在配套正文中找到解释。

## 4. 选择结构

### 4.1 线性流程

单一参与者、顺序清楚且分支很少时使用。从左到右或从上到下保持一个主阅读方向。

### 4.2 水平泳道

多个角色或系统参与时使用：泳道横向延伸、上下排列，角色名位于左侧，主流程从左到右。

- 单图建议不超过七个泳道；更多角色应拆主流程和子流程；
- 节点必须位于真实所属泳道，不靠视觉位置冒充归属；
- 跨泳道连线优先走空白走廊，避免穿过中间节点。

### 4.3 状态流转图

表达一个对象的状态变化时使用。每条边写明触发条件，并在正文提供：状态码、中文名称、进入条件、允许出口和终态说明。

## 5. 形状就是语义

| 类型 | 形状 | 用法 |
|---|---|---|
| 开始、结束 | 圆角药丸形 | 每个独立流程至少有明确开始和终点 |
| 动作 | 圆角矩形 | 一个节点只表达一个动作 |
| 判断 | 菱形 | 出口条件必须写在线上 |
| 数据或文档 | 平行四边形或文档形 | 只在数据本身是流程对象时使用 |
| 异常 | 圆角矩形加异常语义 | 不能只靠红色区分 |
| 状态 | 圆角矩形 | 文字使用状态名词 |

同一张图中，同一语义必须使用同一形状和视觉语言。颜色只作辅助，不能成为唯一语义。

## 6. 布局与间距

- 主阅读方向只能有一个，普通主流程不得来回折返；
- 节点宽度和高度保持少量固定规格，不按每段文字随意变化；
- 相邻节点之间保留足够连线走廊，建议至少60px；
- 同层节点中心线对齐，泳道边界和标题区对齐；
- 长文字优先改写或换行，不无限放大节点；
- 画布四周保留安全边距，任何文字、箭头或图例不得被裁切；
- 图例只解释无法直接写在图上的少量约定，不能替代节点和连线文字。

## 7. 连线规则

1. 每条业务边必须绑定真实起点和终点，禁止用自由线段贴近节点伪造连接；
2. 主流程优先使用正交线，直连能表达时不增加折点；
3. 普通边尽量不超过两个折点，驳回和外围回路不超过四个；
4. 连线不得穿节点、压文字、相互重叠或在非节点处形成T形汇合；
5. 多条边需要汇合时新增明确的汇合节点；
6. 判断出口必须有不重复的条件标签；
7. 实线、虚线和颜色只能表达已在规范中定义的关系；
8. 箭头终点落在目标节点边界，不能悬空或穿入节点内部。

复杂图必须显式规划端口和路径；无法无歧义布线时拆图，不用更小字号硬塞。

## 8. 视觉基线

- 使用中性、低饱和的浅色背景；
- 正文文字不小于12px，正式全图预览中必须可读；
- 普通文字与背景满足至少4.5:1的对比度；
- 红色仅用于异常或阻断，黄色仅用于提醒或判断；
- 不使用项目品牌色，除非目标项目提供自己的上位规范；
- 不靠大量Emoji、阴影或渐变装饰流程。

## 9. 验收

正式交付前同时做结构检查和真实渲染检查。

结构检查：

- [ ] 节点ID唯一，边引用全部有效；
- [ ] 判断出口不少于两个且条件非空；
- [ ] 所有业务边两端真实绑定；
- [ ] 没有悬空线、穿节点、非业务交叉和重叠线；
- [ ] 泳道归属、状态入口和终点完整；
- [ ] 可编辑源文件与预览来自同一版本。

渲染检查：

- [ ] 在目标工具中实际打开，没有语法或加载错误；
- [ ] 全图缩放到常用阅读宽度时仍能读清标题和主流程；
- [ ] 局部放大检查判断出口、跨泳道线和外围回路；
- [ ] 没有裁切、文字溢出、节点遮挡或箭头悬空；
- [ ] 配套正文中的角色、状态和条件与图一致。

任何检查无法执行时，必须报告未验证项，不能以“文件已生成”代替验收。
