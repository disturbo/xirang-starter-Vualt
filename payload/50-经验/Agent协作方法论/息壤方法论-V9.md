# 息壤方法论 V9.7

> 本页负责把当前方法讲完整，不负责替代机器契约。发生冲突时，立即停止采用本页，按 `.xirang/contract/policy.yaml`、根 `AGENTS.md`、`.xirang/adapters/PROTOCOL.md` 和 SQLite StateStore 的当前记录执行，并修复本页。

## 一句话定义

息壤是一套面向真实工作区的 AI 协作治理方法：人用自然语言给出目标和决定，系统把它冻结成有边界的执行包络，Agent 在包络内连续工作，机器记录状态与证据，最后由执行者之外的人验收。

它既不是一篇提示词，也不是“多开几个 Agent”。它解决的是 AI 真正进入项目后最容易失控的六件事：目标变形、权限外溢、多人撞写、过程失忆、结果无证据、执行者自我宣布完成。

“息壤”取自会生长的土。这里的生长不是让规则和文件无限增殖，而是让任务、证据、教训和能力在明确管辖权下持续演化。没有治理的增殖只是新的信息洪水。

## 适用前提：持久工作区

息壤不强制使用 Obsidian，但要求项目拥有一个可持久化、可检索、可链接、可审计的工作区。只存在聊天记录时，Agent 无法可靠接手、恢复或证明依据。

当前工作区的持久上下文由四类对象共同组成：

1. 项目文件保存业务事实与交付物；
2. 根规则和嵌套 `AGENTS.md` 保存当前行为边界；
3. SQLite StateStore 保存授权、执行包络、任务、租约、阶段、收据、交付与验收；
4. handoff 检查点保存跨会话的已完成项、当前状态、下一步和踩坑记录。

不同平台可以另有用户上下文或策展记忆，但不存在所有平台都必须拥有的通用 `MEMORY.md`。任何记忆都只是辅助召回，不能单独扩大授权、改变任务状态或证明外部现实。

## 六条不变量

1. **先有授权**：副作用必须绑定此前已展示的目标、范围、排除项、影响和验收方。
2. **权限取交集**：允许做什么同时取决于规范化路径和操作类型；目录可写不等于允许删除、移动、发布或维护控制面。
3. **重要改动可恢复**：通过逐文件 pre-image、Git、数据库快照、事务 journal 或其他已验证机制提供恢复路径。
4. **结论有新鲜证据**：文件存在、配置存在、脚本通过或历史报告都不能单独证明能力当前接通。
5. **执行者不自验收**：Agent 只能把交付推进到 `submitted`，不能把自己的结果写成 `accepted`。
6. **闭环必须收敛**：发现问题、修复、再验证、确认性审核有预算和终止条件，不能无限重试或用同一证据循环证明自己。

## 四层边界

| 层 | 回答的问题 | 典型对象 | 生命周期 |
|---|---|---|---|
| 息壤基建 | 谁能做什么、状态如何推进、证据和恢复如何成立 | `.xirang/`、`.standards/`、StateStore、适配器、正式测试、根规则 | 版本化、受控发布 |
| 工作平台 | 人和 Agent 从哪里使用息壤 | Codex、Claude、Obsidian、飞书、浏览器 | 按平台安装和 canary 管理 |
| 任务产物 | 某次执行、验证或审查临时产生了什么 | 候选包、测试库、一次性报告、截图、日志导出 | 证据绑定后清理实时副本 |
| 业务内容 | 这个项目实际要交付什么 | PRD、原型、代码、资料、业务决策 | 按项目规范管理 |

同一个文件名里出现“息壤”不代表它就是基建。判断标准是删除或修改它是否会改变授权、门禁、状态、证据、验收、恢复或发布安全。详细裁决见 [[息壤基建与工作平台边界]]。

## 权威结构：正文不是第二真源

| 规则域 | 权威来源 | 本正文的职责 |
|---|---|---|
| 平台无关机器规则 | `.xirang/contract/policy.yaml` | 解释为什么存在这些规则 |
| Agent 结构化约束 | `.standards/agent-contract.yaml` | 解释 Agent 应如何理解 |
| 工作区行为 | 根 `AGENTS.md` 与适用的嵌套规则 | 解释在项目里会看到什么 |
| 维护协议 | `.xirang/adapters/PROTOCOL.md` | 解释授权、收据、交付和恢复的关系 |
| 当前运行状态 | 外置 SQLite StateStore | 解释任务卡、租约和 handoff 的作用 |
| 专项规则 | [[息壤规范管辖权]] 登记的 primary | 提供导航，不复制第二份规范 |

正文可以完整讲解，但不能人工维护另一套字段、状态和阈值。精确列表只在少量“受控事实块”中出现，并由 `python3 .standards/xirang-task.py contract-lint` 对照真源校验。

## 人、Agent 与执行包络

### 包络是什么意思

“执行包络”可以理解为一次任务的权限边界盒子。盒子里冻结了：这次要达成什么、可写哪些位置、允许哪些操作、明确不做什么、可能产生什么影响、谁来验收。换 Agent、压缩上下文或跨会话接力不会自动换盒子；目标或权限实质扩大时才需要新的决定。

一个包络只有一个主任务。主任务 owner 负责推进阶段和收口；参与者通过 worker lease 获得包络的子集权限。handoff 只传上下文，不传权限。

### 不再依赖固定六 Agent

当前方法不规定固定六 Agent，也不按 Agent 名字永久分配目录。执行者来自哪个平台、叫什么名字，不决定权限；当前任务和有效租约才决定权限。

固定六 Agent、基于角色名的路径 Owner、把 prompt-build 产物当作运行授权，这些做法已被当前架构取代，但不属于 Policy 明确退役清单。prompt-build 仍可作为某些平台的构建或预览工具；只有真实应用和 canary 才能证明平台入口生效。

## 开工仪式仍然存在

开工仪式不是口号，也不要求用户说固定暗号。它是第一次副作用前的一次可见边界展示，用于让人知道 Agent 将改变什么，并让系统有机会把这次决定绑定为不可变执行包络。

### 它由哪一层约束

| 层 | 作用 |
|---|---|
| `.xirang/contract/policy.yaml` | 规定开工展示必须存在以及最小机器字段 |
| 根 `AGENTS.md` 与 `.xirang/adapters/PROTOCOL.md` | 要求 Agent 在写入前用人话展示完整边界，同一包络不重复确认 |
| 平台适配器 | 接收用户事件、记录展示与模型动作提议；不能冒充用户身份 |
| StateStore | 固化 objective、disclosure、authorization、envelope 和 task 的关联 |
| pre-write / post-write | 在具体写入时重新核对任务、租约、路径、操作和最终证据 |

因此，开工仪式既在 Agent 根规则里可见，也在息壤基建里有机器记录和写入检查。只有文字声明而没有控制面消费者，不能声称已经硬约束；只有数据库记录而用户看不到范围，也不构成合格交互。

### 展示什么

Policy 的机器授权字段是：`objective`、`write_scope`、`exclusions`、`irreversible_effects`、`external_effects`、`acceptance_owner`。

面向人的开工展示还应补充两类上下文：

- **对象层级**：本次改的是基建、平台、任务产物还是业务内容；
- **恢复路径**：重要改动如果失败，依靠什么恢复。

它们不能混成第二份机器字段表。层级帮助理解，恢复路径满足安全不变量，真正的权限仍由规范化路径和操作类型决定。

示例：

```text
任务：补齐息壤方法论正文
层级：息壤基建的人类说明层
写入范围：方法论正文、运行时契约卡、对应 lint
排除：不发布、不删除历史脚本、不改业务内容
不可逆/外部影响：无
恢复：逐文件 pre-image + Git diff
验收方：用户
```

用户对这份边界表达“执行”“继续做”等当前、明确决定后，系统应在同一包络内连续完成实现、验证和修复；不能每改一个文件都重新追问。

## 任务卡

任务卡仍然存在，但职责已经改变。它不再是靠 Agent 手写并反向驱动门禁的授权文件，而是 SQLite 权威任务的确定性 Markdown 投影，便于人在 Vault 中阅读。

当前任务卡展示：主任务身份、任务类型、owner 会话、活动 worker lease 摘要、允许路径和操作、影响与验收方、最新 handoff、最新 delivery、验证和提交摘要。逐路径 grants、完整阶段运行和收据仍保存在 StateStore。

任务卡本体由投影器管理，不允许混入人工内容。用户备注写到任务卡旁边同名的 `T-<task_id>.notes.md` 文件；任务卡通过 `user_notes_path` 指向它。`.notes.md` 不由投影器创建或覆盖，也不能反向改变授权、阶段或验收状态。

这一区分解决两个矛盾：机器投影仍可确定性校验，用户又不会因为刷新任务卡丢失自己的备注。

## 从目标到验收：两个视角

### 给人的五阶段工作流

下面是面向人的压缩视图，不是第二套状态机：

1. **理解目标**：读取当前项目、规则和现场，把口语请求翻译成可验收目标。
2. **冻结边界**：展示开工仪式，绑定用户决定，建立一个包络和一个主任务。
3. **连续执行**：按计划实现；需要并行时签发范围更小的 worker lease，并在阶段变化时写 handoff。
4. **验证修复**：运行最近的有效验证，做发现性审核；有问题就修复、再验证、再确认。
5. **提交验收**：精确列出变化和证据，提交为 `submitted`；由具名验收方接受、退回或取消。

这个五阶段视图用于记忆和沟通。项目自身还可以有“需求—资料—方案—PRD—评审”等业务工作流；业务流程决定做什么，息壤决定 AI 如何被授权、如何留下证据和如何验收，两者不能互相替代。

### 机器运行阶段

以下是受控事实块，来源为 `runtime_state_machine.main_flow`：

```text
authorized
→ preparing
→ implementing
→ validating
→ discovery_review
→ repairing
→ revalidating
→ confirmation_review
→ committing
→ submitted
```

- `authorized`：授权链和包络已经成立；
- `preparing`：读取现场、确认依赖和恢复路径；
- `implementing`：在授权交集内改变目标对象；
- `validating`：运行可复现验证并绑定证据；
- `discovery_review`：主动发现缺陷，不负责宣布完成；
- `repairing` / `revalidating`：修复后必须重跑验证；
- `confirmation_review`：确认阻断项已闭环；
- `committing`：核对精确 manifest、收据和最终哈希；
- `submitted`：等待他人验收，不等于 accepted。

旧版“拆分→计划→执行→监控→检核→验收”可以作为历史教学概括，但不再是当前 StateStore 的状态机。

## 多 Agent、接力与对抗性审查

多 Agent 是按任务风险和上下文隔离需要启用的执行方式，不是固定编制。

- owner session 推进唯一主任务；
- worker lease 冻结来源会话、工作会话、角色、只读标志、路径、操作和有效期；
- worker 权限是包络与 lease 的交集；
- handoff 保存完成项、当前状态、下一步和踩坑，但不能授予权限；
- lease 过期会挂起任务，不能靠复制 handoff 绕过。

高风险控制面、权限、状态机、并发、支付或跨系统一致性任务可以启用 [[息壤V9-多Agent对抗性审查协议]]。Challenger 是同一任务下的只读 worker，在 `discovery_review` / `confirmation_review` 内证伪，不创建新状态机，也不能替人验收。

## 写入、证据与恢复

每一次真正的文件变化都要经过三层检查：

1. **写前**：当前任务或租约是否有效，路径和操作是否在授权交集内；
2. **写后**：实际落盘路径、存在性和最终 SHA 是否与预期一致，并形成 `file_write` 收据；
3. **交付前**：精确 manifest 中的每个对象是否都有当前有效证据，是否仍是最终字节。

重要改动在写前建立恢复依据。对于文件可以是 pre-image 或 Git；对于 SQLite 是一致性快照和 WAL；对于发布是候选字节、baseline CAS、事务 journal 与 receipt。恢复能力只证明“能回去和能追踪”，同一系统用户可改写的本地文件、HMAC、Tag 或数据库不构成强隔离和不可抵赖性。

控制面发生故障时分开处理：缺少用户授权就不写；已有授权且逐路径 pre-image 与带外审计成立时，可以保留未提交的工作树改动；写后证据失败只阻断提交；验收证据失败只阻断验收。不得为了“干净”而销毁已有恢复证据的合法现场。

## 阻断、续接与收敛

常见暂停状态包括预算耗尽、不收敛、外部依赖故障、需要用户作重大选择和租约过期。预算窗口恢复、依赖恢复或重新取得同包络租约后可以续接，不需要用户复述原授权。

只有以下情况暂停向用户要新决定：

- 目标、路径或操作范围扩大；
- 将发生此前未披露的不可逆动作；
- 将外发、发布或切换生产；
- 出现会改变结果方向的重大业务选择；
- 找不到可靠恢复路径。

连续两轮没有新证据，或重复同一个阻断原因，必须进入不收敛状态，换独立策略或升级人类，不能继续消耗资源。

## 提交与验收

交付不是“文件写完了”，而是候选内容、精确清单、最终哈希、验证结论和剩余风险形成同一个可指向版本。

`submitted` 表示执行者已经提交待验收；`accepted` 只能由真实用户对当前具体 delivery 作出无条件接受产生。普通的“好”“继续”“方案可以”可能只是在讨论或授权继续工作，不能静默验收其他任务。

当前会话有交付焦点时，决定绑定该 delivery；跨会话必须由用户明确指出任务或交付内容。全局状态页、“最新提交”或 Workspace 唯一候选都不能替代明确关联。

## 平台模式与能力真实性

| 模式 | 能做什么 | 不能声称什么 |
|---|---|---|
| `trusted` | 宿主证明用户事件、展示顺序、单次消费、worker 身份和不可绕过门禁 | 缺任何当前证据就不能使用该等级 |
| `manual_guard` | 自然授权、路径检查、外置证据、连续执行和恢复 | 不可抵赖、强隔离、宿主已验证身份或 `connected` |
| `contract_only` | 读取共享协议和做只读诊断 | 控制面授权、文件写入和状态改变 |

一个能力只有调度、输入、输出、消费者、行为效果和新鲜证据全部存在时才算接通。配置存在是 configured；可选模块未启用是 `not_enabled`；入口或 canary 未验证是 `unverified`。

GBrain、Phoenix、CodeRef、状态面板、业务发布器和平台专属增强都是可选模块。可选模块缺失不应破坏最小闭环，但也不能被正文写成已运行能力。

## 最小息壤包

最小息壤包是把普通工作区变成“可授权、可约束、可恢复、可验收”工作区的最小闭包，不是任何个人工作区的完整复制，也不包含具体项目业务资料。

| 层 | 最小内容 | 缺失后的真实状态 |
|---|---|---|
| 人类入口 | 根 `AGENTS.md`、普通入口、维护入口 | 没有稳定使用界面 |
| 机器契约 | Policy、管辖权、恢复根和工作区绑定 | 只能解释规则，不能可靠约束 |
| 平台适配 | 共享 PROTOCOL、适配注册、平台入口 | 对应平台只能 contract_only 或 unverified |
| 权威状态 | SQLite StateStore、任务/租约/阶段协调器、单向投影 | 不能声称运行闭环成立 |
| 写入与恢复 | 写前检查、写后收据、pre-image、快照和恢复器 | 不能安全提交文件变化 |
| 交付与验收 | 精确 manifest、delivery、焦点和他人验收 | 只能报告变化，不能形成正式交付 |
| 安装与自检 | VERSION、包清单、校验和、安装入口、正反 canary | 只是源码集合，不是可分发产品 |

最小指的是职责闭包，不是文件数最少。任何裁剪只要破坏授权、恢复或验收中的一环，就不能再称为可运行息壤包。

## 安装、更新与卸载

### 安装后的本机位置

- 工作区：由用户指定，安装器不假设用户名、桌面目录或 Vault 名称；
- 工作区机器契约：目标目录下 `.xirang/`；
- 权威运行根：由 `.xirang/local-config.json` 绑定到当前用户目录下的独立工作区运行根；
- 息壤基建发布状态必须以安装 Manifest、StateStore 权威检查和当前 canary 结果共同为准，源码或 wrapper 存在不能替代状态检查。

### 对外下载状态

[xirang-starter-Vualt](https://github.com/disturbo/xirang-starter-Vualt) 是公开源码仓库，[GitHub Releases](https://github.com/disturbo/xirang-starter-Vualt/releases) 是正式下载入口。正式包沿用 `xi-rang-v{version}-starter.zip` 命名结构，例如 V9.7.1 为 `xi-rang-v9.7.1-starter.zip`；官网只提供一个通用包，由 Agent 自动判断全新安装、受支持旧版升级、当前版本修复或需要人工协助，普通用户不选择版本路线，也不手工运行命令。

安装、更新和恢复都以同一个 Release 内的版本、manifest、校验和和操作说明为准：

- 安装验证包闭包、工作区绑定和正反 canary；
- 更新从可信 Tag/Commit 构建，使用 baseline CAS 和事务恢复；
- 恢复只还原该事务登记的受管文件、运行根和调度配置，不删除业务工作区、未知文件或 Git 历史。

V9.7 系列提供安装、升级、校验与失败恢复；尚未发布独立卸载动作，因此不得把手工删除目录包装成官方卸载。

## 发布与血缘

息壤基建发布和业务应用生产发布不是同一个对象。前者管理本机控制面，后者由具体项目规定 Tag、包结构、服务器目录、健康端点和保留策略。

两者共享的原则是职责分离：Tag/Commit/Tree 证明源码身份；artifact/manifest Hash 证明实际字节；签名或等价证据证明来源；baseline CAS 防止并发覆盖；journal 与 receipt 证明切换最终结果。任何一层都不能替代其他层。

提交点前失败应恢复旧版本且 baseline 不变；提交点后 current、baseline 与 receipt 已一致时，后续清理失败进入 finalize/recover，不倒退已生效版本。具体基建流程见 [[息壤V9-运行时契约卡]]。

## 与公开旧版页面的关系
