# 息壤 V9.7 运行时契约卡

> 本卡是 Agent 速查，不是机器真源。发生冲突时停止采用本卡，按 `.xirang/contract/policy.yaml`、根 `AGENTS.md`、`.xirang/adapters/PROTOCOL.md` 和 StateStore 等高位真源执行并修卡。

## 开工

只读任务直接完成。写入、删除、外发、发布或运行有副作用脚本前，一次性展示边界；用户对该边界表达当前执行意图后，同一包络内连续工作，不重复确认。

机器披露字段必须完整：

- `objective`：要达成什么；
- `write_scope`：规范化写入路径；
- `exclusions`：明确不做什么；
- `irreversible_effects`：不可逆影响，没有也要如实为空；
- `external_effects`：外发、发布、生产或其他外部影响；
- `acceptance_owner`：具名验收责任方。

人类展示另补对象层级、允许的操作类型和恢复路径。层级用于理解，恢复路径用于安全，真正权限仍为“路径范围 ∩ 操作类型”。

## 任务与包络

- 一个执行包络只有一个主任务；
- owner session 推进任务；其他执行者必须取得同任务 worker lease；
- worker 权限是包络与 lease 的交集；
- 换 Agent、压缩上下文和跨会话续接不扩大权限；
- handoff 只传完成项、当前状态、下一步和踩坑，不传权限；
- 范围扩大、未披露不可逆影响、外发/发布、重大选择或缺少恢复路径才暂停。

## 任务卡

SQLite StateStore 是任务状态真源。Markdown 任务卡只是确定性投影，展示 task kind、owner session、活动 worker lease、路径和操作、影响、验收方、最新 handoff/delivery、验证与提交摘要。

任务卡本体不得人工编辑。用户备注写入 `user_notes_path` 指向的同名 `.notes.md` 文件；投影器不创建、不覆盖该文件，也不把其中内容解释为授权、阶段或验收状态。

## 执行阶段

```text
authorized
→ preparing
→ implementing
→ validating
→ discovery_review
→ repairing
→ revalidating
→ confirmation_review
→ committing
→ submitted
```

- 发现性审核负责找问题，确认性审核负责确认修复闭环；
- 修复后必须重跑验证并再次审核；
- 有阻断项不得进入 `committing`；
- 风险触发型多 Agent 对抗性审查在既有两个 review 阶段内运行，不新增阶段；
- Challenger 使用同一任务下的只读 lease，报告是证据，不是 StateStore 真源。

## 写入与证据

1. pre-write 校验当前任务或租约、阶段、规范化路径和操作；
2. 重要改动写前建立逐文件 pre-image、Git 或其他已验证恢复依据；
3. 每次成功写入立即记录实际路径、操作、最终存在性和 SHA 的 `file_write` 收据；
4. post-write 失败时保留可恢复现场，但禁止提交；
5. 交付前核对精确 manifest，禁止 `git add .`、`git add -A` 或把无证据文件重新分类绕过；
6. 用户排除 Git commit 时使用 `files_no_git`，必须有最终 SHA、有效收据和登记 pre-image，并明确 Git 可恢复性未提供。

## 阻断与恢复

- `blocked_budget`：预算窗口或独立维护调整后续接；
- `blocked_external_dependency`：健康探针确认恢复后续接；
- `suspended_lease_expired`：同包络取得新租约后续接；
- `blocked_nonconvergent`：独立审核给出不同策略后只允许受控续接；
- `awaiting_material_user_choice`：唯一必须取得用户新决定的暂停状态。

连续两轮没有新证据或重复同一阻断原因时停止循环。恢复工具只使用登记恢复根；快照、manifest 或 Hash 不成立时失败关闭。

## StateStore 与投影

SQLite 保存用户事件、目标、披露、授权、包络、任务、租约、阶段、收据、handoff、delivery、焦点、偏好、outbox 和审计事件。

任务卡、状态页、JSONL 和报告只能单向投影。投影与 SQLite 不一致时报告漂移，禁止从 Markdown 猜测或恢复权威状态。数据库由 `.xirang/local-config.json` 和 cutover sentinel 唯一定位；传入其他 DB 或运行根时失败关闭。

## 平台模式

- `trusted`：宿主对用户事件、展示顺序、单次消费、worker 身份和不可绕过门禁都有当前证明；
- `manual_guard`：提供自然授权、显式路径检查、外置证据和恢复，四类 verified 标志保持 false；
- `contract_only`：只读诊断，不改变控制面或文件。

配置存在只表示 configured。调度、输入、输出、消费者、行为效果和新鲜证据齐全才可报告 connected；`manual_guard` 不能冒充 trusted，同用户权限不能声称强隔离。

## 外部与破坏性动作

Vault 外写入必须冻结绝对路径和文件/目录类型，并逐路径授权。删除前验证精确目标、所有权、类型和恢复路径；禁止宽泛删除系统临时目录、用户目录、生产包或 Git 历史。

发布、push、生产切换和外部发送必须在执行包络中明确出现。普通文件写入授权不能推导出发布授权。

## 基建发布

息壤基建发布管理本机控制面，不等于业务网站发布。候选从干净 annotated Tag 构建；运行根独立核对 Tag object/Commit、祖先关系、artifact spec、包 SHA、manifest 闭包、Zip Slip、baseline CAS、事务 journal、receipt 及包与生产树等价关系。

首次 bootstrap 只允许写当前用户拥有的空 `0700` 运行根，并在目录锁内只读冻结输入包。`current` 是最终提交点：提交点前失败恢复为空根或旧版本，提交点后清理失败进入 finalize/recover，不回滚已生效版本。

源码、测试、Tag、wrapper 或 baseline 任一单项都不能证明已激活。只以本机 `xirang-release-lineage status` 当前验证为准；同用户安装仍报告 `manual_guard`、`strongIsolation=false`。

## 业务产品发布

业务应用可以复用源码身份、字节 Hash、来源证明、baseline CAS 和事务 receipt 的职责分离，但 Tag 命名、包结构、服务器目录、健康端点和保留策略由具体项目规则决定。Vault 基建 baseline 不能替代业务服务器 current release。

## 退役与迁移

V8 runtime、M3/M4/M5、二元触发器、pre-flight、亮灯、旧心跳、A2A Mock 和旧成本熔断不参与当前运行或验收。旧 `gate-enforce.py`、`pre-write-hook.sh` 和任务卡 schema 仅为 `migration_legacy` 兼容资产；现行入口是平台适配器与 SQLite StateStore。

## 交付与验收

验证、审核、精确清单、当前哈希和全部写入收据齐全后，交付推进到 `submitted`。执行者不能自验收。

当前会话验收绑定有效 delivery 焦点；跨会话必须由用户明确指向任务或交付。普通讨论、继续工作、全局状态页、“最新提交”或 Workspace 唯一候选都不能自动变成 `accepted`。
